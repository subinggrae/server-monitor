## 접근 방법

묶음에서 운영 명령은 설치 폴더의 `.env`(`$INSTALL_DIR/.env`)를 읽는다. 그리고 `install`, `render`, `start`가 묶음 폴더에 `../.env`를 가리키는 상대 심볼릭 링크 `.env`를 만든다. docker compose는 묶음 폴더의 `.env`를 자동으로 읽어 compose 파일의 `${CORE_PROMETHEUS_PORT}`, `${CORE_SECRETS_DIR}` 등을 채운다. 그래서 링크를 두면 운영 가이드의 `docker compose` 명령을 옵션 없이 그대로 써도 설치 폴더의 값을 쓴다. 2026-11-11에 `docker:cli` 컨테이너에서 `../.env`를 가리키는 링크를 두고 `docker compose config`를 실행해, 링크된 파일의 값(`P=19090`)으로 포트를 채우는 것을 확인했다.

검토했지만 고르지 않은 방법은 다음과 같다.

- **compose를 부를 때마다 `--env-file ../.env`를 붙인다**: 운영 명령 안에서는 되지만, 운영 가이드의 수동 명령(멈추기, token 바꾸기)에도 매번 붙여야 한다. 빠뜨리면 Compose가 기본 포트와 기본 token 폴더로 컨테이너를 다시 만든다. 실수했을 때 결과가 조용히 틀어져서 고르지 않았다.
- **운영 명령이 이전 버전의 `.env`를 새 폴더로 복사한다**: 사람이 요구사항에서 자동 복사를 하지 않기로 했다(S5).
- **링크 대신 설치 폴더 `.env`를 묶음 폴더로 복사한다**: 두 파일이 어긋날 수 있고, 어느 쪽을 고쳐야 하는지 헷갈린다.

저장소 개발용 배치(`LAYOUT=repository`)는 지금처럼 `infrastructure/.env`를 읽는다. 링크도 만들지 않는다.

## 바뀌는 부분

파일마다 바꾸는 것은 다음과 같다.

- **`infrastructure/core-server.sh`**:
  - 묶음 배치에서 `ENV_FILE`을 `$INSTALL_DIR/.env`로 바꾼다.
  - `check_env`에 S5, S6, S7 판정을 넣는다.
  - 링크를 만드는 함수를 더해 `install`, `render`, `start`에서 부른다.
  - `install`은 설치 폴더에 `.env`를 만든다.
- **`infrastructure/tests/core-server.test.sh`**:
  - 시험이 쓰는 설정 파일을 `$INSTALL/.env`로 바꾼다.
  - 링크 시험을 더한다.
  - S5 시험을 더한다(이전 묶음에만 있음, 지금 묶음에만 있음).
  - S6 시험을 더한다(양쪽에 있음, 링크가 다른 곳을 가리킴).
  - S7 시험을 더한다.
- **`infrastructure/.env.example`**: 머리 주석에 설치 폴더의 `.env`로 복사해 쓴다고 적는다.
- **`scripts/build-core-bundle.mjs`**: 묶음 compose 머리 주석의 "바꿀 값은 .env"를 "설치 폴더의 .env"로 고친다.
- **`docs/OPERATIONS.md`**:
  - 다음 곳을 새 위치로 고친다: 설치 4~5단계, 폴더 모양, 새 버전으로 갱신(복사 단계 삭제), 이전 버전으로 되돌리기, 운영 명령이 없던 묶음에서 갱신, 운영 명령 없이 실행, 문제 해결 표
  - 이전 방식 서버를 한 번 옮기는 절차를 더한다.
- **`docs/INTEGRATION.md`**: 코어 설정의 "내부망 묶음에서는 묶음 폴더의 `.env`"를 설치 폴더로 고친다.
- **`docs/decisions/0013-core-env-in-install-folder.md`**: 설정 파일 위치와 링크 방식의 결정을 ADR로 남긴다.

폴더 모양은 다음처럼 바뀐다.

```text
전                                   후
/opt/monitoring/                     /opt/monitoring/
├── secrets/                         ├── .env              ← 모든 버전이 읽음
├── certs/                           ├── secrets/
└── monitoring-core-<버전>/          ├── certs/
    ├── .env                         └── monitoring-core-<버전>/
    └── …                                ├── .env -> ../.env  (운영 명령이 만드는 링크)
                                         └── …
```

### 데이터 모델 변경

해당 없음

### 계약 변경

- 운영자와의 약속: 묶음의 설정 파일 위치가 묶음 폴더에서 설치 폴더로 바뀐다. 설정 값의 이름, 기본값, 허용 범위는 그대로다.
- 관리자 서버와의 계약(API, 네트워크, token 파일 위치)은 바뀌지 않는다.

## 위험과 되돌리기

- **이전 방식 서버에서 갱신하다 멈춤**: 설치 폴더에 `.env`가 없으면 `start`가 코어를 바꾸지 않고 복사 명령을 보여 준다(S5). 운영 가이드에 한 번 옮기는 절차를 둔다.
- **운영자가 묶음 폴더의 링크를 실제 파일로 바꿔 둠**: 어느 값이 쓰이는지 헷갈리므로 S6로 멈추고 지우라고 안내한다. 링크가 `../.env`가 아닌 다른 곳을 가리켜도 같다.
- **이 변경 전 묶음으로 되돌림**: 그 묶음은 자기 폴더의 `.env`를 읽는다. 옮길 때 이동이 아니라 복사로 안내해, 이전 폴더에 파일이 남게 한다.
- **링크를 만들 수 없는 파일 시스템**: 설치 폴더는 Linux 코어 서버의 로컬 디스크라 링크를 만들 수 있다. 만들지 못하면 `ln` 오류를 보이고 멈춘다.
- **되돌리기**: 이 변경을 되돌린 묶음을 쓰려면 설치 폴더의 `.env`를 묶음 폴더로 복사하고 링크를 지운다.

### 보안 위협

- 바뀌는 신뢰 경계와 데이터 흐름: 운영 명령이 묶음 폴더에 링크를 만든다. 이 링크는 운영 명령이 정한 상대 경로 `../.env`만 가리킨다.
- 잘못될 수 있는 것과 막는 방법: 링크 따라가기로 다른 파일을 덮어씀(CWE-59) → 운영 명령은 `.env`에 쓰지 않고 읽기만 한다. `install`은 링크가 아니라 설치 폴더의 실제 경로에 새 파일을 만든다. 묶음 폴더의 `.env`가 다른 곳을 가리키는 링크면 따라가지 않고 S6로 멈춘다.
- 받아들이는 위험: 없음

## 진행 중 발견

- 하위 에이전트 리뷰(HEAD `ee940dc`)에서 다음을 찾아 고쳤다.
  - 이전 설정 파일을 찾을 때 설치 폴더의 모든 하위 폴더를 이름순으로 봐서, 관리자 서버 폴더의 `.env`나 오래된 버전을 고를 수 있었다. 코어 묶음 폴더(`monitoring-core-*`)만 보고, 가장 최근에 고친 파일을 고르게 했다.
  - `install`이 설치 폴더의 `.env` 자리에 있는 링크를 따라 쓸 수 있었다(CWE-59). 설치 폴더 `.env`가 링크면 읽지도 쓰지도 않고 멈추고, 새 파일은 같은 폴더에 쓴 뒤 이름을 바꾼다.
  - 확인을 기다리는 동안 묶음 폴더의 링크가 바뀔 수 있어, 링크를 만들기 직전에 다시 확인한다.
- 이 단계에서는 compose가 링크를 따라 읽는 것을 자동으로 검사하지 않는다. 빌드 검사는 Windows 빌드 PC에서 compose를 실행하는데, 그곳에서는 링크를 만들기 어렵기 때문이다. 그래서 C3는 코어 서버의 수동 확인으로 둔다.
