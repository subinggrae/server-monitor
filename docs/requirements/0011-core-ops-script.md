# 0011. 코어를 빌드하고 운영하는 명령

- 상태: 구현됨
- 작성일: 2026-10-23
- 관련: [0010](0010-core-image-bundle.md), [ADR 0009](../decisions/0009-core-config-in-image.md), [#33](https://github.com/subinggrae/server-monitor/issues/33), [#35](https://github.com/subinggrae/server-monitor/issues/35), [PR #36](https://github.com/subinggrae/server-monitor/pull/36)(구현 계획과 확인 기록 포함)

## 배경

코어를 다루는 명령이 빌드 PC와 코어 서버에 흩어져 있다. 빌드 PC에서는 묶음을 만들 때 `node scripts/build-core-bundle.mjs`, 설정만 검사할 때 같은 스크립트의 `--check`, 개발용으로 띄울 때 `docker compose -f infrastructure/compose.yml up -d --build`를 쓴다. 코어 서버의 운영자는 [운영 가이드](../OPERATIONS.md)를 보고 `sha256sum`, `docker load`, `docker compose`를 차례로 직접 실행해 코어를 띄우고 갱신한다. gradle의 `build`, `bootRun`처럼 스크립트 하나에 작업 이름을 붙여 쓰기로 했다(사람 확인: 2026-10-28). 빌드 PC는 Windows이고 코어 서버는 Linux이므로, 빌드 PC용은 Windows 배치 파일, 코어 서버용은 sh로 만든다(사람 확인: 2026-10-28).

코어 서버의 절차에서 생기는 실수 가운데 일부는 이미 막힌다. 관리자 서버 주소가 없으면 Compose가 멈추고, 이미지를 불러오지 않았으면 인터넷에서 받지 않고 멈추며, 설정과 규칙은 빌드할 때 검사한다. 다음 실수는 명령이 성공으로 끝나거나, 실제 장애가 날 때까지 드러나지 않는다.

- **체크섬 확인을 건너뜀**: 망가진 묶음을 그대로 불러온다.
- **token 파일 없이 띄움**: 갱신하면서 이전 폴더의 `.env`를 가져오지 않아 token 폴더가 기본값으로 돌아간 경우도 같다. `up -d`는 성공으로 끝나고, Docker가 token 자리에 빈 폴더를 만들며, Alertmanager는 계속 다시 시작한다.
- **token 권한이 컨테이너 사용자가 읽지 못하는 값임**: Alertmanager가 계속 다시 시작한다.
- **token을 바꾼 뒤 `up -d`만 실행함**: Alertmanager가 옛 token을 계속 써서 장애 수신이 모두 거부된다. 실제 장애가 나기 전까지 모른다.
- **띄운 뒤 상태를 확인하지 않음**: 어느 컨테이너가 정상이 아닌지 모른다.
- **이전 버전 폴더에서 띄움**: 경고 없이 이전 버전으로 바뀐다.
- **`down -v`를 실행함**: 15일치 기록이 확인 없이 지워진다.

token 폴더는 버전 폴더 밖의 고정 경로에 두라고 권하지만, 그 경로는 운영자가 `.env`에 직접 적어야 한다. 갱신할 때마다 이 값을 옮기는 것도 실수할 곳이다.

코어는 사람이 멈추지 않는 한 서버가 재시작돼도 다시 떠야 한다(사람 확인: 2026-10-28). 세 컨테이너는 이미 `restart: unless-stopped`로 설정되어 있지만, 이 설정은 서버가 켜질 때 Docker도 자동으로 켜져야 동작한다. 이 조건은 서버마다 다르고 지금은 아무도 확인하지 않는다.

설정을 이미지 밖으로 빼거나 서버마다 다른 Alert 규칙을 두는 방안은 검토했으나 필요하지 않다(사람 확인: 2026-10-23). 실수를 줄이는 방법으로, 이미 있는 명령을 정해진 순서로 실행하고 띄우기 전에 검사하는 운영 명령을 코어 묶음에 넣기로 했다(사람 확인: 2026-10-23).

## 목표

- 빌드 PC(Windows)에서 저장소의 명령 하나로 작업 이름만 바꿔 묶음 만들기, 설정 검사, 개발용 코어 띄우기와 멈추기를 한다.
- 코어 서버(Linux)에서 묶음의 운영 명령 하나로 처음 설치, 갱신, 되돌리기, token 바꾸기, 상태 보기를 한다. 띄우기는 체크섬 확인, 사전 검사, 이미지 불러오기, 띄우기, 정상 상태 확인을 차례로 실행한다.
- 배경의 실수를 Docker가 컨테이너를 띄우기 전에 찾아, 무엇이 잘못됐는지와 어떻게 고치는지 알린다.
- 묶음 폴더들은 한 상위 폴더(설치 폴더)에 나란히 두고, token 폴더는 설치 폴더의 `secrets/`로 정해 둔다. 운영자가 token 경로를 입력하거나 고치지 않는다(사람 확인: 2026-10-23). 설치 폴더의 위치는 어디든 된다.
- 처음 설치할 때 token 파일과 설정 파일을 운영 명령이 맞는 위치와 권한으로 만든다. 갱신할 때는 같은 설치 폴더에서 지금 떠 있는 버전의 폴더를 찾아 설정을 가져온다.
- token을 바꾸는 일을 운영 명령 하나로 하고, Alertmanager가 새 token을 쓰게 한다.
- 코어는 사람이 멈추지 않는 한 서버나 Docker가 재시작된 뒤 다시 뜬다. 띄우기 명령은 서버가 켜질 때 Docker가 자동으로 켜지는지 확인하고, 꺼져 있으면 켜는 방법을 알린다(사람 확인: 2026-10-28).
- 운영 명령은 코어 서버에 기본으로 있는 도구와 Docker만으로 동작한다. 인터넷, 저장소, Node가 필요 없다.

## 하지 않는 것

- 설정 검증, 설정 백업, 실패 시 설정 복원. 설정은 이미지에 들어 있고 빌드할 때 검사한다([ADR 0009](../decisions/0009-core-config-in-image.md)).
- 기록까지 지우는 명령. 실수로 실행할 길을 줄이기 위해 어느 명령에도 넣지 않고, 지금처럼 `docker compose down -v`로만 한다.
- 코어 서버 운영 명령의 Windows판. 코어와 관리자 서버는 Linux에만 올린다(사람 확인: 2026-10-28).
- Linux나 macOS 빌드 PC용 명령. 빌드 PC는 Windows다(사람 확인: 2026-10-28). 빌드 스크립트를 직접 실행하는 방법은 남는다.
- 개발용 코어 띄우기에 코어 서버용 사전 검사와 설치 준비를 넣는 것. 개발에서는 지금처럼 token을 `infrastructure/secrets/`에 둔다.
- 감시 대상 서버의 exporter 설치 명령과 windows_exporter 묶음. [#35](https://github.com/subinggrae/server-monitor/issues/35)에서 요구사항 0012로 다룬다(사람 확인: 2026-10-28).
- 서버가 켜질 때 Docker가 자동으로 켜지도록 운영 명령이 서버 설정을 바꾸는 것. 확인하고 방법만 알린다.
- 관리자 서버의 token이 코어와 같은지 확인하는 것. 관리자 서버는 코어를 쓰는 쪽이 띄우므로 코어 쪽에서 알 수 없다.
- 관리자 서버를 띄우거나 다시 띄우는 것
- 묶음 폴더 안에 둔 기존 token을 설치 폴더로 자동으로 옮기는 것. 운영 명령은 옮기라고 안내만 한다.
- 관리자 서버 주소와 token 밖의 코어 설정을 서버에서 바꾸게 하는 것. 바꿀 값이 생기면 YAML을 열지 않고 그 값만 설정 파일의 변수로 열기로 했고(사람 확인: 2026-10-23), 어떤 값을 열지는 [#33](https://github.com/subinggrae/server-monitor/issues/33)에서 정한다.

## 사용자 경험

사용자는 두 부류다. Windows 빌드 PC에서 묶음을 만들고 개발하는 개발자와, Linux 코어 서버에서 코어를 띄우는 운영자다.

개발자는 저장소 폴더에서 빌드 PC용 명령에 작업 이름을 붙여 실행한다.

1. 개발용으로 띄울 때는 띄우기 작업을 실행한다. 바뀐 설정으로 이미지를 다시 만들어 띄운다.
2. 설정과 규칙을 바꿨으면 설정 검사 작업으로 확인한다.
3. 서버에 옮길 묶음이 필요하면 묶음 만들기 작업을 실행한다.
4. 개발을 마치면 멈추기 작업으로 코어를 멈춘다.

코어 서버의 폴더는 다음 모양이 된다.

```text
설치 폴더/
├── secrets/alertmanager_webhook_token
├── monitoring-core-<이전 버전>/
└── monitoring-core-<새 버전>/
```

운영자가 처음 설치할 때는 다음 순서를 따른다.

1. 운영자가 설치 폴더를 정하고 묶음 폴더를 그 안에 옮긴다.
2. 운영자가 설치 준비 명령을 실행하고 관리자 서버 주소를 넣는다. 운영 명령이 token 파일과 설정 파일을 만든다.
3. 운영자가 띄우기 명령을 실행한다. 운영 명령이 체크섬을 확인하고, 사전 검사를 하고, 이미지를 불러와 띄운 뒤, 세 컨테이너가 정상이 될 때까지 기다려 결과와 버전을 보인다.

갱신할 때는 다음 순서를 따른다.

1. 운영자가 새 묶음 폴더를 이전 묶음 폴더 옆에 옮긴다.
2. 운영자가 새 폴더에서 설치 준비 명령을 실행한다. 운영 명령이 지금 떠 있는 버전의 폴더에서 설정을 가져온다.
3. 운영자가 띄우기 명령을 실행한다. 떠 있는 버전과 새로 띄울 버전이 보인다.

되돌릴 때는 이전 묶음 폴더에서 띄우기 명령을 실행한다. 지금보다 이전 버전으로 바뀐다는 확인을 받은 뒤 띄운다.

## 동작

### 정상 동작

- **S1. 처음 설치 준비**
  - 상황: 코어를 띄운 적이 없는 서버의 설치 폴더에 묶음 폴더가 있다.
  - 행동: 운영자가 설치 준비 명령을 실행하고 관리자 서버 주소를 넣는다.
  - 결과: 설치 폴더에 token 폴더가 운영자만 열 수 있는 권한으로 생긴다. 그 안에 예측할 수 없는 값의 token 파일이 컨테이너 사용자가 읽을 수 있는 권한으로 생긴다. 묶음 폴더에 관리자 서버 주소를 담은 설정 파일이 생긴다. token 값은 화면에 보이지 않는다.
- **S2. 띄우기**
  - 상황: 설치 준비를 마친 묶음 폴더가 있다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 체크섬 확인, 사전 검사, 이미지 불러오기(서버에 그 버전 이미지가 없을 때만), 띄우기가 차례로 실행된다. 세 컨테이너가 3분 안에 정상 상태가 되면 띄운 버전과 커밋이 보이고 성공으로 끝난다.
- **S3. 갱신 준비**
  - 상황: 이전 버전의 코어가 떠 있고, 새 묶음 폴더를 이전 묶음 폴더 옆에 옮겼다.
  - 행동: 운영자가 새 폴더에서 설치 준비 명령을 실행한다.
  - 결과: 같은 설치 폴더에서 지금 떠 있는 버전의 묶음 폴더를 찾아 그 설정 파일을 새 폴더로 복사하고, 어느 폴더에서 가져왔는지 보인다. token은 설치 폴더에 있으므로 옮기지 않는다.
- **S4. 새 버전으로 갱신**
  - 상황: S3을 마쳤다.
  - 행동: 운영자가 새 폴더에서 띄우기 명령을 실행한다.
  - 결과: 떠 있는 버전과 새 버전이 보이고, 새 버전으로 바뀐다. 쌓아 온 기록과 Alert 상태가 이어진다.
- **S5. 이전 버전으로 되돌리기**
  - 상황: 새 버전이 떠 있고, 이전 묶음 폴더가 남아 있다.
  - 행동: 운영자가 이전 폴더에서 띄우기 명령을 실행한다.
  - 결과: 지금보다 이전 버전으로 바뀐다는 확인을 묻는다. 운영자가 확인하면 이전 버전으로 바뀌고, 확인하지 않으면 아무것도 바꾸지 않는다.
- **S6. token 바꾸기**
  - 상황: 코어가 떠 있다.
  - 행동: 운영자가 token 바꾸기 명령을 실행한다.
  - 결과: token 파일이 새 값으로 바뀌고, Alertmanager가 새 값으로 다시 만들어져 정상 상태가 된다. 관리자 서버도 다시 띄워야 한다는 안내와 관리자 서버가 붙일 token 파일의 실제 경로가 보인다. token 값은 화면에 보이지 않는다.
- **S7. 상태 보기**
  - 상황: 코어가 떠 있거나 멈춰 있다.
  - 행동: 운영자가 상태 명령을 실행한다.
  - 결과: 떠 있는 코어의 버전, 커밋, 세 컨테이너의 상태가 보인다. 이 묶음 폴더의 버전과 떠 있는 버전이 다르면 그 사실도 보인다.
- **S14. 서버 재시작**
  - 상황: 코어가 떠 있고, 서버가 켜질 때 Docker가 자동으로 켜지도록 설정되어 있다.
  - 행동: 서버가 재부팅되거나 Docker가 다시 시작된다.
  - 결과: 사람이 아무것도 하지 않아도 세 컨테이너가 다시 떠 정상 상태가 된다. 사람이 멈춘 코어는 다시 뜨지 않는다.
- **S15. 빌드 PC에서 묶음 만들기**
  - 상황: Windows 빌드 PC에 저장소, Docker, Node가 있다.
  - 행동: 개발자가 빌드 PC용 명령의 묶음 만들기 작업을 실행한다.
  - 결과: 지금 빌드 스크립트와 같은 묶음이 만들어지고, 그 안에 코어 서버용 운영 명령이 들어 있다.
- **S16. 빌드 PC에서 설정 검사**
  - 상황: S15와 같다.
  - 행동: 개발자가 설정 검사 작업을 실행한다.
  - 결과: 이미지를 빌드해 Prometheus 설정 검사, 규칙 테스트, Alertmanager 설정 검사를 실행하고 결과를 보인다. 묶음은 만들지 않는다.
- **S17. 빌드 PC에서 개발용으로 띄우고 멈추기**
  - 상황: 저장소의 `infrastructure/`에 설정 파일과 token 파일이 있다.
  - 행동: 개발자가 띄우기 작업을, 개발을 마친 뒤 멈추기 작업을 실행한다.
  - 결과: 띄우기는 바뀐 설정으로 이미지를 다시 만들어 코어를 띄운다. 멈추기는 코어를 멈추고 쌓은 기록은 남긴다.

### 예외 동작

S18을 뺀 모든 예외 동작에서 명령은 무엇이 잘못됐는지와 고치는 방법을 한국어로 보이고, 실패로 끝난다.

- **S8. 망가진 묶음**
  - 상황: 묶음 파일이 옮기는 중에 잘렸거나 바뀌었다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 어느 파일의 체크섬이 맞지 않는지 보이고, 이미지를 불러오거나 띄우지 않는다.
- **S9. 설정 파일이 없거나 관리자 서버 주소가 잘못됨**
  - 상황: 설치 준비를 하지 않았거나, 설정 파일의 관리자 서버 주소가 비어 있거나 `컨테이너 이름:포트` 형식이 아니다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 설치 준비 명령을 실행하거나 주소를 고치라는 안내가 보이고 띄우지 않는다.
- **S10. token이 없거나 쓸 수 없음**
  - 상황: 설치 폴더의 token 파일이 없거나, 비어 있거나, 그 자리에 폴더가 있거나, 컨테이너 사용자가 읽을 수 없는 권한이다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 네 경우를 구분해 알리고 띄우지 않는다. 묶음 폴더 안에 token이 있으면 설치 폴더로 옮기라는 안내도 보인다. token 자리에 Docker가 빈 폴더를 새로 만드는 일이 생기지 않는다.
- **S11. 정상 상태가 되지 않음**
  - 상황: 띄운 컨테이너 가운데 하나가 3분 안에 정상 상태가 되지 않는다.
  - 행동: 운영자가 띄우기 명령이나 token 바꾸기 명령을 실행했다.
  - 결과: 정상이 아닌 컨테이너와 그 로그를 보는 명령이 보인다. 이미 띄운 컨테이너는 그대로 둔다.
- **S12. 설치 준비를 다시 실행함**
  - 상황: token 파일이나 설정 파일이 이미 있다.
  - 행동: 운영자가 설치 준비 명령을 실행한다.
  - 결과: 이미 있는 token과 설정을 덮어쓰지 않고, 이미 있다는 사실을 알린다.
- **S13. 가져올 설정을 찾지 못함**
  - 상황: token은 설치 폴더에 있는데, 떠 있는 코어가 없거나 떠 있는 버전의 묶음 폴더가 같은 설치 폴더에 없다.
  - 행동: 운영자가 새 폴더에서 설치 준비 명령을 실행한다.
  - 결과: 설정을 가져올 폴더를 찾지 못했다고 알리고, 관리자 서버 주소를 물어 설정 파일을 만든다. token은 새로 만들지 않는다.
- **S18. 서버가 켜질 때 Docker가 켜지지 않음**
  - 상황: 코어 서버에서 Docker가 서버 시작 때 자동으로 켜지도록 설정되어 있지 않다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 서버가 재시작되면 코어가 뜨지 않는다는 경고와 자동 시작을 켜는 명령을 보인다. 띄우기는 계속하고, 확인할 수 없는 환경이면 확인하지 못했다고 알린다.
- **S19. 알 수 없는 작업 이름이거나 Docker가 꺼져 있음**
  - 상황: 빌드 PC용 명령이나 운영 명령에 없는 작업 이름을 줬거나, Docker가 실행 중이 아니다.
  - 행동: 개발자나 운영자가 명령을 실행한다.
  - 결과: 쓸 수 있는 작업 목록이나 Docker를 켜라는 안내가 보이고, 아무것도 바꾸지 않는다.

### 보안

- 접근 권한: 빌드 PC용 명령은 저장소를 가진 개발자가, 운영 명령은 Docker를 쓸 수 있고 설치 폴더에 쓸 수 있는 서버 운영자가 실행한다. 코어 포트는 지금처럼 `127.0.0.1`에만 연다.
- 외부 입력: 운영자가 넣는 관리자 서버 주소, 설정 파일의 내용, 설치 폴더 안의 다른 폴더 이름, 명령에 준 작업 이름. 관리자 서버 주소는 `컨테이너 이름:포트` 형식만 받는다.
- 민감한 정보: webhook token. 운영 명령은 token 값을 화면, 로그, 설정 파일에 쓰지 않는다. token 폴더는 운영자만 열 수 있게, token 파일은 컨테이너 사용자가 읽을 수 있게 만든다. 법이 암호화를 요구하는 항목은 아니다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 코어 이미지의 내용, 통합 계약([INTEGRATION.md](../INTEGRATION.md))
- 세 컨테이너의 재시작 정책 `restart: unless-stopped`
- 빌드 스크립트와 `docker compose`를 직접 실행하는 절차도 동작한다. 코어 서버에서 직접 실행하면 token은 설치 폴더의 `secrets/`에서 읽는다.
- 설정 파일에 token 폴더를 직접 적은 서버는 그 경로를 그대로 쓴다.
- 코어와 관리자 서버가 같은 token 파일을 읽는 방식
- 네트워크 이름 `monitoring`, 데이터 volume 이름, 기록 보관 15일
- 묶음에 비밀값이 들어가지 않는다.
