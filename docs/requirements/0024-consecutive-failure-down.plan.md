## 접근 방법

두 Alert 규칙의 `for: 1m`을 없애고, 최근 확인 결과를 길이가 다른 창(range) 여러 개로 보는 상태 없는 식 하나로 판정한다. 결정과 이유는 [ADR 0015](../decisions/0015-check-down-by-result-windows.md)에 있다.

창 하나(길이 W)의 조건은 다음 세 가지다. 세 조건을 모두 채우는 창이 하나라도 있고, 최근 5분 안에 확인 결과가 있으면 장애다.

1. 창 안의 확인 결과가 모두 실패다(`max_over_time == 0`).
2. 창 안의 확인 결과가 3개 이상이다(`count_over_time >= 3`).
3. 창 안에 60초보다 오래된 확인 결과가 있다(`count_over_time([W−60s] offset 60s) > 0`).

창에 성공이 들어가지 않으면서 3번째 실패와 60초 넘은 실패를 함께 담는 길이가 있으면 연속 실패가 기준을 채웠다. 그런 길이의 범위는 마지막 성공과 첫 실패 사이에서 끝나므로 폭이 수집 주기 이상이다. 그래서 창 길이 사이 간격을 주기보다 좁게 두면 기준을 채운 첫 규칙 평가에서 장애가 된다. 창 길이는 70, 80, 90, 100초(주기 30초 이하가 1분에 걸리는 구간이라 10초 간격), 그 위로는 앞 길이의 1.25배 안쪽인 125, 155, 190, 235, 290, 360, 450, 560, 700, 900초다. 주기 T가 30초보다 길면 필요한 창이 3T보다 짧고 간격이 창 길이의 1/4 이하라서 T보다 좁다. 900초(15분)는 요구사항 S9의 이어 세는 범위다.

두 id로 묶어(`by (check_id, check_target_id)`) 세므로, 이름·환경·확인 방식·주소를 바꿔 series가 바뀌어도 한 대상의 확인 결과로 이어서 센다. range 함수는 실제로 수집한 표본만 세고 stale 표시는 세지 않으므로, 지금 식의 "가장 최근 series만 보는" 처리가 필요 없다. 옛 series의 마지막 성공은 그 시각의 표본일 뿐이라 새 series의 뒤 실패를 가리지 않는다. 최근 5분 조건은 지금의 `last_over_time(...[5m])`과 같은 역할(지우거나 끈 대상의 복구 시점)을 한다.

검토했지만 고르지 않은 방법은 ADR 0015의 검토한 선택지에 있다. 요약하면 다음과 같다.

- 가. 주기 값마다 규칙을 만들고 `for`로 기다림: `startsAt`이 첫 실패 시각으로 남지만, 규칙이 약 420개가 되고 주기를 series label로 남겨야 해서 배포와 주기 변경 때 series가 끊긴다. 주기를 바꾸면 같은 label의 Alert를 두 규칙이 함께 보낸다.
- 나. 연속 실패 횟수를 recording rule로 이어 셈: 직전 평가 결과에 기대므로 재시작, 평가 누락, stale 표시 때 횟수가 틀어질 수 있고 promtool로 그 상태를 재현하기 어렵다.

## 바뀌는 부분

| 위치 | 변경 |
|---|---|
| `infrastructure/prometheus/rules/monitoring-checks.yml` | 두 규칙의 식, `for`, annotation, 머리 주석 |
| `infrastructure/prometheus/tests/monitoring-checks.test.yml` | 기존 기댓값 고침, 새 시나리오 더함 |
| `docs/INTEGRATION.md` | Alert 절의 판정 기준·시간·annotation·`startsAt`, SD 절의 150초 한계 |
| `docs/OPERATIONS.md` | 감시 흐름(19행)과 장애 기준(387행) |
| `docs/ADMIN-SERVER.md` | `{발생시각}`의 뜻, 같은 장애의 기준 |
| `docs/decisions/0015-check-down-by-result-windows.md` | 새 ADR |

파일마다 바꾸는 내용은 다음과 같다.

- **규칙**: 두 규칙의 식을 위 창 판정으로 바꾸고 `for: 1m`을 지운다. `description`을 요구사항의 문장으로 바꾸고 `judgment_failures: "3"`, `judgment_min_seconds: "60"` annotation을 더한다. 머리 주석의 "지금 값 `or` 최근 5분" 설명을 창 판정 설명으로 바꾼다.
- **규칙 테스트**: 기존 시나리오의 `ALERTS_FOR_STATE` 기댓값(판정 시각), annotation, 성공 중 변경 뒤 실패 시나리오의 판정 시각을 고친다. 테스트 계획의 새 시나리오를 더한다.
- **INTEGRATION.md**: Alert 절의 webhook 예시 annotation, annotation 표(두 annotation 더함), 도착 시간 문단(판정 식, 주기별 표, 시간 구성, 대상이 실패하기 시작한 때부터의 최대 시간), `startsAt`의 뜻과 첫 실패 추정 식, 배포 순서를 고친다. SD 절의 150초 한계 문장은 새 판정에서 확인한 결과로 고친다.
- **ADMIN-SERVER.md**: `{발생시각}`을 장애로 판정한 시각이라고 고치고, 같은 장애의 기준에 모니터링 시스템을 다시 띄울 때도 시작 시각이 새로 온다고 더한다.
- **ADR 0015**: ADR 0002의 감수할 점 한 줄과 ADR 0010의 식 구조(지금 값 `or` 최근 5분)만 대신한다.

### 데이터 모델 변경

해당 없음. 수집한 series와 SD label은 바뀌지 않는다.

### 계약 변경

[INTEGRATION.md의 Alert](../INTEGRATION.md#alert-post-apiintegrationsalertmanagerwebhook)에서 다음이 바뀐다.

| 항목 | 이전 | 새 값 |
|---|---|---|
| 장애가 되는 기준 | 실패가 1분 이어짐 | 연속 3번 실패하고 첫 실패 뒤 1분이 지남(첫 실패부터 `max(60초, 주기 × 2)`) |
| `startsAt` | 실패를 처음 본 규칙 평가 시각 | 장애로 판정한 규칙 평가 시각 |
| annotation | `summary`, `description` | `summary`, `description`, `judgment_failures`(`"3"`), `judgment_min_seconds`(`"60"`) |
| `description` | "…1분 넘게 실패하고 있습니다…" | "…3번 이상 연속으로 실패했습니다…" |

Alert label, `fingerprint`, 묶음과 다시 보내는 간격, 복구 webhook은 바뀌지 않는다. 계약을 확인하는 테스트는 규칙 테스트의 `exp_labels`, `exp_annotations`, `ALERTS_FOR_STATE`다.

## 위험과 되돌리기

- 창 길이 사이에 틈이 있어 어떤 주기에서 판정이 늦거나 빠짐: 계획 단계에서 10~240초 정수 주기 231개 × 위상 4가지를 1초 단위로 만든 promtool 테스트로 판정 직전 평가에는 장애가 없고 판정 평가에는 있음을 확인했다(진행 중 발견). 저장소의 규칙 테스트에는 경계 주기(10, 29, 30, 31, 61, 119, 240초 등)를 넣는다. 창 길이를 바꾸면 같은 확인을 다시 한다.
- 규칙 계산 비용: 평가마다 대상당 range 조회 85개(창 14개 × 3 + 최근 5분, 규칙 2개)다. 가장 긴 창 900초에 든 표본은 주기 10초에서 90개라 대상 수백 개에서도 작다. 문제가 되면 Prometheus의 `prometheus_rule_group_last_duration_seconds`로 알아챈다.
- `startsAt`의 뜻이 바뀌어 관리자 서버의 장애 기록이 둘로 갈림: 관리자 서버가 같은 장애를 `fingerprint` 기준으로 판단하게 먼저 배포한 뒤 새 판정을 배포한다(요구사항의 배포 순서).
- 되돌리기: 모니터링 서버에서 `sh monitoring-server.sh rollback`으로 직전 버전으로 돌아간다. 기록과 설정은 이어진다. 되돌린 뒤 진행 중 장애는 이전 규칙으로 다시 판정하므로 `startsAt`이 새로 오고, `fingerprint`는 같다.

### 보안 위협

해당 없음. 외부 입력, 인증·권한, 개인정보, 의존성을 건드리지 않는다. 더하는 annotation은 규칙에 적은 상수다.

## 테스트 계획

규칙 테스트는 `node scripts/build-monitoring-bundle.mjs --check`가 운영 이미지에서 꺼낸 규칙으로 실행한다. 작업 중에는 Dockerfile `src` 단계 이미지의 `promtool test rules`로 그 파일만 실행한다.

| 완료 기준 | 테스트 | 기대 결과 |
|---|---|---|
| C1 | 주기 10초(위상 2가지)와 15초 대상의 판정 직전 평가와 판정 평가 | 첫 실패 + 60초 뒤 첫 평가에서 firing, 그 직전 평가는 Alert 없음 |
| C2 | 주기 31초, 60초, 61초, 119초, 240초 대상 | 3번째 실패 뒤 첫 평가에서 firing, 2번째 실패 뒤와 판정 직전 평가는 Alert 없음 |
| C3 | 주기 60초, 실패·실패·성공·실패·실패·실패 | 성공 뒤 3번째 실패 전에는 Alert 없음, 뒤에는 firing |
| C4 | 기존 살아난 주소 시나리오 + 주기 60초 장애 중 성공 | 성공 표본 뒤 평가에서 Alert 없음 |
| C5 | 주기 15초로 실패 2번 뒤 120초로 바꿈 | 바꾸기 전 실패를 이어 세어, 3번째 실패와 첫 실패 + 60초를 모두 채운 뒤 첫 평가에서 firing |
| C6 | 기존 값 변경 시나리오 4개(stale 표시 있음·없음, 수집 틈 15초·4분, stale 표시 늦게 씀, 성공 중 변경 뒤 실패) | 판정 시각만 새 기준으로 고친 기대값으로 통과 |
| C7 | 기존 감시 항목 2(계속 성공) | Alert 없음 |
| C8 | 기존 지운 주소 시나리오 + 주기 60초에서 실패 2번 뒤 끊김 | 장애 중이던 대상은 마지막 결과 5분 뒤부터 Alert 없음, 실패 2번 뒤 끊긴 대상은 끝까지 Alert 없음 |

## 진행 중 발견

- 2026-11-18 계획 단계 promtool 시험(Prometheus v3.14.0, 저장소 밖 임시 폴더). 창 판정 식으로 다음을 확인했다.
  - 주기 10~240초 정수 231개 × 위상 4가지를 1초 단위로 넣으면 모두 판정 직전 평가에 Alert가 없고 판정 평가(`max(60, 2T)` 뒤 첫 평가)에 있다.
  - 지금 규칙 테스트를 그대로 돌리면 Alert의 발생·복구 시각, label 유지, 지운 대상 5분 판정은 모두 통과하고, `ALERTS_FOR_STATE`(시작 시각)만 다르다. 지금은 실패를 처음 본 평가 시각, 새 식은 판정 시각이다. 이 차이로 `startsAt`의 뜻을 사람에게 물었다(요구사항 S10).
