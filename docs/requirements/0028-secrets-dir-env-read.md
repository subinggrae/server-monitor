# 0028. 경로 설정 값을 운영 명령과 Compose가 같게 읽기

- 상태: 구현됨
- 작성일: 2026-11-25
- 관련: [0011](0011-core-ops-script.md), [0013](0013-core-env-settings.md), [0017](0017-core-shared-env.md), [0027](0027-ca-file-path.md), [ADR 0018](../decisions/0018-ca-file-path.md), [OPERATIONS.md](../OPERATIONS.md), 지운 계획은 [PR #74](https://github.com/subinggrae/server-monitor/pull/74)에서 볼 수 있다

## 배경

모니터링 서버의 `.env`에는 경로 설정 값이 두 개 있다. token 폴더 값(`MONITORING_SECRETS_DIR`)은 Alertmanager가 관리자 서버의 webhook을 부를 때 붙이는 token 파일의 폴더다. CA 인증서 파일 경로 값(`MONITORING_CA_FILE`)은 Blackbox Exporter가 HTTPS 확인에 쓰는 OS의 CA 인증서 파일이다([0027](0027-ca-file-path.md)). 운영 명령(`monitoring-server.sh`)은 두 값으로 파일 위치를 정해 검사하고, compose 파일은 같은 값으로 그 파일을 컨테이너에 붙인다. 운영 명령이 검사한 파일과 Compose가 붙이는 파일이 같아야 검사가 뜻이 있다.

운영 명령의 `.env` 읽기는 Compose를 흉내 내지만 똑같지 않다. 2026-11-25에 같은 표기의 `.env`를 Compose(Docker Compose v5.7.0)와 운영 명령(공식 Prometheus 이미지 v3.5.0에 든 BusyBox sh)에 주어 token 폴더 값을 비교했다. 결과는 다음과 같다.

- 운영 명령이 읽지 않는 표기로 token 폴더를 적으면, 운영 명령은 값이 없다고 보고 기본 위치(설치 폴더의 `secrets/`)의 token을 검사했다. 기본 위치에 token이 있으면 `render`가 성공했다. 같은 `.env`에서 Compose는 적힌 폴더의 token 파일을 붙이는 설정을 만들었다.
- 운영 명령이 값을 읽지만 Compose와 다른 값으로 읽는 표기도 있었다. 시험한 표기에서는 운영 명령이 실제로 없는 경로를 검사해 멈췄으므로, 검사하지 않은 파일로 뜨지는 않았다.

token 폴더 값은 `start`가 Compose에 넘기지 않는다. 그래서 Compose가 `.env`를 스스로 읽고, 위 첫 경우에 검사하지 않은 위치의 token 파일로 뜬다. 그 위치에 파일이 없으면 Docker가 그 자리에 빈 폴더를 만들고 Alertmanager가 계속 다시 시작한다([0011](0011-core-ops-script.md)의 배경). 파일이 있으면 검사를 거치지 않은 파일을 token으로 쓴다. 그 값이 관리자 서버의 token과 다르면 관리자 서버가 장애를 모두 거부하고, 실제 장애가 나기 전까지 아무도 모른다. 이 어긋남은 0027의 독립 리뷰에서 찾았다.

CA 인증서 파일 경로 값은 0027부터 `start`가 검사한 값을, 값이 없다고 본 경우에는 빈 값을 Compose에 넘긴다. 그래서 `start`로 띄우면 검사한 파일이 붙는다. 하지만 운영 명령이 읽지 않는 표기로 OS의 파일 경로를 적은 운영자는 그 파일 대신 설치 폴더의 복사본(`certs/ca-certificates.crt`)이 조용히 쓰이는 줄 모른다. 복사본이 오래됐으면 새 인증서를 쓰는 HTTPS 주소의 확인이 실패한다.

검사한 값을 Compose에 넘기는 것만으로는 token 폴더 값을 고칠 수 없다. 지금 이 어긋남 덕분에 관리자 서버와 같은 token으로 돌고 있는 서버가 있을 수 있기 때문이다. 운영 명령이 읽지 않는 표기로 다른 폴더를 적었고, 기본 위치에도 `install`이 만든 token이 있는 서버다. 이런 서버에서 검사한 기본 위치만 넘기면 다음 `start`부터 token이 조용히 바뀌어 장애가 거부된다. 또 운영 가이드의 token 바꾸기처럼 운영자가 묶음 폴더에서 직접 실행하는 `docker compose` 명령은 여전히 Compose가 `.env`를 스스로 읽는다([0017](0017-core-shared-env.md)의 목표). 그러면 `start`와 그 명령이 서로 다른 파일을 붙인다. 그래서 운영 명령이 읽지 않는 표기를 만나면 멈추고 운영자가 고치게 하기로 했다(사람 확인: 2026-11-25). CA 인증서 파일 경로 값도 같은 원인이므로 이번에 함께 멈추게 한다(사람 확인: 2026-11-25).

Windows 개발 환경의 `monitoring-dev.bat start`에도 같은 종류의 어긋남이 있다. 이 명령은 운영 명령의 `render`를 Linux 컨테이너 안에서 실행하고, Compose는 Windows에서 실행한다. 셸 환경 변수가 `.env`보다 먼저 쓰이도록 설정 값의 셸 환경 변수를 컨테이너에 넘기지만, token 폴더 값은 넘기지 않는다. 그래서 개발자가 셸 환경 변수로 token 폴더를 주면 `render`는 `.env`의 폴더를 검사하고, Compose는 셸 환경 변수의 폴더를 붙인다. 이 문제도 이번에 함께 고친다(사람 확인: 2026-11-25).

0027과 [ADR 0018](../decisions/0018-ca-file-path.md)은 고치지 않는다. 이 요구사항은 0027의 CA 인증서 파일 경로 값에 운영 명령이 읽지 않는 표기를 만나면 멈추는 동작만 더한다. 0027이 정한 형식 검사, 파일 검사, 기본값은 그대로다.

사람이 2026-11-25에 범위를 넓히기로 정했다. 위 내용을 구현한 뒤 Linux Docker 호스트에서 확인하고 두 번째 독립 리뷰를 받는 동안 문제 두 개와 고치지 않을 한계 하나가 나왔기 때문이다.

첫째 문제는 이 변경 전부터 있던 동작이다. 모니터링 시스템이 떠 있는 채로 token 폴더 값만 바꾸고 `start`를 실행하면, 운영 명령은 새 폴더의 token을 검사하고 성공으로 끝나지만 Alertmanager는 예전 token 파일을 붙인 채 계속 돈다. `start`는 펼친 설정이나 CA 인증서 파일의 내용이 바뀌었을 때만 컨테이너를 다시 만든다. Compose도 token 파일의 경로가 바뀐 것만으로는 Alertmanager를 다시 만들지 않는다. 2026-11-26에 Docker Compose v5.7.0의 `docker compose config --hash`로 확인했더니, token 폴더 값을 바꿔도 Alertmanager의 해시는 그대로였고 CA 경로 값을 바꾸면 Blackbox Exporter의 해시가 바뀌었다. 운영자는 검사를 통과한 새 token으로 돈다고 믿지만, 예전 token이 관리자 서버의 token과 다르면 관리자 서버가 장애를 모두 거부한다.

둘째 문제는 Windows 개발 환경에만 있다. `monitoring-dev.bat start`의 `render`는 Linux 컨테이너 안에서 검사한 값을 Windows의 Compose에 넘기지 못한다. 그래서 Compose가 `.env`를 스스로 다시 읽는다. 운영 명령과 Compose가 다르게 읽는 표기(변수 치환 등)로 두 경로 값을 적으면, `render`가 검사한 파일과 Compose가 붙이는 파일이 다르다. 운영 서버의 `start`는 검사한 값을 넘겨 이 경우를 맞추지만(S4, S5), 개발용 띄우기는 맞추지 못한다. CA 경로 값은 0027의 형식 검사가 변수 치환, 따옴표, 백슬래시가 든 값을 막는다. 하지만 2026-11-26에 `docker compose config`로 확인했더니, 줄 끝 주석을 다루는 방식의 차이나 다른 변수의 여러 줄 값을 거치는 표기는 형식 검사를 통과하고도 두 쪽이 다르게 읽었다.

고치지 않을 한계는 운영 명령이 읽지 않는 줄을 알아보는 검사(S8, S9)에 있다. 다른 변수의 여러 줄 따옴표 값을 거치는 드문 표기는 운영 명령이 그 줄을 건너뛰지만 Compose는 그 변수로 읽는다. 다른 프로그램의 읽기를 흉내 내는 검사는 고칠수록 비켜 가는 표기가 다시 나오고, 이 표기는 실수로 적기 어렵다. 그래서 이 한계는 받아들이고, 두 문제는 이번에 함께 고친다(사람 확인: 2026-11-25).

## 목표

- `start`로 띄운 Alertmanager가 쓰는 token 파일이 운영 명령이 검사한 파일과 같다. token 폴더를 `.env`에 어떤 표기로 적었든, 셸 환경 변수로 주었든, 적지 않았든 같다.
- `.env`에 token 폴더를 운영 명령이 읽지 않는 표기로 적었으면 `start`, `render`, `install`이 아무것도 바꾸지 않고 멈춘다. 그리고 그 줄을 `MONITORING_SECRETS_DIR=폴더` 형식으로 고치라고 안내한다. 그래서 token이 조용히 바뀌지 않고, 고친 뒤에는 운영자가 직접 실행하는 `docker compose` 명령도 같은 token 파일을 붙인다.
- `.env`에 CA 인증서 파일 경로를 운영 명령이 읽지 않는 표기로 적었으면 `start`와 `render`가 아무것도 바꾸지 않고 멈춘다. 그리고 그 줄을 `MONITORING_CA_FILE=경로` 형식으로 고치라고 안내한다. 이 값을 다루는 운영 명령은 이 둘뿐이다. `install`은 CA 인증서 파일을 다루지 않는다.
- 운영 명령과 Compose가 다른 값으로 읽는 표기로 두 값을 적었으면, `start`로 띄운 컨테이너에 운영 명령이 검사한 값의 파일이 붙거나 운영 명령이 검사에서 멈춘다.
- `monitoring-dev.bat start`에서 셸 환경 변수로 token 폴더를 주면 `render`가 그 폴더를 검사하고 Compose도 그 폴더의 token 파일을 붙인다.
- 모니터링 시스템이 떠 있는 채로 token 폴더 값을 다른 폴더로 바꾸고 `start`하면, 뜬 Alertmanager가 새로 검사한 token 파일을 붙인다. token 폴더가 그대로면 지금처럼 컨테이너를 다시 만들지 않는다.
- `monitoring-dev.bat start`로 띄운 Alertmanager와 Blackbox Exporter가 `render`가 검사한 token 파일과 CA 인증서 파일을 붙이고, 호스트 포트도 `render`가 검사한 값으로 연다. `.env`에 이 값들을 어떤 표기로 적었든 같다(사람 확인: 2026-11-26).
- 다른 OS에서 저장소로 띄우는 운영 가이드의 명령(저장소에서 실행)도 `render`가 검사한 값으로 Compose를 부른다(사람 확인: 2026-11-26).

## 하지 않는 것

- 운영 명령 없이 Compose로 직접 띄우는 경우(운영 가이드의 운영 명령 없이 실행, token 바꾸기의 `docker compose` 명령)에 Compose가 `.env`를 읽는 방식을 바꾸는 것. 이 경우에는 그 전에 실행한 `render`나 `start`의 멈춤이 운영 명령이 읽지 않는 표기를 막는다.
- 운영 명령이 읽지 않는 줄을 알아보는 검사(S8, S9)가 Compose의 `.env` 읽기를 모두 따라가는 것. 다른 변수의 여러 줄 따옴표 값을 거치는 드문 표기는 이 검사가 골라내지 못해 멈추지 않는다. 이때도 `start`와 개발용 띄우기는 운영 명령이 검사한 값을 Compose에 넘기므로 검사한 파일로 뜬다. 다만 운영자가 직접 실행하는 `docker compose`는 다른 파일을 붙일 수 있다. 실수로 적기 어렵고, 다른 프로그램의 읽기를 흉내 내는 검사는 고칠수록 비켜 가는 표기가 다시 나와 받아들인다(사람 확인: 2026-11-25).
- 운영 서버의 token 폴더 값에 허용 글자나 형식 검사를 더하는 것. 지금 적어 둔 값으로 도는 서버가 멈출 수 있고, 이 값은 설정에 펼치지 않는다. 저장소에서 `render`할 때의 제한(S14)은 개발 환경에만 있다.
- token 파일의 내용만 바꾼 경우에 `start`가 Alertmanager를 다시 만드는 것. token은 운영 가이드의 token 바꾸기대로 바꾼다.
- CA 인증서 파일 경로 값의 형식 검사(0027의 S6)와 파일 검사(0027의 S7)를 바꾸는 것
- 숫자 설정 값, 서버 사용량 수집 값, 관리자 서버 주소의 읽기와 검사를 바꾸는 것
- 이 변경 전의 묶음으로 되돌린 경우의 동작. 예전 버전의 운영 명령은 바뀌지 않는다.
- 상태 명령(`status`)에 token 폴더나 CA 인증서 파일 경로를 보이는 것
- token 값을 새로 만들거나 옮기는 것
- `monitoring-dev.bat start`에서 Windows 경로나 절대 경로를 두 경로 값으로 쓰게 하는 것. `render`는 Linux 컨테이너 안에서 돌아 Windows 경로를 볼 수 없고, 절대 경로는 컨테이너 안과 Windows에서 서로 다른 곳을 가리킨다. 그래서 개발용 띄우기에서는 지금처럼 token 폴더에 `infrastructure/` 기준 상대 경로를 쓰고 CA 경로 값은 비워 둔다(운영 가이드의 저장소에서 실행).

## 사용자 경험

모니터링 시스템을 설치하고 운영하는 운영자 관점이다.

1. 운영자가 `.env`에 두 경로 값을 `변수=값` 형식으로 적었거나 적지 않았으면 지금과 같다. 운영 명령이 그 값(적지 않았으면 기본 위치)의 파일을 검사하고 붙인다.
2. 운영 명령이 읽지 않는 표기로 적었으면 그 값을 다루는 운영 명령이 멈추고, 변수 이름과 고칠 형식을 보인다. token 폴더는 `start`, `render`, `install`이, CA 인증서 파일 경로는 `start`, `render`가 멈춘다. 떠 있는 모니터링 시스템은 그대로 돈다.
3. 운영자가 그 줄을 고친 뒤 다시 실행한다. 고친 값의 파일을 쓸 수 있으면 그대로 뜬다.

모니터링 시스템이 떠 있는 채로 token 폴더를 옮기는 운영자는 다음 순서를 겪는다.

1. `.env`의 token 폴더 값을 새 폴더로 고치고 `start`를 실행한다.
2. 운영 명령이 새 폴더의 token을 검사하고, 세 컨테이너를 다시 만들어 띄운다. 다시 만드는 동안 잠깐 감시가 멈춘다. OS의 CA 인증서를 갱신했을 때와 같다.
3. Alertmanager가 새 폴더의 token으로 관리자 서버를 부른다.

개발자는 Windows에서 `monitoring-dev.bat start`를 쓴다. 셸 환경 변수로 token 폴더를 주면 `render`와 Compose가 모두 그 폴더를 쓴다. `.env`의 표기는 운영자와 같은 규칙을 따르고, Compose는 두 경로 값과 호스트 포트를 `.env`에서 스스로 읽지 않고 `render`가 검사한 값을 쓴다. token 폴더 값에 Compose에 그대로 넘길 수 없는 글자가 있으면 `render`가 멈추고 고칠 방법을 보인다. 다른 OS에서 저장소로 띄우는 개발자도 운영 가이드의 명령을 따르면 같다.

## 동작

아래에서 "token 폴더 값"은 `.env`(또는 같은 이름의 셸 환경 변수)의 `MONITORING_SECRETS_DIR`이고, "CA 경로 값"은 `MONITORING_CA_FILE`이다. 운영 명령과 Compose는 다른 설정 값처럼 셸 환경 변수를 `.env`보다 먼저 본다. token 폴더의 상대 경로는 compose 파일이 있는 폴더(묶음 폴더) 기준이다.

### 정상 동작

- **S1. `.env`에 token 폴더를 적음**
  - 상황: `.env`에 `MONITORING_SECRETS_DIR=폴더` 형식으로 token 폴더를 적었고, 그 폴더에 쓸 수 있는 token 파일이 있다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: 운영 명령이 그 폴더의 token 파일을 검사하고, Alertmanager에 그 파일이 붙는다.
- **S2. token 폴더를 적지 않거나 비움**
  - 상황: token 폴더 값이 없거나 비어 있다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: 운영 명령이 설치 폴더의 `secrets/`(저장소에서는 `infrastructure/secrets/`)의 token 파일을 검사하고, Alertmanager에 그 파일이 붙는다.
- **S3. 셸 환경 변수로 token 폴더를 줌**
  - 상황: 셸 환경 변수 `MONITORING_SECRETS_DIR`가 있다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: `.env`의 값과 관계없이 셸 환경 변수의 폴더를 검사하고, Alertmanager에 그 폴더의 token 파일이 붙는다.
- **S4. 운영 명령과 Compose가 token 폴더를 다르게 읽는 표기**
  - 상황: 운영 명령이 token 폴더 값을 읽지만, Compose가 같은 줄을 다른 값으로 읽는 표기로 적었다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: Alertmanager에 운영 명령이 검사한 폴더의 token 파일이 붙는다. Compose가 스스로 읽은 값은 쓰지 않는다. 검사한 폴더에 쓸 수 있는 token이 없으면 S7대로 멈춘다.
- **S5. 운영 명령과 Compose가 CA 경로를 다르게 읽는 표기**
  - 상황: 운영 명령이 CA 경로 값을 읽지만, Compose가 같은 줄을 다른 값으로 읽는 표기로 적었다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: 운영 명령이 읽은 값이 0027의 형식에 맞지 않으면 0027의 S6대로 멈춘다. 형식에 맞으면 Blackbox Exporter에 운영 명령이 검사한 파일이 붙는다. Compose가 스스로 읽은 값은 쓰지 않는다.
- **S6. 개발용 띄우기에서 셸 환경 변수로 token 폴더를 줌**
  - 상황: Windows의 저장소 폴더에서 셸 환경 변수 `MONITORING_SECRETS_DIR`에 저장소의 `infrastructure/` 기준 상대 경로를 주었고, 그 폴더에 쓸 수 있는 token 파일이 있다.
  - 행동: 개발자가 `monitoring-dev.bat start`를 실행한다.
  - 결과: `render`가 셸 환경 변수의 폴더를 검사하고, Compose가 띄운 Alertmanager에 그 폴더의 token 파일이 붙는다. 그 폴더에 쓸 수 있는 token이 없으면 `render`가 멈추고 Compose를 부르지 않는다.
- **S10. 떠 있는 채로 token 폴더를 바꿈**
  - 상황: 모니터링 시스템이 떠 있다. 운영자가 token 폴더 값(`.env`나 셸 환경 변수)을 다른 폴더로 바꿨고, 그 폴더에 쓸 수 있는 token 파일이 있다. 다른 설정 값과 CA 인증서 파일은 그대로다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: 운영 명령이 새 폴더의 token을 검사하고 세 컨테이너를 다시 만든다. 다시 뜬 Alertmanager에 새 폴더의 token 파일이 붙는다. 운영자가 `start` 대신 `render`를 실행한 뒤 `docker compose up -d`로 직접 띄워도 Compose가 세 컨테이너를 다시 만든다.
- **S11. token 폴더가 그대로인 start**
  - 상황: 모니터링 시스템이 떠 있다. token 폴더 값, 다른 설정 값, CA 인증서 파일이 지난번 `start`와 같다. token 폴더 값을 같은 폴더를 가리키는 다른 형태(예: 상대 경로를 절대 경로로)로만 바꾼 경우도 포함한다.
  - 행동: 운영자가 `start`를 실행한다.
  - 결과: 지금처럼 컨테이너를 다시 만들지 않는다.
- **S12. 이 버전으로 갱신한 뒤 첫 start**
  - 상황: 이 변경 전 버전으로 모니터링 시스템이 떠 있다.
  - 행동: 운영자가 이 버전의 묶음으로 [새 버전으로 갱신](../OPERATIONS.md#새-버전으로-갱신)하고 `start`를 실행한다. 개발자는 저장소를 이 버전으로 받고 `monitoring-dev.bat start`를 실행한다.
  - 결과: 운영 서버는 지금처럼 새 버전의 컨테이너로 다시 만들고, 이 변경 때문에 더 멈추지 않는다. 개발용 시스템은 첫 `monitoring-dev.bat start`에서 세 컨테이너를 한 번 다시 만들고, 그 뒤에는 설정이 바뀔 때만 다시 만든다. 직전 버전으로 되돌리면(`rollback`) 그 버전의 운영 명령이 지금처럼 판단한다.
- **S13. 개발용 띄우기에서 운영 명령과 Compose가 다르게 읽는 표기**
  - 상황: Windows의 저장소 폴더에 있는 `.env`에, 운영 명령은 읽지만 Compose가 다른 값으로 읽는 표기로 token 폴더 값이나 CA 경로 값을 적었다.
  - 행동: 개발자가 `monitoring-dev.bat start`를 실행한다.
  - 결과: `render`가 운영 명령이 읽은 값을 검사하고, Compose가 띄운 컨테이너에 그 값의 파일이 붙는다. Compose가 `.env`에서 스스로 읽은 두 경로 값은 쓰지 않는다. 호스트 포트 세 개도 `render`가 검사한 값으로 연다(사람 확인: 2026-11-26). 검사한 파일을 쓸 수 없으면 `render`가 멈추고 Compose를 부르지 않는다.
- **S15. 다른 OS에서 저장소로 띄움**
  - 상황: Linux 같은 다른 OS의 저장소 폴더에서 `infrastructure/.env`에 두 경로 값과 호스트 포트를 적었다. 운영 명령과 Compose가 다르게 읽는 표기로 적은 경우도 포함한다.
  - 행동: 개발자가 운영 가이드의 저장소에서 실행대로 `render`를 실행한 뒤 안내된 `docker compose` 명령으로 띄운다.
  - 결과: S13과 같이 `render`가 검사한 값의 파일이 붙고, 검사한 호스트 포트로 연다. `render`의 안내에도 그 명령이 있다.

### 예외 동작

- **S7. 검사한 폴더의 token을 쓸 수 없음**
  - 상황: 운영 명령이 읽은 token 폴더에 token 파일이 없거나, 그 자리에 폴더가 있거나, 파일이 비었거나, 컨테이너 사용자가 읽을 수 없다. S4의 표기로 적어 Compose가 읽는 위치에만 token이 있는 경우도 포함한다.
  - 행동: 운영자가 `start`나 `render`를 실행한다.
  - 결과: 지금처럼 경우를 구분해 알리고, Compose를 부르지 않고 펼친 설정을 바꾸지 않는다.
- **S8. 운영 명령이 읽지 않는 표기의 token 폴더**
  - 상황: `.env`에 token 폴더 값을 운영 명령이 읽지 않는 표기로 적었다. 기본 위치나 적은 폴더에 token이 있는지와는 관계없다.
  - 행동: 운영자가 `start`, `render`, `install` 가운데 하나를 실행한다.
  - 결과: 펼친 설정, token 파일, `.env`, 컨테이너를 바꾸지 않고 실패로 끝난다. Compose를 부르지 않는다. 안내에는 변수 이름, 그 줄의 번호, 운영 명령이 그 줄을 읽지 못했다는 것, `MONITORING_SECRETS_DIR=폴더` 형식으로 고치라는 방법이 있다. 그 줄이 token 폴더를 적은 줄이 아니면(다른 변수의 값이나 줄 끝 주석에 이름이 든 경우) 그 값이나 주석에서 이름을 빼라는 방법도 있다. 떠 있는 모니터링 시스템은 그대로 돈다.
- **S9. 운영 명령이 읽지 않는 표기의 CA 경로**
  - 상황: `.env`에 CA 경로 값을 운영 명령이 읽지 않는 표기로 적었다. 적은 경로의 파일이나 설치 폴더의 복사본이 있는지와는 관계없다.
  - 행동: 운영자가 `start`나 `render`를 실행한다.
  - 결과: 펼친 설정과 컨테이너를 바꾸지 않고 실패로 끝난다. Compose를 부르지 않는다. 안내에는 변수 이름, 그 줄의 번호, 운영 명령이 그 줄을 읽지 못했다는 것, `MONITORING_CA_FILE=경로` 형식으로 고치라는 방법이 있다. 그 줄이 CA 경로를 적은 줄이 아니면 그 값이나 주석에서 이름을 빼라는 방법도 있다. 떠 있는 모니터링 시스템은 그대로 돈다.
- **S14. 저장소에서 Compose에 넘길 수 없는 글자가 든 token 폴더**
  - 상황: 저장소의 `infrastructure/`에서 `render`를 실행한다(`monitoring-dev.bat start` 포함). 운영 명령이 읽은 token 폴더 값에 작은따옴표, 백슬래시, 줄바꿈 가운데 하나가 있다.
  - 행동: 개발자가 `monitoring-dev.bat start`나 `render`를 실행한다.
  - 결과: 펼친 설정을 바꾸지 않고 실패로 끝나며, Compose를 부르지 않는다. 안내에는 변수 이름과, 그 글자를 빼고 `infrastructure/` 기준 상대 경로로 적으라는 방법이 있다. 묶음의 운영 명령(운영 서버)은 이 글자로 멈추지 않는다.

### 보안

- 접근 권한: 바뀌지 않는다. `.env`는 설치 폴더에 쓸 수 있는 운영자가 고치고, 운영 명령은 운영자 권한으로 실행한다.
- 외부 입력: `.env`와 셸 환경 변수의 token 폴더 값과 CA 경로 값. 운영자가 적지만 복사해 붙인 값이나 셸에 남은 환경 변수처럼 의도하지 않은 값이 들어올 수 있다([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계)의 신뢰 경계). 운영 명령은 지금처럼 `.env`를 셸로 실행하지 않고 읽는다.
- 외부 입력의 전달: 개발용 띄우기에서 `render`가 검사한 값을 Compose에 넘길 때, 값에 든 글자가 다른 설정 값을 만들거나 Compose가 값을 다시 풀게 하지 않는다. 그렇게 넘길 수 없는 값이면 S14대로 멈춘다.
- 민감한 정보: webhook token. 운영 명령은 token 값을 화면, 로그, 설정 파일에 쓰지 않는다. S8의 안내에도 변수 이름과 경로만 보이고 token 값은 보이지 않는다. S10을 위해 남기는 정보에도 token 값이나 token 값에서 만든 값은 없다. 법이 암호화를 요구하는 항목은 아니다. CA 인증서 파일은 공개된 인증서 묶음이다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 두 경로 값을 `변수=값` 형식으로 적었거나, 셸 환경 변수로 주었거나, 적지 않은 서버가 쓰는 파일 위치
- token 파일의 네 가지 검사(없음, 폴더, 빈 파일, 읽을 수 없음)와 그 안내
- CA 경로 값의 형식 검사와 파일 검사, 그 안내(0027의 S6, S7, S8). 다만 셸 환경 변수로 준 CA 경로 값의 끝에 줄바꿈이 있으면, 전에는 운영 명령이 그 줄바꿈을 떼고 받아들였지만 이제는 형식 검사가 그 줄바꿈을 보고 모든 배치에서 멈춘다. 0027의 형식 검사는 줄바꿈을 받지 않도록 정해져 있고, 검사가 Compose가 쓰는 값과 같은 값을 봐야 하기 때문이다(사람 확인: 2026-11-26).
- `install`이 token 폴더와 파일을 만드는 권한, 이미 있는 token과 `.env`를 덮어쓰지 않는 것
- compose 파일의 두 값 기본값(token 폴더는 저장소 `./secrets`, 묶음 `../secrets`, CA 인증서 파일은 저장소 `./certs/ca-certificates.crt`, 묶음 `../certs/ca-certificates.crt`)
- 숫자 설정 값, 서버 사용량 수집 값, 관리자 서버 주소의 읽기와 검사
- `monitoring-dev.bat start`가 render 컨테이너에 넘기는 셸 환경 변수와 CA 인증서 파일 준비, `monitoring-dev.bat stop`
- 설정 값, token 폴더, CA 인증서 파일이 그대로면 `start`가 컨테이너를 다시 만들지 않는 것(S11), 바뀌면 다시 만드는 것
- 모니터링 시스템이 떠 있지 않을 때 `start`가 컨테이너를 새로 만드는 것
