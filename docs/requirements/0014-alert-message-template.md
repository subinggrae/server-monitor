# 0014. 관리자 서버에서 정하는 알림 메시지 틀

- 상태: 초안
- 작성일: 2026-11-09
- 관련: [#9](https://github.com/subinggrae/server-monitor/issues/9), [#24](https://github.com/subinggrae/server-monitor/issues/24), [#5](https://github.com/subinggrae/server-monitor/issues/5), [0009](0009-resource-threshold-schema.md), 요구사항 0012(브랜치 `feature/check-label-continuity`), [관리자 서버 만들기](../ADMIN-SERVER.md), [통합 계약](../INTEGRATION.md)

## 배경

장애 알림의 문장은 코어가 아니라 관리자 서버가 만든다. 코어(Alertmanager)가 webhook으로 보내는 것은 감시 항목 id, 확인하던 주소, 장애·복구 상태, 시각, Alert 규칙의 summary 같은 재료뿐이다. 알림 수단은 관리자 서버마다 구현하고 장애 판단 규칙은 코어가 정하기로 했으므로([#24](https://github.com/subinggrae/server-monitor/issues/24), [#5](https://github.com/subinggrae/server-monitor/issues/5), 2026-10-29), 메시지 문구도 관리자 서버가 정할 수 있다.

하지만 이 저장소의 Manager는 문구를 코드(`AlertMessageFormatter`)에 고정해 두었다. 첫 줄은 `🚨 [CRITICAL] 전자결재 Health`, `✅ [RESOLVED] 전자결재 Health`처럼 영어 대문자 표기를 쓰고, 장애 본문 한 줄은 코어 Alert 규칙의 summary를 그대로 옮긴다. 장애 기록(`alert_events.summary`)에도 코어 summary를 저장한다. 그래서 개발에 참여하지 않은 운영자는 `RESOLVED`, `CRITICAL`이 무엇인지 알아야 메시지를 읽을 수 있고, 문구를 바꾸려면 코드를 고쳐 다시 배포해야 한다.

관리자 서버의 웹과 API는 이 저장소가 아닌 다른 웹에서 만든다(사람 확인: 2026-11-09). 그래서 이 요구사항의 결과물은 코드가 아니라 다른 웹의 개발자가 읽을 문서와, 메시지 틀 테이블의 참고용 DDL(MariaDB, PostgreSQL)이다. 방식은 [요구사항 0009](0009-resource-threshold-schema.md)의 참고용 DDL(`docs/reference-schema/`)을 따른다(사람 확인: 2026-11-09). 다른 웹은 이어 받아야 할 운영 DB가 있고, 테이블과 열 이름을 도입처 용어사전에 맞춰 바꾼다. 그래서 이 저장소의 기준 migration(`V1__baseline.sql`)은 고치지 않는다(사람 확인: 2026-11-09). [동작](#동작)은 다른 웹이 만들 동작의 기준이고, [완료 기준](#완료-기준)은 이 저장소가 제공하는 것만 확인한다.

## 목표

- 관리자가 알림 메시지 틀을 화면에서 정하고, 관리자 서버는 그 틀로 알림을 만든다. 문구를 바꾸려고 코드를 고치거나 다시 배포하지 않는다.
- 틀은 감시 항목 장애, 감시 항목 복구, 리소스 임계값 장애, 리소스 임계값 복구의 네 종류이고 종류마다 하나씩 둔다. 모든 감시 항목이 감시 항목 장애·복구 틀을 함께 쓰고, 리소스 임계값 알림은 같은 테이블에 종류를 나눠 담는다(사람 확인: 2026-11-09).
- 틀에는 정해 둔 재료만 쓸 수 있고, 목록에 없는 재료를 쓴 틀은 저장할 때 거부한다(사람 확인: 2026-11-09).
- 기본 틀은 개발에 참여하지 않은 비개발자 운영자도 바로 이해하는 쉬운 한국어다. `[RESOLVED]`, `[CRITICAL]`, `firing` 같은 영어·기술 표기 대신 [TERMS.md의 화면 글](../TERMS.md#화면-글) 용어(장애, 복구, 감시 항목, 위험, 경고)를 쓴다(사람 확인: 2026-11-09).
- 알림의 감시 항목 이름과 환경은 알림을 보낼 때 관리자 서버가 자기 DB에서 읽은 값이다. 요구사항 0012와 같은 방향이다(사람 확인: 2026-11-09).
- 다른 웹의 개발자는 [관리자 서버 만들기](../ADMIN-SERVER.md)와 참고용 DDL만 보고 틀 저장, 검사, 메시지 만들기를 구현할 수 있다. 메시지 틀은 코어와 주고받는 약속이 아니라 관리자 서버 안의 기능이므로 설명은 관리자 서버 만들기에 두고, [통합 계약](../INTEGRATION.md)에는 리소스 임계값의 알림 발송과 참고용 DDL 목록에서 그 절로 가는 링크만 더한다.
- 참고용 DDL은 MariaDB용과 PostgreSQL용이 있고 같은 논리 schema다. 둘 다 기준 migration으로 만든 빈 DB에 적용된다.

## 하지 않는 것

- 코어(`compose.yml`, Alert 규칙, Alertmanager 설정)를 바꾸는 것. Alert 규칙의 summary와 description은 그대로 두고 Alertmanager 화면에만 남는다(사람 확인: 2026-11-09).
- 이 저장소의 기준 migration(`V1__baseline.sql`)을 고치거나, 메시지 틀 테이블을 이 저장소 Manager의 migration과 Entity에 넣는 것(사람 확인: 2026-11-09).
- 틀 저장·검사 API, 메시지 만들기, 틀을 고치는 화면을 이 저장소에 만드는 것. 다른 웹이 만든다(사람 확인: 2026-11-09).
- 이 저장소 Manager의 지금 알림 문구(`AlertMessageFormatter`의 `[RESOLVED]`, `[CRITICAL]` 등)를 기본 틀에 맞춰 고치는 것. 이 요구사항의 결과물은 문서와 참고용 DDL이고, Manager 코드를 고치면 범위와 검증이 크게 늘어나서 별도 작업으로 넘기고 GitHub 이슈로 남긴다(사람 확인: 2026-11-09).
- 이미 쌓인 장애 기록의 문구를 새 문구로 바꾸는 것. 운영에는 쌓인 기록이 없다(사람 확인: 2026-11-09).
- 감시 항목마다, 받는 곳마다, 환경마다 다른 틀을 두는 것. 틀은 종류마다 하나다(사람 확인: 2026-11-09).
- 알림 수단(문자, Telegram, webhook 등)을 정하는 것. 관리자 서버마다 구현한다([#24](https://github.com/subinggrae/server-monitor/issues/24)).
- 재료에 알림 받을 곳(chat id 등), token 같은 비밀값을 넣는 것

## 사용자 경험

사용자는 세 부류다. 다른 웹의 개발자, 관리자 서버 화면에서 틀을 고치는 관리자, 알림을 받는 운영자다.

1. 다른 웹의 개발자가 관리자 서버 만들기와 참고용 DDL을 보고 자기 DB에 맞는 메시지 틀 테이블을 만들고, 틀 저장·검사와 메시지 만들기를 구현한다.
2. 관리자가 관리자 서버의 설정 화면에서 틀 네 개를 본다. 아무것도 고치지 않았으면 기본 틀이 보인다.
3. 관리자가 틀을 고치면서 그 종류에 쓸 수 있는 재료 목록을 본다.
4. 관리자가 저장한다. 목록에 없는 재료가 있으면 저장되지 않고, 어떤 재료가 문제인지와 쓸 수 있는 재료가 보인다.
5. 운영자는 저장한 뒤 보내는 알림부터 새 문구로 받는다.

## 동작

메시지는 틀의 재료 자리마다 재료 값을 넣어 만든다. 재료와 그 값은 [재료 목록](#재료-목록)에, 고치지 않았을 때 쓰는 문구는 [기본 틀](#기본-틀)에 있다.

### 재료 목록

틀에 쓸 수 있는 재료는 다음과 같다. 사람이 든 재료에 리소스 임계값의 단계를 알리는 `{단계}`를 더했다. 종류마다 값이 있는 재료만 쓸 수 있어서, 메시지에 빈자리가 생기지 않는다(사람 확인: 2026-11-09).

| 재료 | 쓰는 틀 | 넣는 값 | 예 |
|---|---|---|---|
| `{상태}` | 모든 틀 | `장애` 또는 `복구` | `장애` |
| `{감시항목}` | 감시 항목 장애·복구 | 보낼 때 관리자 서버 DB의 감시 항목 이름 | `전자결재 Health` |
| `{환경}` | 모든 틀 | 보낼 때 관리자 서버 DB의 감시 항목이나 서버의 환경 | `운영` |
| `{확인방식}` | 감시 항목 장애·복구 | 감시 항목의 확인 방식 | `HTTPS` |
| `{대상}` | 감시 항목 장애·복구 | 확인하던 주소(webhook의 `instance` label) | `https://example.com/health` |
| `{서버}` | 리소스 장애·복구 | 보낼 때 관리자 서버 DB의 서버 이름 | `웹 서버 1` |
| `{리소스}` | 리소스 장애·복구 | 감시 리소스의 표시 이름 | `디스크 /` |
| `{단계}` | 리소스 장애·복구 | `위험` 또는 `경고` | `위험` |
| `{사용률}` | 리소스 장애·복구 | 판단에 쓴 사용률, 소수 첫째 자리까지 | `91.3%` |
| `{임계값}` | 리소스 장애·복구 | 그 단계의 임계값 | `90%` |
| `{발생시각}` | 모든 틀 | 장애가 발생한 시각 | `2026-11-09 14:03:21` |
| `{복구시각}` | 복구 틀 | 복구된 시각 | `2026-11-09 14:20:05` |

재료 이름과 값은 다음을 따른다.

- 감시 항목의 `{발생시각}`은 webhook의 `startsAt`, `{복구시각}`은 `endsAt`이다. 리소스는 발생 기록의 발생 시각과 복구 시각이다([통합 계약의 판단 규칙](../INTEGRATION.md#판단-규칙)).
- 복구 틀의 `{사용률}`은 복구를 판단한 때의 사용률이다(사람 확인: 2026-11-09).
- 시각은 `2026-11-09 14:03:21`(`yyyy-MM-dd HH:mm:ss`) 형식으로 보인다. 시간대는 관리자 서버에 정한 하나를 쓰고 기본값은 `Asia/Seoul`이며, 메시지에 시간대를 표시하지 않는다. 이 저장소 Manager의 지금 메시지와 같고, 대상이 사내 운영 담당자이기 때문이다(사람 확인: 2026-11-09).

### 기본 틀

관리자가 틀을 고치지 않았으면 다음 기본 틀을 쓴다. 기본 틀은 관리자 서버가 갖고, 메시지 틀 테이블에 그 종류의 행이 없으면 기본 틀을 쓴다. 문구는 다음 예대로 쓰고 이모지를 넣지 않는다. 첫머리의 `[장애]`, `[복구]` 글자만으로 구분되어 알림 미리 보기에서도 읽히기 때문이다(사람 확인: 2026-11-09). 기본 틀은 재료 뒤에 조사를 붙이지 않는다. 값의 받침에 따라 맞는 조사가 달라서, 붙이면 `90%을`처럼 틀린 문장이 나오기 때문이다.

감시 항목 장애 틀은 다음과 같다.

```text
[{상태}] {감시항목}
{대상} 확인에 실패했습니다.

환경: {환경}
확인 방식: {확인방식}
발생 시각: {발생시각}
```

이 틀로 만든 메시지는 다음과 같다.

```text
[장애] 전자결재 Health
https://example.com/health 확인에 실패했습니다.

환경: 운영
확인 방식: HTTPS
발생 시각: 2026-11-09 14:03:21
```

감시 항목 복구 틀은 다음과 같다.

```text
[{상태}] {감시항목}
{대상} 확인이 정상으로 돌아왔습니다.

환경: {환경}
확인 방식: {확인방식}
발생 시각: {발생시각}
복구 시각: {복구시각}
```

리소스 임계값 장애 틀은 다음과 같다.

```text
[{상태}] {서버}의 {리소스} 사용률이 높습니다
단계: {단계}
사용률: {사용률} (임계값 {임계값})

환경: {환경}
발생 시각: {발생시각}
```

이 틀로 만든 메시지는 다음과 같다.

```text
[장애] 웹 서버 1의 디스크 / 사용률이 높습니다
단계: 위험
사용률: 91.3% (임계값 90%)

환경: 운영
발생 시각: 2026-11-09 14:03:21
```

리소스 임계값 복구 틀은 다음과 같다.

```text
[{상태}] {서버}의 {리소스} 사용률이 임계값 이하로 내려왔습니다
단계: {단계}
사용률: {사용률} (임계값 {임계값})

환경: {환경}
발생 시각: {발생시각}
복구 시각: {복구시각}
```

### 정상 동작

- **S1. 기본 틀로 알림**
  - 상황: 관리자가 틀을 한 번도 고치지 않았다.
  - 행동: 감시 항목에 장애가 생겨 관리자 서버가 알림을 보낸다.
  - 결과: 감시 항목 장애의 기본 틀로 만든 메시지가 간다.
- **S2. 틀 바꾸기**
  - 상황: 관리자가 감시 항목 장애 틀을 고쳐 저장했다.
  - 행동: 그 뒤에 장애 알림을 보낸다.
  - 결과: 모든 감시 항목의 장애 알림이 새 틀로 간다. 이미 보낸 알림과 이미 쌓인 장애 기록의 문구는 바뀌지 않는다(사람 확인: 2026-11-09). 저장하기 전에 시작한 장애라도 저장 뒤에 보내는 재알림과 복구 알림은 새 틀을 쓴다.
- **S3. 복구 알림**
  - 상황: 감시 항목의 장애가 이어지고 있다.
  - 행동: 대상 확인이 다시 성공해 복구된다.
  - 결과: 감시 항목 복구 틀로 만든 메시지가 간다. 복구 알림을 받지 않게 정한 받는 곳에는 가지 않는다. 지금 Manager의 알림 연결 설정과 같다.
- **S4. 재알림**
  - 상황: 감시 항목의 장애가 재알림 주기보다 오래 이어진다.
  - 행동: 관리자 서버가 다시 알린다.
  - 결과: 감시 항목 장애 틀로 만든 메시지가 다시 간다. 틀은 장애용과 복구용 하나씩이므로 재알림 틀을 따로 두지 않는다(사람 확인: 2026-11-09).
- **S5. 이름이나 환경을 바꾼 뒤 알림**
  - 상황: 장애가 이어지는 동안 사용자가 감시 항목이나 서버의 이름 또는 환경을 바꿨다.
  - 행동: 관리자 서버가 재알림이나 복구 알림을 보낸다.
  - 결과: `{감시항목}`, `{서버}`, `{환경}`에 보낼 때의 관리자 서버 DB 값이 들어간다. Alert label에 남은 옛 값은 쓰지 않는다(사람 확인: 2026-11-09).
- **S6. 리소스 임계값 알림**
  - 상황: 리소스 사용률이 한 단계의 임계값을 지속 시간 동안 넘었다가, 나중에 임계값 이하로 내려온다.
  - 행동: 관리자 서버가 [요구사항 0009](0009-resource-threshold-schema.md)의 판단 규칙대로 장애, 재알림, 복구를 알린다.
  - 결과: 장애와 재알림은 리소스 장애 틀로, 복구는 리소스 복구 틀로 만든다. 위험과 경고는 같은 틀을 쓰고 `{단계}`로 구분한다.
- **S7. 재료 값에 중괄호가 든 경우**
  - 상황: 감시 항목 이름이 `{환경} 점검`처럼 중괄호를 담고 있다.
  - 행동: 관리자 서버가 그 감시 항목의 알림을 만든다.
  - 결과: 재료 값은 다시 재료로 바꾸지 않고 적힌 그대로 넣는다. 메시지에는 `{환경} 점검`이 그대로 보인다.
- **S8. 새 장애 기록의 문구**
  - 상황: 이 기능을 붙인 뒤 장애가 생긴다.
  - 행동: 관리자 서버가 장애 기록을 남긴다.
  - 결과: 기록에는 코어 summary 대신 관리자 서버가 만든 고정 문구 `{대상} 확인에 실패했습니다`를 저장한다. 예: `https://example.com/health 확인에 실패했습니다`. 감시 항목 이름은 기록에 저장하지 않고, 화면이 기록을 보일 때 관리자 서버 DB의 지금 이름으로 보인다. 요구사항 0012의 장애 목록과 같은 방식이라, 이름을 바꿔도 지난 기록에 지금 이름이 보이고 틀을 바꿔도 기록 문구가 섞이지 않는다(사람 확인: 2026-11-09).

### 예외 동작

- **S9. 목록에 없는 재료**
  - 상황: 관리자가 틀에 `{담당자}`처럼 재료 목록에 없는 이름을 중괄호로 감싸 넣었다.
  - 행동: 저장을 요청한다.
  - 결과: 저장을 거부하고 문제인 재료와 그 틀에 쓸 수 있는 재료를 알린다. 예: `쓸 수 없는 재료가 있습니다: {담당자}. 이 틀에는 {상태}, {감시항목}, {환경}, {확인방식}, {대상}, {발생시각}을 쓸 수 있습니다.` 기존 틀은 바뀌지 않는다(사람 확인: 2026-11-09).
- **S10. 다른 종류의 재료**
  - 상황: 관리자가 감시 항목 장애 틀에 `{사용률}`이나 `{복구시각}`처럼 그 종류에 값이 없는 재료를 넣었다.
  - 행동: 저장을 요청한다.
  - 결과: S9처럼 거부한다(사람 확인: 2026-11-09). 값이 없는 재료를 받아 두면 메시지에 빈자리가 생기기 때문이다.
- **S11. 짝이 맞지 않는 중괄호**
  - 상황: 관리자가 `{감시항목`처럼 닫는 중괄호가 없는 틀을 넣었다.
  - 행동: 저장을 요청한다.
  - 결과: S9처럼 거부한다(사람 확인: 2026-11-09). 재료 자리로 쓰지 않는 중괄호를 글자로 쓰는 방법은 두지 않는다.
- **S12. 비운 틀**
  - 상황: 관리자가 틀을 모두 지웠다.
  - 행동: 저장을 요청한다.
  - 결과: 그 종류의 행을 지우고 기본 틀로 돌아간다. 다음 알림부터 기본 틀로 간다. 그래서 빈 메시지가 가지 않고, 기본 틀로 되돌리는 기능을 따로 만들지 않아도 된다(사람 확인: 2026-11-09).
- **S13. 너무 긴 틀**
  - 상황: 관리자가 1000자를 넘는 틀을 넣었다.
  - 행동: 저장을 요청한다.
  - 결과: 저장을 거부하고 1000자까지 쓸 수 있다고 알린다. 기존 틀은 바뀌지 않는다. 기본 틀은 100자 안팎이라 1000자면 여유가 있다(사람 확인: 2026-11-09).
- **S15. 재료 값이 들어가 길어진 메시지**
  - 상황: 1000자 이하의 틀에 긴 재료 값(긴 주소 등)이 들어가, 만든 메시지가 알림 수단 한 메시지의 한도를 넘는다. 예: Telegram은 4096자다.
  - 행동: 관리자 서버가 알림을 보낸다.
  - 결과: 한도에 맞춰 메시지의 뒤를 자르고 보낸다(사람 확인: 2026-11-09).
- **S14. 지운 감시 항목의 장애**
  - 상황: 장애가 이어지던 감시 항목을 지웠다.
  - 행동: 코어가 그 감시 항목의 복구 Alert를 보낸다.
  - 결과: 지금 [통합 계약](../INTEGRATION.md#alert-post-apiintegrationsalertmanagerwebhook)대로 기록만 남기고 알리지 않는다. 그래서 감시 항목 이름을 찾지 못한 메시지를 만들 일이 없다.

### 보안

- 접근 권한: 관리자 서버가 정한다. 틀을 바꾸면 모든 알림의 문구가 바뀌므로, 다른 설정 API처럼 로그인과 권한 확인을 거친 사람만 바꾸게 한다([관리자 서버 만들기의 화면과 설정 기능](../ADMIN-SERVER.md#화면과-설정-기능)).
- 외부 입력: 관리자가 넣는 틀 문구. 틀에 넣는 재료 값(감시 항목 이름, 환경, 서버 이름, 리소스 표시 이름)도 사용자가 입력한 값이고, `{대상}`은 webhook으로 들어온 값이다. 재료 값은 S7처럼 다시 해석하지 않는다. 메시지는 지금 Manager처럼 서식 없는 글로 보낸다. 값의 밑줄이나 괄호를 알림 수단이 서식으로 읽으면 메시지가 바뀌거나 거부되기 때문이다.
- 민감한 정보: 없음. 재료는 지금 알림에 들어가는 것과 같은 수준(감시 항목 이름, 확인 주소, 서버 이름, 리소스 이름)이고, 받는 곳의 id와 token은 재료에 없다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 코어의 설정, Alert 규칙과 그 summary·description, 코어와 관리자 서버 사이의 계약([통합 계약](../INTEGRATION.md))
- 이 저장소의 기준 migration, Manager Database schema, Entity
- 이 저장소 Manager의 알림 문구, 장애 기록, 화면
- 알림을 보내는 때(장애, 재알림 주기, 복구)와 받는 곳을 고르는 규칙
- 리소스 임계값의 판단 규칙([요구사항 0009](0009-resource-threshold-schema.md))
- 참고용 리소스 임계값 DDL(`resource-thresholds.sql`)
- MariaDB와 PostgreSQL 모두 지원
