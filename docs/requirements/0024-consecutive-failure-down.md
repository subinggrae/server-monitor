# 0024. 연속 3번 실패하면 장애로 판정

- 상태: 승인
- 작성일: 2026-11-18
- 관련: [0001](0001-per-target-scrape-interval.md), [0003](0003-alert-repeat-interval.md), [0012](0012-check-label-continuity.md), [0013](0013-core-env-settings.md), [ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md), [ADR 0009](../decisions/0009-core-config-in-image.md), [ADR 0010](../decisions/0010-alert-labels-by-check-id.md), [ADR 0012](../decisions/0012-core-render-outside-image.md), [INTEGRATION.md](../INTEGRATION.md)

## 배경

감시 항목의 두 Alert 규칙(`MonitoringCheckDown`, `MonitoringCheckProbeFailed`)은 실패가 1분 이어지면 장애로 판정한다(`for: 1m`). 그런데 수집 주기는 대상마다 10~240초다([0001](0001-per-target-scrape-interval.md)). 그래서 주기가 길수록 판정이 느슨해진다. 주기 15초면 실패 5번이 쌓여야 장애지만, 주기가 60초를 넘으면 실패 1번으로 장애가 된다. 이 모니터링 시스템을 여러 프로젝트가 쓰므로 긴 주기 대상도 생긴다.

판정 기준을 주기와 관계없이 "연속 실패 횟수"로 정하면 어느 주기에서도 일시적인 실패 한 번으로 장애가 되지 않는다.

이 변경은 다음 문서의 문장과 부딪친다. 이 요구사항과 계획 단계에서 쓰는 ADR이 아래 문장만 대신한다. 이전 문서는 고치지 않는다.

- [0001](0001-per-target-scrape-interval.md)의 하지 않는 것: "Alert 규칙의 판단 시간(`for: 1m`)을 대상의 주기에 맞춰 바꾸는 것". 대상마다 Alert 규칙을 고치거나 만들지 않는다는 문장은 그대로다.
- [ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md)의 감수할 점: "Alert 규칙의 `for: 1m`은 주기와 관계없이 고정이라, 주기가 길수록 Alert가 늦게 온다". 수집 주기를 `__scrape_interval__`로 전하고 series label로 남기지 않는 결정은 그대로다.
- [0003](0003-alert-repeat-interval.md), [0012](0012-check-label-continuity.md), [0013](0013-core-env-settings.md)의 "`for: 1m`을 바꾸지 않는다"는 문장. 판정 기준을 코어의 Alert 규칙에 두고 서버에서 열지 않는다는 결정은 그대로다.

판정 기준은 모니터링 시스템 이미지에 들어 있으므로([ADR 0009](../decisions/0009-core-config-in-image.md), [ADR 0012](../decisions/0012-core-render-outside-image.md)), 새 기준은 묶음을 다시 만들고 모든 모니터링 서버를 새 버전으로 갱신해야 적용된다.

## 목표

- 감시 항목의 주소가 연속 3번 실패하면 장애로 판정한다. 수집 주기와 관계없이 같다.
- 첫 실패 뒤 1분이 지나기 전에는 장애로 판정하지 않는다. 그래서 첫 실패 확인부터 판정까지 기다리는 시간은 `max(60초, 수집 주기 × 2)`다. 주기 30초 이하는 지금과 같은 1분이다.
- 관리자 서버를 만드는 개발자가 [INTEGRATION.md](../INTEGRATION.md)에서 판정 식과 주기별 판정 시간, webhook이 오기까지의 시간을 숫자로 찾아 등록 화면에 보일 수 있다.
- 관리자 서버가 장애마다 첫 실패 추정 시각을 계산할 수 있게, 판정 기준(연속 실패 횟수, 최소 대기 시간)을 장애에 고정값으로 싣는다.

## 하지 않는 것

- 통합 계약의 기존 부분을 바꾸는 것. HTTP SD 응답(label, `__scrape_interval__`, 주기 범위 10~240초), Alert label(`alertname`, `severity`, `check_id`, `check_target_id`), webhook의 기존 필드는 그대로다. 더하는 것은 장애의 annotation 두 개(`judgment_failures`, `judgment_min_seconds`)뿐이다(사람 확인: 2026-11-18).
- 장애 시작 시각(`startsAt`)을 첫 실패 시각으로 앞당기는 것. Prometheus가 주는 판정 시각을 그대로 쓴다(사람 확인: 2026-11-18). 표준 Prometheus 규칙으로 앞당기려면 주기 값마다 규칙을 두거나 중계 장치를 따로 둬야 한다. 관리자 서버는 `startsAt`과 판정 기준 annotation으로 첫 실패 시각을 추정한다.
- 실패 구간에서 계산한 값(첫 실패 시각, 실패 횟수 등)을 annotation에 넣는 것. 장애가 이어지는 동안 다시 보낼 때마다 값이 달라진다(사람 확인: 2026-11-18).
- 연속 실패 횟수(3번)와 최소 대기 시간(1분)을 대상마다, 관리자 서버 화면에서, 모니터링 서버의 `.env`에서 바꾸는 것. 장애 판정 기준은 코어가 정한다([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계)).
- 값을 바꿨다가 15분 안에 되돌린 직후 실패의 판정 지연(늦어도 수집 주기 한 번과 규칙 평가 한 번)을 더 줄이는 것. 옛 값의 마지막 확인과 새 값의 첫 확인이 5초 안에 붙을 때의 같은 지연, 판정 식 확인이 `for:` 추가를 잡지 못하는 것, 마지막 수집 시각이 ms까지 같은 두 series도 함께 [#68](https://github.com/subinggrae/server-monitor/issues/68)에서 다룬다(사람 확인: 2026-11-19).
- 복구 기준을 바꾸는 것. 장애 중에 확인이 한 번 성공하면 지금처럼 바로 복구한다.
- 지우거나 끈 대상의 복구 시점(마지막 확인 결과가 5분 지나면 복구)을 바꾸는 것
- 주기가 150초를 넘는 대상에서 장애 중에 이름, 환경, 확인 방식, 주소를 바꾸면 장애가 끊길 수 있는 한계([INTEGRATION.md](../INTEGRATION.md)의 SD 응답 규칙)를 고치는 것. 이 변경 뒤에도 같은 한계가 남는지 확인하고 문서에 맞게 적는다.
- 관리자 서버의 화면 문구와 등록 화면의 판정 시간 표시. 관리자 서버는 다른 저장소에서 만든다.
- Alertmanager의 `group_wait`, `group_interval`, `repeat_interval`
- 서버 사용량(OS exporter) 수집. Alert 규칙이 없다.

## 사용자 경험

모니터링 시스템을 설치하는 운영자, 관리자 서버를 만드는 개발자, 알림을 받는 담당자 관점이다.

배포는 다음 순서로 한다(사람 확인: 2026-11-18).

1. 관리자 서버 개발자가 같은 장애인지를 `startsAt`이 아니라 [INTEGRATION.md](../INTEGRATION.md)의 기준(`fingerprint`, 곧 `alertname`, `check_id`, `check_target_id`)으로 판단하게 고쳐 먼저 배포한다. 새 판정에서는 장애가 이어지는 동안 `startsAt`이 바뀌지 않지만, 모니터링 시스템을 다시 띄우거나 갱신하면 지금처럼 새 값이 된다.
2. 운영자가 새 버전의 묶음을 받아 모든 모니터링 서버를 [새 버전으로 갱신](../OPERATIONS.md#새-버전으로-갱신)한다. `.env`와 관리자 서버 설정은 바꾸지 않는다.
3. 관리자 서버 개발자가 [INTEGRATION.md](../INTEGRATION.md)의 판정 식과 주기별 표를 보고, 감시 항목 등록 화면에 "연속 3번 실패하면 장애로 판정하고, 이 주기에서는 약 N초 걸린다"를 보인다. 장애 화면에는 판정 기준 annotation으로 계산한 첫 실패 추정 시각을 추정이라고 밝혀 보인다. 이 화면 문구는 새 판정이 들어간 모니터링 시스템을 배포한 뒤에 바꾼다. 먼저 바꾸면 갱신하지 않은 모니터링 서버의 동작과 화면 설명이 어긋난다.

담당자는 일시적으로 한 번 실패한 대상의 장애 알림을 받지 않는다. 주기가 긴 대상의 장애 알림은 지금보다 늦게 온다(주기 240초면 첫 실패 확인 뒤 8분).

## 동작

아래에서 "확인 결과"는 Prometheus가 한 대상을 한 번 수집해 얻은 값이다. `MonitoringCheckDown`은 주소 확인 결과(`probe_success`)를, `MonitoringCheckProbeFailed`는 확인 결과를 가져왔는지(`up`)를 본다. 두 규칙의 판정 기준은 같다. 첫 실패 시각은 연속 실패 가운데 가장 이른 확인 결과의 시각이다.

판정은 규칙 평가(15초마다) 때 한다. 그래서 기준을 채운 확인 결과가 들어온 뒤 다음 규칙 평가에서 장애가 된다.

판정은 기준보다 이르지 않다. 기준을 채우지 않은 대상을 장애로 보내면 관리자 서버가 헛 알림을 보내기 때문이다. 다만 실패가 시작될 즈음 주기를 바꾸거나 실패 중에 이름, 환경, 확인 방식, 주소를 바꾸면, 드물게 판정이 규칙 평가 몇 번 늦을 수 있다. 시뮬레이션에서 이런 경우의 0.5% 안쪽이 최대 45초 늦었다(사람 확인: 2026-11-18). 값을 바꿨다가 15분 안에 원래 값으로 되돌리고 바로 실패가 이어지면, 판정이 늦어도 수집 주기 한 번과 규칙 평가 한 번(15초) 안에 된다. 시뮬레이션에서 이 경우의 약 8%가 늦었고 가장 늦으면 주기 240초에서 4분이었다. 헛 장애를 막으려고 되돌린 값의 옛 확인 결과를 따로 세지 않기 때문이다(사람 확인: 2026-11-18, 더 줄이는 일은 [#68](https://github.com/subinggrae/server-monitor/issues/68)). 성공 중에 값을 바꾼 직후 실패할 때도, 옛 값의 마지막 확인 뒤 5초 안에 값을 바꾸고 새 값의 첫 확인도 그 5초 안에 오면 같은 만큼 늦을 수 있다. 판정 식이 확인 결과의 수집 시각을 5초 단위로 보기 때문이다.

장애의 `description`은 다음 문장으로 바꾼다. 주기 30초 이하에서는 판정 때 이미 3번 넘게 실패했으므로 "3번 이상"이라고 쓴다(사람 확인: 2026-11-18).

- `MonitoringCheckDown`: "주소 확인이 3번 이상 연속으로 실패했습니다. 대상 서버와 네트워크 상태를 확인해 주세요."
- `MonitoringCheckProbeFailed`: "확인 결과를 3번 이상 연속으로 가져오지 못했습니다. Blackbox Exporter 상태를 확인해 주세요."

두 규칙의 장애에는 판정 기준을 고정값 annotation으로 싣는다. 값은 규칙마다 상수이고 대상이나 장애 진행에 따라 바뀌지 않는다. 관리자 서버는 자기가 아는 수집 주기로 `대기 시간 = max(judgment_min_seconds, (judgment_failures − 1) × 주기)`, `첫 실패 추정 시각 = startsAt − 대기 시간`을 계산한다. 판정은 15초마다 하므로 실제 첫 실패는 이 추정보다 최대 15초 이르다.

- `judgment_failures`: `"3"`
- `judgment_min_seconds`: `"60"`

### 정상 동작

- **S1. 짧은 주기**
  - 상황: 주기가 30초 이하인 대상(예: 15초)이 실패하기 시작한다.
  - 행동: 실패가 이어진다.
  - 결과: 첫 실패 시각에서 1분이 지난 뒤 첫 규칙 평가에서 장애가 된다. 그때는 이미 3번 넘게 실패했다. 주기 15초면 지금과 같은 시각이다.
- **S2. 긴 주기**
  - 상황: 주기가 30초보다 긴 대상(예: 60초, 240초)이 실패하기 시작한다.
  - 행동: 실패가 이어진다.
  - 결과: 3번째 실패 확인 결과(첫 실패 시각에서 주기 × 2 뒤)가 들어온 뒤 첫 규칙 평가에서 장애가 된다. 그 전에는 장애가 아니다.
- **S3. 중간에 성공**
  - 상황: 대상이 실패, 실패, 성공, 실패 순서로 확인된다.
  - 행동: 규칙을 평가한다.
  - 결과: 성공 뒤부터 다시 센다. 성공 앞의 실패는 세지 않는다.
- **S4. 복구**
  - 상황: 장애 중인 대상의 확인이 한 번 성공한다.
  - 행동: 규칙을 평가한다.
  - 결과: 성공한 확인 결과가 들어온 뒤 첫 규칙 평가에서 복구된다. 지금과 같다.
- **S5. 실패 중에 주기를 바꿈**
  - 상황: 대상이 실패하는 동안 사용자가 수집 주기를 바꾼다.
  - 행동: 실패가 이어진다.
  - 결과: 바꾸기 전의 실패도 이어서 센다. 3번째 실패와 첫 실패 뒤 1분, 두 조건을 모두 채운 뒤 첫 규칙 평가에서 장애가 된다. 이미 장애면 이어진다. 실패가 시작될 즈음 바꾸면 드물게 규칙 평가 몇 번 늦을 수 있다.
- **S6. 실패 중에 이름, 환경, 확인 방식, 주소를 바꿈**
  - 상황: 대상이 실패하는 동안 사용자가 이 값들을 바꿔 원래 series가 끝나고 새 series가 시작한다. id는 그대로다.
  - 행동: 실패가 이어진다.
  - 결과: 옛 series와 새 series의 확인 결과를 한 대상의 것으로 이어서 센다. 이미 장애면 장애가 끊기지 않는다. 지금과 같다. 장애가 되기 전에 바꿨으면 드물게 규칙 평가 몇 번 늦을 수 있다. 새 값의 확인이 성공하면 S4처럼 바로 복구된다. 값을 바꿨다가 15분 안에 되돌려도, 그 사이 다른 값의 성공 뒤부터 다시 센다. 이때는 판정이 기준보다 이르지 않고, 늦어도 수집 주기 한 번과 규칙 평가 한 번 안에 된다.
- **S11. 성공 중에 값을 바꿨는데 새 값이 실패함**
  - 상황: 대상의 확인이 성공하는 동안 사용자가 이름, 환경, 확인 방식, 주소를 바꾸고, 새 값의 확인이 바로 실패한다.
  - 행동: 실패가 이어진다.
  - 결과: 새 값의 첫 실패부터 세어 S1, S2의 시각에 장애가 된다. 옛 series의 마지막 성공이 새 series의 첫 실패와 몇 초 차이로 붙어 있거나, 옛 series에 stale 표시가 늦게 쓰여도 같다.
- **S7. 장애가 아닌 대상**
  - 상황: 대상의 확인이 계속 성공한다.
  - 행동: 규칙을 평가한다.
  - 결과: 장애가 없다.
- **S10. 장애 시작 시각**
  - 상황: 대상이 S1이나 S2의 기준을 채워 장애가 된다.
  - 행동: 장애가 이어지는 동안 Alertmanager가 webhook을 처음 보내고 5분마다 다시 보낸다.
  - 결과: `startsAt`은 장애로 판정한 규칙 평가 시각이고, 다시 보낼 때도 같다. 첫 실패 시각보다 대기 시간만큼 늦다. 주기 15초면 판정 시각은 지금과 같지만 `startsAt`은 지금보다 1분 늦다. 지금은 1분을 기다리기 시작한 시각이 `startsAt`이기 때문이다.

### 예외 동작

- **S8. 지우거나 끈 대상**
  - 상황: 대상의 확인 결과가 더 들어오지 않는다(감시 항목이나 주소를 지우거나 끔, Blackbox Exporter 멈춤).
  - 행동: 규칙을 평가한다.
  - 결과: 장애 중이었으면 마지막 확인 결과가 5분 지난 뒤 복구되고, 그 전에는 끊기지 않는다. 지금과 같다. 아직 장애가 아니었으면, 끊기기 전에 연속 3번 실패한 대상만 첫 실패 뒤 1분이 지날 때(마지막 결과가 5분 안일 때) 장애가 된다. 연속 3번 실패한 것은 사실이라 장애로 본다. 지금 규칙도 같다(사람 확인: 2026-11-18). 그보다 적게 실패하고 끊긴 대상은 장애가 되지 않는다.
- **S9. 확인 결과가 한동안 비었다가 다시 들어옴**
  - 상황: Prometheus를 다시 띄우는 등의 이유로 확인 결과가 몇 분 비었다가 다시 들어온다.
  - 행동: 규칙을 평가한다.
  - 결과: 비기 전과 뒤의 확인 결과 사이에 성공이 없으면 연속 실패로 이어서 센다. 이어 세는 확인 결과는 최근 15분 안의 것뿐이다. 15분은 주기 240초에서 3번 실패를 세는 데 필요한 시간(최대 12분)보다 길게 잡은 값이다. 장애 중이던 대상은 마지막 확인 결과가 5분 안에 있는 동안 장애가 이어진다(S8과 같은 기준).

### 보안

- 접근 권한: 바뀌지 않는다.
- 외부 입력: 바뀌지 않는다. Alert 규칙은 Prometheus가 수집한 확인 결과만 읽는다.
- 민감한 정보: 없음
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- Alert 규칙 이름, Alert label 네 개, `summary` annotation, webhook의 기존 필드
- 한 감시 항목의 여러 주소 Alert가 한 webhook 요청으로 묶여 오는 것, 이어지는 장애를 5분마다 다시 보내는 것
- HTTP SD 응답과 수집 주기 범위(10~240초), `__scrape_interval__`을 series label로 남기지 않는 것
- 수집한 time series의 이름과 label. 주기를 바꿔도 series가 끊기지 않는다.
- 지우거나 끈 대상의 복구 시점(S8), 살아난 대상이 바로 복구되는 것(S4)

## 완료 기준

규칙 테스트는 `infrastructure/prometheus/tests/monitoring-checks.test.yml`(`promtool test rules`)이고, 두 규칙을 모두 확인한다.

- [ ] C1. 주기 10초와 15초인 대상은 첫 실패 시각에서 1분이 지난 뒤 첫 규칙 평가에서 firing이고, 그 전 평가에서는 firing이 아니다. (S1) — 확인: 규칙 테스트
- [ ] C2. 주기 60초와 240초인 대상은 3번째 실패 확인 결과 뒤 첫 규칙 평가에서 firing이고, 2번째 실패 뒤에는 firing이 아니다. (S2) — 확인: 규칙 테스트
- [ ] C3. 실패, 실패, 성공, 실패 순서면 firing이 아니고, 성공 뒤 실패가 기준을 채우면 firing이다. (S3) — 확인: 규칙 테스트
- [ ] C4. 장애 중 성공 확인 결과가 들어오면 다음 규칙 평가에서 Alert가 없다. (S4) — 확인: 규칙 테스트
- [ ] C5. 실패가 시작될 즈음 주기를 바꾸면(15초로 실패 2번 뒤 120초) 바꾸기 전의 실패를 이어서 세어 S5의 시각에 firing이다. (S5) — 확인: 규칙 테스트
- [ ] C6. 기존 규칙 테스트의 값 변경 시나리오(stale 표시 있음·없음, 수집 틈, stale 표시가 늦게 쓰임)가 새 판정 시각에 맞춰 통과하고, 장애 중 값을 바꿔도 Alert가 이어진다. 실패 중 값을 바꿔 새 series가 성공하면 바로 복구된다. 옛 series가 성공하고 실패한 뒤 새 series가 실패하는 경우(8, 26, 44초 성공, 62초 실패, 새 series 91, 193초 실패)에 195초에 firing이다. (S6) — 확인: 규칙 테스트

- [ ] C7. 계속 성공하는 대상에 Alert가 없다. (S7) — 확인: 규칙 테스트
- [ ] C8. 장애 중이던 대상의 확인 결과가 끊기면 마지막 결과 5분 뒤 평가부터 Alert가 없고, 그 전에는 시작 시각이 바뀌지 않는다(주기 11초 7번 실패 뒤 끊김 포함). 실패 2번 뒤 끊긴 대상은 firing이 되지 않고, 실패 3번 뒤 1분 전에 끊긴 대상은 첫 실패 1분 뒤 firing이 되어 마지막 결과 5분 뒤 복구된다. (S8) — 확인: 규칙 테스트
