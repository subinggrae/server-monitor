# 0005. 시각 체계와 화면 전면 재정비

- 상태: 승인
- 작성일: 2026-10-15
- 관련: [0002](0002-e2e-and-screen-check.md), 0004(브랜치 `feature/resource-threshold-alert`), [DESIGN.md](../design/DESIGN.md), [#7](https://github.com/subinggrae/server-monitor/issues/7), [#8](https://github.com/subinggrae/server-monitor/issues/8), [#9](https://github.com/subinggrae/server-monitor/issues/9)

## 배경

지금 화면은 코드로 만든 토큰과 컴포넌트가 있을 뿐, 사람이 시각 체계로 정하고 승인한 적이 없다([DESIGN.md 개요](../design/DESIGN.md#개요)의 스타일, 원하는 인상, 참고 화면이 "아직 정하지 않았다"). 그 결과 다음 문제가 있다.

- 화면 검사에서 `--subtle-foreground` 글자의 대비가 3.18:1로 WCAG 2.2 AA(4.5:1)에 못 미친다. 0002에서 기준선으로 빼 두었다. 다크 모드와 오류 화면은 검사하지 않는다.
- 글꼴로 Pretendard를 지정했지만 불러오지 않아, 대부분의 PC에서 맑은 고딕으로 보인다.
- 사용자가 가장 자주 하는 일은 Telegram 알림을 받고 대시보드에서 지금 문제인 Check를 확인하는 것이다([PRODUCT.md](../PRODUCT.md)). 그런데 대시보드는 다음과 같다.
  - 자동으로 새로고침되지 않고 마지막 확인 시각이 없다.
  - 위험 개수가 정상 개수와 같은 크기와 무게로 보인다.
  - 위험한 Check 표에 머리글과 "언제부터"가 없다.
  - 서버 절은 이미 만든 SNMP 기능이 없다고 안내한다.
- Check 목록에 정렬이 없고 위험한 Check가 먼저 보이지 않는다. Alert 목록에서는 발생 중인 Alert와 해결된 Alert가 시간순으로 섞이고, 상태 표시가 다른 화면과 따로 구현돼 있다.
- 화면 글이 한 번에 이해하기 어렵다. 2026-10-15에 화면과 Backend 오류 문구를 모두 모아 검토한 결과는 다음과 같다.
  - Check, Alert, Resource, Threshold를 영어 그대로 쓴다. "알림"이 장애 이벤트(Alert)와 Telegram 발송을 함께 가리키고, "대상"이 확인하는 주소와 알림을 받는 그룹을 함께 가리킨다.
  - 같은 개념을 화면마다 다르게 부른다. 예: 같은 목록을 "Check", "Monitoring Check", "Check 목록"으로, 같은 값을 "Message Thread ID"와 "Topic"으로, 같은 상태를 `해소`와 `복구`로 부른다.
  - 사실과 다른 안내가 다섯 곳 있다. 예: 대시보드와 서버 화면이 이미 만든 SNMP 수집을 "아직 설정하지 않았다", "사용할 예정"이라고 안내한다.
  - [RULES.md의 화면 글](../design/RULES.md#화면-글)이 금지한 내부 용어(Backend, Prometheus, Alertmanager, Service Discovery, snmp_exporter)와 코드 값(`MEMORY`, `STORAGE`)이 화면에 나온다. 사용자를 탓하는 오류 문구("형식이 올바르지 않습니다")와 같은 오류의 다른 문구도 있다.

조사한 참고 화면은 [DESIGN.md 개요](../design/DESIGN.md#개요)에 둔다. 시각 체계는 사람이 2026-10-15에 미리 보기 페이지로 확인했다.

## 목표

- 사람이 승인한 시각 체계(글자, 색, 간격, 깊이, 모양, 움직임, 배경)를 DESIGN.md와 토큰 파일에 둔다.
- 모든 화면이 그 시각 체계를 따르고, 기준 폭 두 개, 밝은 모드와 다크 모드에서 화면 검사(WCAG 2.2 AA)를 기준선 없이 통과한다.
- Telegram 알림을 받고 연 사람이 대시보드 첫 화면에서 "무엇이, 언제부터 문제인가"를 바로 안다.
- 목록 화면에서 위험한 것이 먼저 보이고, 정렬과 필터 상태가 보이며 주소에 남는다.
- 화면 글이 정한 용어 하나로 통일되고, 처음 보는 사람도 이해할 수 있다.
- 버튼, 표, 대화상자, 입력 칸, 탭은 라이브러리의 기본 모양이 아니라 회사 브랜드를 살린 이 제품의 모양으로 디자인한다(사람 요청: 2026-10-15). 브랜드 색과 로고는 회사 자료를 쓴다. [확인 필요]
- 화면 종류(목록, 상세, 대시보드, 설정, 대화상자 폼)마다 정해 둔 레이아웃 틀이 있고, 모든 화면은 그 틀의 자리에만 컴포넌트를 넣는다. 화면마다 배치를 따로 짜지 않는다(사람 요청: 2026-10-15).

## 하지 않는 것

- 새 기능. 서버 사용률 알림은 0004에서 만든다. 이 작업은 0004가 더하는 화면에도 같은 시각 체계를 적용할 수 있게 컴포넌트와 규칙을 남긴다.
- 좁은 화면(휴대폰, 태블릿)을 위한 배치. 사용 환경이 사무실 데스크톱이다.
- Telegram 메시지의 문구를 바꾸는 것. 장애 목록에 그대로 나오는 Alert 규칙의 summary 문장도 바꾸지 않는다(`infrastructure/` 변경). 화면 용어에 맞추는 일은 [#9](https://github.com/subinggrae/server-monitor/issues/9)로 넘겼다.
- 화면 글이 아닌 버그. 검토 중 찾은 오류 표시 버그 둘은 따로 고친다([#7](https://github.com/subinggrae/server-monitor/issues/7), [#8](https://github.com/subinggrae/server-monitor/issues/8)).
- 차트와 그래프를 그리는 것. 자세한 추세는 지금처럼 Grafana 링크로 본다.
- 화면에서 다크 모드를 고르는 전환 버튼. 지금처럼 운영체제 설정을 따른다(사람 확인: 2026-10-15).
- Check 상세에 최근 결과를 띠로 보이는 것. 새 API가 필요하다. 이번에는 기존 장애 API를 그 Check로 걸러 최근 장애만 보인다.
- 바깥 CDN에서 글꼴을 불러오는 것. 사내망에서 쓸 수 없을 수 있어 글꼴 파일을 화면과 함께 배포한다.

## 사용자 경험

1. Telegram 알림을 받은 사용자가 대시보드를 연다. 맨 위에 위험한 Check 수가 가장 크게 보이고, 0이면 "모든 Check가 정상입니다"가 보인다. 정상, 알 수 없음, 사용 안 함 수는 그 아래 작게 보인다.
2. 위험한 Check 표에는 이름, 환경, 실패한 대상 수, 위험이 시작된 시각과 지속 시간("12분째")이 보이고, 이름을 누르면 Check 상세로 간다.
3. 화면 위쪽에 마지막으로 확인한 시각이 보이고, 대시보드는 장애 목록과 같은 30초마다 저절로 새로고침된다(사람 확인: 2026-10-15).
4. Check 목록은 처음에 위험 → 알 수 없음 → 정상 → 사용 안 함 순서로 보인다. 사용자가 열 머리글을 눌러 정렬을 바꾸고 필터를 고르면, 고른 조건이 표 위에 보이고 주소에 남는다.
5. Alert 목록은 발생 중인 Alert를 위에, 해결된 Alert를 아래에 보이고, 상태로 거를 수 있다.
6. Check 상세에서는 이 Check의 최근 장애를 볼 수 있다(사람 확인: 2026-10-15).
7. 모든 화면은 같은 글꼴, 글자 크기 단계, 상태 표시를 쓴다. 상태는 색과 모양과 문구로 함께 구분하고, 위험만 강조색으로 두드러진다.
8. 같은 종류의 화면은 같은 틀로 보인다. 예를 들어 목록 화면은 모두 제목과 설명, 주요 동작 버튼, 도구 막대(검색·필터), 표, 빈 상태의 자리가 같고, 상세 화면은 모두 제목·상태·주요 동작, 요약 정보, 탭이나 절의 자리가 같다.

## 동작

### 정상 동작

- **S1. 시각 체계 적용**
  - 상황: 사용자가 어느 화면이든 연다.
  - 행동: 화면을 읽는다.
  - 결과: 글자, 색, 간격, 모서리, 그림자가 토큰 파일의 값만 쓴다. Pretendard가 사용자 PC에 없어도 Pretendard로 보인다.
- **S2. 위험 우선 대시보드**
  - 상황: 위험한 Check가 하나 이상 있다.
  - 행동: 사용자가 대시보드를 연다.
  - 결과: 위험한 Check 수, 위험한 Check 표(시작 시각과 지속 시간 포함)가 첫 화면에 보인다.
- **S3. 모두 정상**
  - 상황: 위험한 Check가 없다.
  - 행동: 사용자가 대시보드를 연다.
  - 결과: "모든 Check가 정상입니다"와 마지막 확인 시각이 보인다.
- **S4. 저절로 새로고침**
  - 상황: 대시보드를 열어 둔다.
  - 행동: 30초가 지난다.
  - 결과: 상태와 마지막 확인 시각이 바뀐다. 새로고침하는 동안 표가 비거나 위치가 밀리지 않는다.
- **S5. 목록 정렬과 필터**
  - 상황: Check 목록이나 Alert 목록을 연다.
  - 행동: 정렬이나 필터를 바꾸고 주소를 복사해 새 탭에서 연다.
  - 결과: 같은 정렬과 필터로 보인다.
- **S6. 다크 모드**
  - 상황: 운영체제를 다크 모드로 둔다.
  - 행동: 화면을 연다.
  - 결과: 모든 화면이 다크 토큰으로 보이고 WCAG 2.2 AA 대비를 지킨다.
- **S7. 화면 글**
  - 상황: 사용자가 메뉴, 제목, 버튼, 표 머리글, 안내, 오류를 읽는다.
  - 행동: 화면을 오간다.
  - 결과: 같은 개념은 모든 화면에서 같은 말이고, [PRODUCT.md의 제약](../PRODUCT.md#제약)에 둔 용어 기준과 [TERMS.md의 화면 글](../TERMS.md#화면-글) 표기를 따른다(사람 확인: 2026-10-15). 창만 닫는 버튼은 RULES.md대로 "닫기"로 쓴다. 감시 도구는 감시 단위와 장애 이벤트를 다른 이름으로 나누고(PagerDuty, Better Stack), Alert를 "경고"로 옮기면 Warning과 겹친다(Grafana 한국어판). NN/g는 전문가가 확실히 아는 말만 전문 용어로 두라고 한다.

### 예외 동작

- **S8. 불러오기 실패**
  - 상황: 화면이 쓰는 API가 실패한다.
  - 행동: 사용자가 화면을 연다.
  - 결과: 무엇을 못 불러왔는지와 다시 시도 버튼이 보인다. 대시보드는 마지막으로 불러온 값을 그대로 두고 확인하지 못했다는 표시를 더한다.
- **S9. 아주 긴 값**
  - 상황: Check 이름, 대상 주소, 디스크 이름이 아주 길다.
  - 행동: 목록과 상세를 연다.
  - 결과: 줄임표나 줄바꿈으로 보이고 가로 스크롤이 생기지 않는다. 줄인 값은 가리키면 전체가 보인다.

### 보안

- 접근 권한: 바뀌지 않는다.
- 외부 입력: 주소에 담는 정렬과 필터 값. 정한 값이 아니면 무시하고 기본값을 쓴다.
- 민감한 정보: 없음
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 라우트 주소와 화면이 부르는 API. 새 API가 필요하면 화면용 API에만 더한다.
- 상태를 색만으로 구분하지 않는 것, 삭제 전 확인, 칸별 입력 오류 표시
- 저장한 데이터와 입력 검증 범위
