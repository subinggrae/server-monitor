# 0010. 내부망에 옮겨 실행하는 코어 이미지 묶음

- 상태: 초안
- 작성일: 2026-10-22
- 관련: [0008](0008-embeddable-core.md), [ADR 0007](../decisions/0007-core-app-contract.md), [#15](https://github.com/subinggrae/server-monitor/issues/15)

## 배경

모니터링 코어(Prometheus, Blackbox Exporter, Alertmanager)는 저장소를 받은 서버에서 `docker compose -f infrastructure/compose.yml up -d`로 띄운다. 이 방식은 실행하는 서버에 두 가지가 있어야 한다.

- **저장소의 설정 파일**: Prometheus 설정과 Alert 규칙, Alertmanager 설정, Blackbox 설정을 저장소의 `infrastructure/`에서 컨테이너로 붙여 넣는다(volume 마운트).
- **인터넷**: 처음 띄울 때 공개 이미지를 `quay.io`에서 받는다.

코어를 내부망 서버에서 쓸 수도 있다(사람 확인: 2026-10-22). 내부망 서버는 인터넷에 닿지 않고, 저장소를 받아 두기도 어렵다. 그래서 인터넷이 되는 PC에서 설정을 넣은 코어 이미지를 빌드하고, 빌드한 파일만 옮겨 Docker로 실행하는 방식이 필요하다(사람 확인: 2026-10-22). 코어 자체는 실행 중에 밖으로 나가는 연결이 없고, 감시 대상과 앱에만 닿는다.

코어를 어떤 서버에서 어떻게 실행하는지도 문서 한곳에 없다. 띄우는 명령은 README에, 설정 준비는 DEVELOPMENT.md에, 앱 주소와 token은 INTEGRATION.md에 흩어져 있고, 서버 조건과 멈추거나 갱신하는 방법은 없다.

## 목표

- 인터넷이 되는 PC에서 명령 하나로 설정을 넣은 코어 이미지 세 개를 빌드하고, 파일 하나(이미지 묶음)로 내보낸다. 무결성을 확인할 체크섬도 함께 만든다.
- 내부망 서버는 이미지 묶음, 실행용 compose 파일, 그 서버에서 만드는 앱 주소 설정과 webhook token만으로 코어를 띄운다. 저장소와 인터넷이 필요 없다.
- 앱 주소와 webhook token은 이미지를 다시 빌드하지 않고 서버에서 바꾼다. token은 이미지에 넣지 않는다.
- 이미지에는 버전 태그가 있어, 서버에서 띄운 코어가 어떤 설정으로 빌드한 것인지 알 수 있다.
- 새 버전 이미지로 갱신해도 쌓아 온 확인·수집 기록과 Alert 상태가 이어진다.
- 코어를 실행하는 방법(서버 조건, 띄우기, 확인, 설정 바꾸기, 갱신, 멈추기)이 문서 한곳에 있다.

## 하지 않는 것

- 앱(이 저장소의 Manager API, 화면, DB) 이미지를 묶는 것. 코어를 붙일 다른 웹은 그쪽에서 배포한다. [확인 필요]
- 사내 이미지 저장소(registry)에 올리는 것. 파일로 옮긴다.
- 코어와 앱을 다른 서버에 두는 것([#15](https://github.com/subinggrae/server-monitor/issues/15)). 이번에도 같은 서버의 Docker 네트워크로 붙는다.
- Alert 규칙이나 Blackbox 설정을 서버에서 빌드 없이 바꾸는 것. 이 설정을 바꾸면 이미지를 다시 빌드한다(사람 확인: 2026-10-22).
- 코어의 감시·알림 동작, 통합 계약, Alert 규칙의 내용을 바꾸는 것

## 사용자 경험

사용자는 두 부류다. 이미지를 빌드하는 개발자와 내부망 서버에서 코어를 띄우는 운영자다.

1. 개발자가 인터넷이 되는 PC의 저장소에서 빌드 명령을 실행한다. 이미지 묶음 파일, 체크섬 파일, 실행용 compose 파일과 설정 예시가 한 폴더에 만들어진다.
2. 개발자가 그 폴더를 내부망 서버로 옮긴다.
3. 운영자가 체크섬을 확인하고 이미지 묶음을 Docker에 불러온다.
4. 운영자가 앱 주소 설정과 webhook token 파일을 만들고 코어를 띄운다.
5. 운영자가 세 컨테이너가 정상인지 확인한다. 앱을 붙이면 감시 대상이 보인다.
6. 규칙을 바꿔야 하면 개발자가 새 버전을 빌드해 옮기고, 운영자가 불러온 뒤 다시 띄운다.

## 동작

### 정상 동작

- **S1. 빌드**
  - 상황: 인터넷이 되는 PC에 저장소와 Docker가 있다.
  - 행동: 개발자가 빌드 명령을 실행한다.
  - 결과: 설정을 넣은 코어 이미지 세 개가 버전 태그로 빌드된다. 이미지 묶음 파일 하나, 체크섬 파일, 실행용 compose 파일, 앱 주소 설정 예시가 한 폴더에 만들어진다. 어느 파일에도 비밀값이 없다.
- **S2. 내부망 서버에서 띄우기**
  - 상황: 인터넷에 닿지 않고 저장소도 없는 서버에 Docker가 있다.
  - 행동: 운영자가 S1의 폴더를 옮겨 이미지 묶음을 불러오고, 앱 주소와 token을 넣은 뒤 코어를 띄운다.
  - 결과: 인터넷에서 아무것도 받지 않고 세 컨테이너가 정상 상태가 된다. 앱을 붙이면 지금처럼 감시와 알림이 동작한다.
- **S3. 앱 주소나 token 바꾸기**
  - 상황: 코어가 떠 있다.
  - 행동: 운영자가 서버에서 앱 주소 설정이나 token 파일을 바꾸고 코어를 다시 띄운다.
  - 결과: 이미지를 다시 빌드하지 않고 새 주소와 token으로 동작한다.
- **S4. 새 버전으로 갱신**
  - 상황: 코어가 떠 있고, 개발자가 규칙을 바꿔 새 버전을 빌드했다.
  - 행동: 운영자가 새 이미지 묶음을 불러와 새 버전으로 다시 띄운다.
  - 결과: 바뀐 규칙으로 동작하고, 쌓아 온 기록과 Alert 상태가 이어진다. 이전 버전으로 되돌릴 수도 있다.
- **S5. 띄운 버전 확인**
  - 상황: 코어가 떠 있다.
  - 행동: 운영자가 띄운 코어의 버전을 확인한다.
  - 결과: 이미지 태그로 버전이 보이고, 그 버전을 빌드한 저장소 커밋을 알 수 있다.
- **S6. 저장소에서 개발**
  - 상황: 개발자가 저장소에서 코어를 띄워 개발한다.
  - 행동: 규칙이나 설정을 바꾸고 코어를 다시 띄운다.
  - 결과: 바뀐 설정으로 뜬다. 개발용 코어와 내부망용 코어가 같은 설정 출처에서 만들어진다. [확인 필요]

### 예외 동작

- **S7. 앱 주소나 token이 없음**
  - 상황: 앱 주소 설정이나 token 파일을 만들지 않았다.
  - 행동: 운영자가 코어를 띄운다.
  - 결과: 코어가 뜨지 않고, 무엇이 없는지와 어디에 만들어야 하는지를 알리는 메시지가 보인다.
- **S8. 옮기다 망가진 파일**
  - 상황: 이미지 묶음 파일이 옮기는 중에 잘렸거나 바뀌었다.
  - 행동: 운영자가 체크섬을 확인한다.
  - 결과: 체크섬이 맞지 않는다고 나오고, 운영자는 불러오기 전에 알아챈다.
- **S9. 이미지를 불러오지 않고 띄움**
  - 상황: 이미지 묶음을 불러오지 않았다.
  - 행동: 운영자가 코어를 띄운다.
  - 결과: 인터넷에서 받으려 하지 않고, 이미지가 없다는 오류로 멈춘다.

### 보안

- 접근 권한: 바뀌지 않는다. 코어 포트는 지금처럼 `127.0.0.1`에만 연다.
- 외부 입력: 없음. 옮기는 이미지 묶음은 개발자가 빌드한 파일이고, 체크섬으로 바뀌지 않았는지 확인한다.
- 민감한 정보: webhook token. 이미지, 이미지 묶음, 실행용 compose 파일에 넣지 않고 서버에서 비밀값 파일로 만든다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 코어의 감시·알림 동작, Alert 규칙과 recording rule의 내용, 통합 계약([INTEGRATION.md](../INTEGRATION.md))
- 코어가 쓰는 공개 이미지의 버전(Prometheus v3.14.0, Alertmanager v0.34.1, Blackbox Exporter v0.28.0)
- 네트워크 이름 `monitoring`, 포트와 `127.0.0.1` 바인딩, 기록 보관 15일, 데이터 volume 이름
- 앱 주소를 `MONITORING_APP_ADDRESS` 하나로 받는 것

## 완료 기준

- [ ] C1. 빌드 명령 하나로 이미지 세 개, 이미지 묶음, 체크섬, 실행용 compose 파일, 설정 예시가 만들어지고, 그 파일들에 비밀값이 없다. (S1) — 확인: 빌드 실행, 만들어진 파일 검사
- [ ] C2. 저장소와 인터넷 없이 만들어진 폴더만으로 코어가 정상 상태로 뜨고, 이 저장소의 앱을 붙이면 Check 등록부터 실패 알림까지 동작한다. (S2) — 확인: 로컬 이미지를 지운 Docker에서 묶음을 불러와 네트워크 없이 띄우는 수동 확인, 기존 E2E
- [ ] C3. 앱 주소와 token을 서버에서 바꾸면 다시 빌드하지 않고 반영된다. (S3) — 확인: 수동 확인
- [ ] C4. 새 버전으로 갱신해도 기록과 Alert 상태가 이어지고, 이전 버전으로 되돌릴 수 있다. (S4, S5) — 확인: 수동 확인
- [ ] C5. 앱 주소나 token이 없으면 무엇이 없는지 알리며 뜨지 않고, 이미지가 없으면 인터넷에서 받지 않고 멈추며, 망가진 묶음은 체크섬에서 걸린다. (S7~S9) — 확인: 수동 확인
- [ ] C6. Prometheus 설정 검사와 규칙 테스트가 빌드한 이미지 기준으로 통과한다. (바뀌지 않는 것) — 확인: `promtool check config`, `promtool test rules`
- [ ] C7. 코어 실행 방법(서버 조건, 띄우기, 확인, 설정 바꾸기, 갱신, 멈추기)이 문서 한곳에 있고 문서 검사가 통과한다. — 확인: `node scripts/check-docs.mjs`, 문서 리뷰

## 확인 필요

- 내부망 서버의 CPU 종류를 정해야 한다. (가정: x86-64(amd64)만 빌드한다)
- 감시 대상 서버에 설치할 node_exporter 이미지도 묶음에 넣을지 정해야 한다. 내부망의 감시 대상 서버도 인터넷에서 받을 수 없다. (가정: 코어와 별도의 묶음으로 함께 만든다)
- 이 저장소의 앱(Manager) 이미지도 묶을지 정해야 한다. (가정: 묶지 않는다. 코어를 붙일 다른 웹이 그쪽에서 배포한다)
- 저장소에서 개발할 때도 같은 방식으로 코어 이미지를 빌드해 띄울지 정해야 한다. (가정: 저장소의 `infrastructure/compose.yml`도 같은 빌드 정의로 이미지를 만들어 띄운다. 설정 출처가 하나여야 개발용과 내부망용이 어긋나지 않기 때문이다)
