# 0013. 서버에서 바꾸는 코어 설정 값

- 상태: 초안
- 작성일: 2026-10-29
- 관련: [#33](https://github.com/subinggrae/server-monitor/issues/33), [0011](0011-core-ops-script.md), [ADR 0001](../decisions/0001-alert-repeat-in-manager.md), [ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md), [ADR 0004](../decisions/0004-os-exporter-collection.md), [ADR 0005](../decisions/0005-common-resource-recording-rules.md), [ADR 0007](../decisions/0007-core-app-contract.md), [ADR 0009](../decisions/0009-core-config-in-image.md), [#5](https://github.com/subinggrae/server-monitor/issues/5), [#22](https://github.com/subinggrae/server-monitor/issues/22)

## 배경

코어 설정과 Alert 규칙은 코어 이미지에 들어 있다([ADR 0009](../decisions/0009-core-config-in-image.md)). 그래서 운영자가 코어 서버의 설정 파일(`.env`)에서 바꿀 수 있는 코어 값은 관리자 서버 주소(`MONITORING_APP_ADDRESS`)와 token 폴더(`CORE_SECRETS_DIR`) 둘뿐이다. 나머지 값은 [운영 가이드의 빌드 전에 저장소에서 고치는 값](../OPERATIONS.md#빌드-전에-저장소에서-고치는-값)에 있고, 바꾸려면 저장소에서 고쳐 다시 빌드한 뒤 모든 코어 서버를 갱신해야 한다. 서버에서 바꿔야 할 값이 생기면 YAML 전체를 열지 않고 그 값만 설정 파일의 변수로 열기로 했다(사람 확인: 2026-10-23, [0011](0011-core-ops-script.md)의 하지 않는 것).

YAML을 열지 않는 이유는 두 가지다. 첫째, 빌드할 때 돌리는 Prometheus·Alertmanager 설정 검사는 문법만 본다. 그래서 `repeat_interval`과 `group_interval`의 관계([ADR 0001](../decisions/0001-alert-repeat-in-manager.md)), `scrape_timeout` 상한([ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md)), keep 규칙과 recording rule([ADR 0004](../decisions/0004-os-exporter-collection.md), [ADR 0005](../decisions/0005-common-resource-recording-rules.md))처럼 관리자 서버와의 약속은 검사를 통과한 채로 깨질 수 있다. 둘째, 서버마다 고친 YAML은 새 버전으로 갱신할 때마다 새 설정과 합쳐야 한다.

후보 값 네 개가 지금 어디에 있는지는 다음과 같다. 2026-10-29에 저장소 코드로 확인했다.

| 후보 | 지금 값이 있는 곳 | 같은 값에 기대는 곳 |
|---|---|---|
| 장애 판단 기준 1분 | `infrastructure/prometheus/rules/monitoring-checks.yml`의 `MonitoringCheckDown`, `MonitoringCheckProbeFailed` 두 규칙의 `for: 1m` | 두 규칙의 `description` 문구 "1분 넘게", [통합 계약의 Alert](../INTEGRATION.md#alert-post-apiintegrationsalertmanagerwebhook)의 도착 시간 설명 |
| 확인 제한 시간 5초 | `infrastructure/blackbox/blackbox.yml`의 `icmp`, `tcp_connect`, `http_2xx` module마다 `timeout: 5s` | `infrastructure/prometheus/prometheus.yml`의 전역 `scrape_timeout: 10s` |
| 기록 보관 15일 | `infrastructure/prometheus/Dockerfile`의 실행 인자 `--storage.tsdb.retention.time=15d` | 운영 가이드의 디스크 안내, 요구사항 0010·0011의 바뀌지 않는 것 |
| 코어 포트 9090, 9093, 9115 | `infrastructure/compose.yml`의 `ports`(`127.0.0.1:9090:9090` 등) | 아래 문단의 컨테이너 안 포트 |

코어 포트는 두 가지로 나뉜다. 코어 서버의 `127.0.0.1`에 열리는 호스트 쪽 포트는 운영자가 브라우저, SSH 터널, `curl`로 쓴다. 반면 `monitoring` 네트워크 안의 컨테이너 포트는 약속이다. 관리자 서버가 `http://prometheus:9090`을 부르고([ADR 0007](../decisions/0007-core-app-contract.md), [통합 계약](../INTEGRATION.md#코어가-제공할-것)), `prometheus.yml`이 `alertmanager:9093`과 `blackbox-exporter:9115`를 부르며, 세 컨테이너의 healthcheck가 컨테이너 안에서 같은 포트를 부른다.

확인 제한 시간에는 Prometheus 쪽 상한이 있다. Blackbox Exporter는 module의 `timeout`과 Prometheus `scrape_timeout`에서 0.5초(`--timeout-offset` 기본값)를 뺀 값 가운데 짧은 쪽으로 확인한다([Blackbox Exporter README](https://github.com/prometheus/blackbox_exporter/blob/v0.28.0/README.md), [v0.28.0 `main.go`](https://github.com/prometheus/blackbox_exporter/blob/v0.28.0/main.go), 확인일 2026-10-29). `scrape_timeout`은 수집 주기 하한(10초)보다 길 수 없으므로([ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md)), 확인 제한 시간을 9.5초보다 길게 적어도 실제로는 9.5초에서 끊긴다. 이 동작은 문서와 코드를 읽어 확인했고, 이 저장소에서 실행해 확인하지는 않았다.

장애 판단 기준에는 그 뒤에 정한 경계가 있다. 감시 항목의 장애 판단 규칙은 코어의 Alert 규칙에 두고, 바꾸려면 코어를 다시 빌드하기로 했다(사람 확인: 2026-10-29, [ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계), [#5](https://github.com/subinggrae/server-monitor/issues/5)). 그래서 이 값은 서버에서 열지 않는다(사람 확인: 2026-10-29).

## 목표

- 운영자가 코어 서버의 설정 파일에서 정해진 값만 바꾸고 코어를 다시 띄우면, 다시 빌드하지 않고 그 값으로 코어가 돈다. 여는 값은 기록 보관 기간, 기록 보관 용량, 확인 제한 시간, 호스트 쪽 코어 포트 세 개다. 장애 판단 기준은 열지 않는다(사람 확인: 2026-10-29).
- 값마다 허용 범위가 정해져 있고, 코어는 범위를 벗어난 값으로 시작하지 않는다. 운영자는 어느 값이 왜 틀렸고 어떻게 고치는지 안내를 받는다.
- 값을 적지 않으면 지금과 같은 기본값(15일, 용량 제한 없음, 5초, 9090·9093·9115)으로 돈다. 이 기능 전에 만든 설정 파일을 그대로 써도 동작이 바뀌지 않는다.
- 여는 값이 다른 값과의 약속을 깨지 않는다. 허용 범위가 그 약속을 지키도록 정해진다.

## 하지 않는 것

- Alertmanager `group_by`와 SD label을 정하거나 바꾸는 것. [#22](https://github.com/subinggrae/server-monitor/issues/22)가 다룬다.
- `group_wait`, `group_interval`, `repeat_interval`을 여는 것. `repeat_interval`은 `group_interval`보다 짧아야 하고, 관리자 서버의 재알림 주기 하한(5분)이 `group_interval`에 묶여 있다([ADR 0001](../decisions/0001-alert-repeat-in-manager.md)).
- Prometheus의 `scrape_timeout`, `scrape_interval`, `evaluation_interval`, HTTP SD 갱신 주기를 여는 것. `scrape_timeout`은 관리자 서버가 허용하는 수집 주기 하한(10초)보다 길 수 없다([ADR 0002](../decisions/0002-scrape-interval-via-http-sd.md)).
- `manager-os` job의 keep 규칙, `sample_limit`, recording rule을 여는 것. 화면과 알림이 읽는 이름과 계산이 바뀐다([ADR 0004](../decisions/0004-os-exporter-collection.md), [ADR 0005](../decisions/0005-common-resource-recording-rules.md)).
- 컨테이너 안 포트, 컨테이너 이름, 네트워크 이름을 바꾸는 것. 관리자 서버와의 약속이다([운영 가이드의 바꾸지 않는 값](../OPERATIONS.md#바꾸지-않는-값)).
- 코어 포트를 `127.0.0.1` 밖의 주소에 여는 것. Prometheus와 Alertmanager에 인증이 없다([운영 가이드의 포트](../OPERATIONS.md#포트)).
- 확인 방식의 나머지 값(IPv4만, HTTP는 2xx만 성공)을 여는 것
- 감시 항목마다 확인 제한 시간을 다르게 두는 것. Blackbox Exporter는 확인 요청마다 제한 시간을 받지 않는다(`blackbox.yml` 주석).
- 관리자 서버 화면에서 이 값들을 바꾸는 것. 이 값들은 코어 서버마다 정하는 배포 설정이다([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계)).

## 사용자 경험

이 변경의 사용자는 코어 서버의 운영자와, 빌드 PC에서 코어를 빌드하는 개발자다.

운영자가 값을 바꿀 때는 다음 순서를 따른다.

1. 운영자가 지금 쓰는 묶음 폴더의 설정 파일에 바꿀 값을 적는다. 설정 예시 파일에 변수마다 뜻, 단위, 기본값, 허용 범위가 적혀 있다.
2. 운영자가 운영 명령의 띄우기를 실행한다.
3. 운영 명령이 값을 검사한다. 틀린 값이 있으면 무엇이 틀렸는지와 고칠 방법을 보이고 아무것도 바꾸지 않는다. 맞으면 코어를 다시 띄우고, 기본값과 다른 값을 보인다. `[확인 필요]`

새 버전으로 갱신할 때는 [0011](0011-core-ops-script.md)의 갱신 절차대로 이전 폴더의 설정 파일을 가져오므로, 바꿔 둔 값이 이어진다.

개발자는 빌드 PC의 설정 검사를 실행해, 기본값뿐 아니라 허용 범위 양 끝 값으로 펼친 코어 설정도 검사를 통과하는지 본다.

## 동작

각 값의 허용 범위와 다른 값과의 약속은 다음과 같다.

| 값 | 단위 | 기본값 | 허용 범위 | 지켜야 할 약속과 근거 |
|---|---|---|---|---|
| 기록 보관 기간 | 정수 일 | 15 | 1~365 | 화면과 알림이 읽는 최장 범위 10분 이상(ADR 0005) |
| 기록 보관 용량 | 정수 GB `[확인 필요]` | 없음(제한 없음) | 1 이상 `[확인 필요]` | 없음 |
| 확인 제한 시간 | 정수 초 | 5 | 1~9 | `scrape_timeout` 10초 − 0.5초 이하(ADR 0002) |
| Prometheus 호스트 포트 | 포트 번호 | 9090 | 1024~65535 | 다른 두 호스트 포트와 다름 |
| Alertmanager 호스트 포트 | 포트 번호 | 9093 | 1024~65535 | 다른 두 호스트 포트와 다름 |
| Blackbox Exporter 호스트 포트 | 포트 번호 | 9115 | 1024~65535 | 다른 두 호스트 포트와 다름 |

보관 기간 1~365일, 확인 제한 시간 1~9초와 세 확인 방식에 같은 값, 포트 1024~65535는 사람이 정했다(사람 확인: 2026-10-29). 확인 제한 시간의 상한 9초는 배경에 적은 9.5초 안의 가장 큰 정수다. 호스트 포트를 바꿔도 컨테이너 안 포트는 바뀌지 않는다.

보관 기간과 보관 용량은 함께 연다(사람 확인: 2026-10-29). 감시 대상이 많고 보관 기간이 길면 기록이 수십 GB를 넘을 수 있기 때문이다. 두 값을 모두 적으면 먼저 닿는 쪽에 맞춰 오래된 기록부터 지운다.

### 정상 동작

- **S1. 값을 적지 않음**
  - 상황: 설정 파일에 새 값이 없거나 값이 비어 있다. 이 기능 전에 만든 설정 파일도 같다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 코어가 기본값(보관 15일, 보관 용량 제한 없음, 확인 제한 시간 5초, 포트 9090·9093·9115)으로 뜬다. 지금과 동작이 같다.
- **S2. 기록 보관 기간을 늘림**
  - 상황: 코어가 15일로 돌고 있다.
  - 행동: 운영자가 보관 기간을 30일로 적고 띄우기 명령을 실행한다.
  - 결과: 코어가 다시 뜨고 쌓아 온 기록이 이어진다. 그 뒤로는 30일이 지난 기록부터 지운다.
- **S14. 기록 보관 용량을 정함**
  - 상황: 감시 대상이 많아 기록이 디스크를 많이 차지할 수 있다.
  - 행동: 운영자가 보관 용량을 50GB로 적고 띄우기 명령을 실행한다.
  - 결과: 기록이 50GB를 넘으면 보관 기간이 지나지 않았어도 가장 오래된 기록부터 지운다. 보관 기간 제한도 그대로 적용된다.
- **S3. 확인 제한 시간을 바꿈**
  - 상황: 응답이 느린 대상이 있어 5초로는 확인이 실패한다.
  - 행동: 운영자가 확인 제한 시간을 8초로 적고 띄우기 명령을 실행한다.
  - 결과: ping, TCP, 웹 주소의 모든 확인 방식이 8초까지 응답을 기다린다. 감시 항목, SD label, time series는 그대로다.
- **S4. 호스트 쪽 포트를 바꿈**
  - 상황: 코어 서버의 다른 프로그램이 9090을 쓴다.
  - 행동: 운영자가 Prometheus 호스트 포트를 19090으로 적고 띄우기 명령을 실행한다.
  - 결과: 코어 서버의 `127.0.0.1:19090`에서 Prometheus가 열린다. 관리자 서버가 부르는 `http://prometheus:9090`과 코어끼리 부르는 주소는 그대로라 관리자 서버 설정을 바꾸지 않는다.
- **S5. 새 버전으로 갱신**
  - 상황: 이전 버전의 설정 파일에 바꾼 값이 있다.
  - 행동: 운영자가 [0011](0011-core-ops-script.md)의 갱신 절차대로 새 폴더에서 설치 준비와 띄우기를 실행한다.
  - 결과: 새 버전이 이전 설정 파일의 값으로 뜬다.
- **S6. 직접 실행**
  - 상황: 운영자가 운영 명령 없이 묶음 폴더에서 Compose로 코어를 띄운다.
  - 행동: 운영자가 [운영 가이드의 운영 명령 없이 실행](../OPERATIONS.md#운영-명령-없이-실행)대로 띄운다.
  - 결과: 값이 맞으면 S1~S4와 같게 뜬다.
- **S7. 빌드 PC의 설정 검사**
  - 상황: 개발자가 코어 설정이나 규칙을 바꿨다.
  - 행동: 개발자가 빌드 PC의 설정 검사를 실행한다.
  - 결과: 기본값과 허용 범위 양 끝 값으로 각각 펼친 Prometheus·Alertmanager·Blackbox 설정이 검사를 통과하고 결과가 보인다.

### 예외 동작

S8~S10에서 운영 명령은 틀린 값의 이름, 적힌 값, 허용 범위, 고치는 방법을 한국어로 보이고 실패로 끝난다. 이때 컨테이너를 만들거나 바꾸지 않으므로, 떠 있던 코어는 그대로 돈다.

- **S8. 형식이 틀린 값**
  - 상황: 값이 정수가 아니거나 단위가 붙어 있다. 예: `15d`, `5s`, `abc`, `-1`, `7.5`
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 단위 없는 정수를 적으라는 안내가 보이고 띄우지 않는다.
- **S9. 범위를 벗어난 값**
  - 상황: 보관 기간이 0일, 확인 제한 시간이 10초, 포트가 80이다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 허용 범위와 그 이유가 보이고 띄우지 않는다. 확인 제한 시간이면 수집 제한 시간(10초)보다 짧아야 한다는 이유를 보인다.
- **S10. 호스트 포트가 겹침**
  - 상황: 세 호스트 포트 가운데 둘 이상이 같다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 겹친 포트와 그 포트를 쓰는 구성 요소가 보이고 띄우지 않는다.
- **S11. 직접 실행에서 틀린 값**
  - 상황: S8이나 S9의 값으로 운영 명령 없이 Compose로 띄운다.
  - 행동: 운영자가 Compose로 띄운다.
  - 결과: 보관 기간과 확인 제한 시간이 틀리면 그 값을 쓰는 구성 요소가 시작하지 않고, 로그에 S8·S9와 같은 안내를 남긴다. 포트는 Compose가 형식만 검사하므로, 허용 범위는 운영 명령에서만 검사한다.
- **S12. 보관 기간을 줄임**
  - 상황: 코어가 떠 있고, 설정 파일의 보관 기간이 떠 있는 코어의 값보다 짧다. 바꾼 값이 있는 폴더에서 이전 폴더로 되돌릴 때도 같다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 새 기간보다 오래된 기록이 지워져 되돌릴 수 없다는 경고와 함께 확인을 묻는다. 운영자가 확인하면 띄우고, 확인하지 않거나 입력을 받을 수 없으면 아무것도 바꾸지 않는다. `[확인 필요]`
- **S13. 다른 프로그램이 쓰는 포트**
  - 상황: 적은 호스트 포트를 코어 서버의 다른 프로그램이 쓰고 있다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: Docker가 그 컨테이너를 띄우지 못하고, 운영 명령이 정상이 아닌 컨테이너와 로그를 보는 명령을 보인다([0011](0011-core-ops-script.md)의 S11). `[확인 필요]`

### 보안

- 접근 권한: 설정 파일은 묶음 폴더에 쓸 수 있는 코어 서버 운영자만 바꾼다. 코어 포트는 지금처럼 `127.0.0.1`에만 열고, 이 변경으로 연 값으로는 바꿀 수 없다.
- 외부 입력: 설정 파일과 셸 환경 변수의 새 값. 이 값은 코어 설정에 펼쳐지므로 S8대로 단위 없는 정수만 받는다. 그래서 줄바꿈이나 YAML 문법을 넣어 다른 설정을 바꾸는 길이 없다.
- 민감한 정보: 없음. 새 값은 비밀이 아니고, 비밀값은 지금처럼 token 파일로만 받는다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 장애 판단 기준(실패가 1분 이어지면 장애), 장애 메시지 문구, 장애를 다시 보내는 간격(5분)
- Alertmanager의 `group_by`, `group_wait`, `group_interval`, `repeat_interval`과 webhook 설정
- Prometheus의 `scrape_timeout`(10초), `scrape_interval`, `evaluation_interval`, HTTP SD 갱신 주기, keep 규칙, `sample_limit`, recording rule
- SD label, Alert label, time series 이름표
- 컨테이너 이름, 컨테이너 안 포트, 네트워크 이름 `monitoring`, 데이터 volume 이름, `127.0.0.1` 바인딩
- 관리자 서버 주소와 token 폴더를 설정 파일에서 정하는 방식, token을 비밀값 파일로 받는 방식
- 통합 계약([INTEGRATION.md](../INTEGRATION.md))
- 코어 이미지에 서버마다 다른 값이나 비밀값이 들어가지 않는다([ADR 0009](../decisions/0009-core-config-in-image.md)).

## 완료 기준

- [ ] C1. 새 값이 없는 설정 파일과 빈 값만 있는 설정 파일로 띄운 코어가 보관 15일, 보관 용량 제한 없음, 확인 제한 시간 5초, 포트 9090·9093·9115로 돈다. (S1) — 확인: 아직 정하지 않았다. 계획에서 띄운 코어의 실행 인자와 설정을 읽는 시험을 정한다
- [ ] C2. 허용 범위 안의 값을 적고 띄우면 Prometheus 보관 기간과 보관 용량, 세 확인 방식의 제한 시간, 세 호스트 포트가 그 값으로 바뀌고, 컨테이너 안 포트와 관리자 서버가 부르는 주소는 그대로다. (S2~S4, S14) — 확인: 개발용 코어에서 값을 바꿔 띄운 수동 확인과, 느린 대상으로 제한 시간이 적용되는지 보는 확인
- [ ] C3. 갱신하면 이전 설정 파일의 값이 새 버전에 이어지고, 보관 기간을 늘려 띄워도 쌓아 온 기록이 이어진다. (S2, S5) — 확인: 버전이 다른 묶음 두 개로 수동 확인
- [ ] C4. S8~S10의 경우마다 운영 명령이 틀린 값의 이름, 적힌 값, 허용 범위, 고치는 방법을 보이고, 컨테이너를 바꾸지 않고 실패 종료 코드로 끝난다. (S8~S10) — 확인: 경우마다 상황을 만들어 실행하는 운영 명령 자동 시험. 검사를 지운 사본에서 시험이 실패하는지도 본다
- [ ] C5. 운영 명령 없이 Compose로 띄울 때 틀린 보관 기간이나 확인 제한 시간이면 그 구성 요소가 시작하지 않고 로그에 원인이 남는다. (S6, S11) — 확인: 틀린 값으로 직접 띄우는 시험
- [ ] C6. 보관 기간을 줄여 띄우면 확인을 받은 뒤에만 띄우고, 확인하지 않거나 입력을 받을 수 없으면 아무것도 바꾸지 않는다. (S12) — 확인: 운영 명령 자동 시험
- [ ] C7. 빌드 PC의 설정 검사가 기본값과 허용 범위 양 끝 값으로 펼친 설정을 각각 검사하고, 범위 밖 값을 허용 범위에 넣으면 검사가 실패한다. (S7) — 확인: 빌드 PC의 설정 검사 실행
- [ ] C8. 설정 예시 파일에 새 값마다 뜻, 단위, 기본값, 허용 범위가 있고, 운영 가이드의 값 표·운영 작업·문제 해결과 ARCHITECTURE.md의 경계가 새 값에 맞게 바뀌며, 문서 검사가 통과한다. — 확인: `node scripts/check-docs.mjs`, 문서 리뷰
- [ ] C9. 묶음과 코어 이미지에 비밀값이 들어가지 않고, 새 값은 이미지가 아니라 실행할 때 받는다. (바뀌지 않는 것) — 확인: 묶음 만들기의 비밀값 검사, 이미지 설정 리뷰

## 확인 필요

- 기록 보관 용량의 단위와 범위를 정해야 한다. 근거가 되는 약속은 없다. 선택지는 정수 GB, 1 이상(권장: 운영자가 디스크 크기와 바로 비교할 수 있다), MB 단위, 나중에 정한다이다. (가정: 정수 GB, 1 이상)
- 다른 프로그램이 쓰는 포트를 띄우기 전에 확인할지 정해야 한다. 선택지는 미리 확인하지 않고 Docker 오류를 안내(권장: 코어 서버에 포트를 보는 도구가 있다고 보장할 수 없고, 0011의 정상 상태 확인이 이미 알린다), 띄우기 전에 쓰는 포트를 확인, 나중에 정한다이다. (가정: 미리 확인하지 않음)
- 보관 기간이나 보관 용량을 줄여 띄울 때 확인을 받을지 정해야 한다. 줄이면 오래된 기록이 지워져 되돌릴 수 없고, 바꾼 값이 없는 이전 폴더로 되돌릴 때도 생긴다. 선택지는 확인을 받음(권장: [0011](0011-core-ops-script.md)이 이전 버전으로 되돌릴 때 확인을 받는 것과 같은 이유다), 경고만 보이고 계속, 나중에 정한다이다. (가정: 확인을 받는다)
- 띄우기 명령이나 상태 명령이 기본값과 다른 값을 보일지 정해야 한다. 선택지는 띄우기와 상태 명령이 보임(권장: 셸 환경 변수가 설정 파일을 덮을 수 있어, 운영자가 실제로 쓰는 값을 알기 어렵다), 보이지 않음, 나중에 정한다이다. (가정: 띄우기와 상태 명령이 보인다)
