# 0009. 서버 리소스 임계값 알림의 DDL과 판단 계약

- 상태: 승인
- 작성일: 2026-10-19
- 관련: [#23](https://github.com/subinggrae/server-monitor/issues/23), [#24](https://github.com/subinggrae/server-monitor/issues/24), [#5](https://github.com/subinggrae/server-monitor/issues/5), [0003](0003-alert-repeat-interval.md), [0008](0008-embeddable-core.md), [ADR 0001](../decisions/0001-alert-repeat-in-manager.md), [ADR 0005](../decisions/0005-common-resource-recording-rules.md), [ADR 0008](../decisions/0008-resource-threshold-in-app.md)

## 배경

모니터링 코어와 Manager Database를 다른 웹에 붙여 다음 네 기능을 쓰려 한다(사람 확인: 2026-10-19). 기능마다 지금 상태는 다음과 같다.

| 기능 | 지금 상태 |
|---|---|
| 앱 상태를 정한 주기마다 확인하고 끊기면 알림 | 있음: Check, 수집 주기 10~240초, `MonitoringCheckDown` 규칙 |
| CPU·Memory·Storage가 임계값을 넘으면 알림, 임계값·수집 주기·포트 지정 | 수집 주기와 포트는 있음, 임계값과 알림은 없음 |
| 정한 주기마다 다시 알림 | Check에만 있음: 재발송 주기 5~1440분 |
| 알림 방법 | Telegram만 있음 |

남은 것은 리소스 임계값과 리소스 알림의 재발송이다. 사용률은 코어의 공통 recording rule `manager:resource_usage_percent`로 이미 나온다([ADR 0005](../decisions/0005-common-resource-recording-rules.md)). 하지만 Manager Database에는 임계값을 저장할 곳도, 리소스 알림의 재발송 주기와 판단 상태를 저장할 곳도 없다.

임계값은 사용자가 화면에서 바꾸는 값이라 Alert 규칙 파일에 적을 수 없다([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계)). 그래서 앱이 Prometheus에서 사용률을 읽어 임계값과 비교하고 직접 알린다(사람 확인: 2026-10-19). 병합하지 않은 이전 초안(요구사항 0004)은 임계값을 metric으로 내보내 Prometheus 규칙이 비교하게 했다. 하지만 지금 [통합 계약](../INTEGRATION.md)에서는 코어가 앱의 metric을 수집하지 않으므로 그 방식은 코어를 고쳐야 한다. 앱이 판단하면 코어가 바뀌지 않고 지속 시간도 규칙의 단계에 묶이지 않는다. 대신 대기, 발생, 복구 판정과 다시 띄운 뒤 판단을 이어 가는 일을 앱이 맡는다.

판단, 발송, 설정 API, 화면은 다른 웹이 만든다(사람 확인: 2026-10-19). 다른 웹은 DB 구조를 참고만 하고 테이블을 그대로 쓰지 않는다. 이 저장소의 백엔드도 새 테이블을 쓰지 않는다. 그래서 이 저장소는 Manager Database의 migration을 바꾸지 않는다. 대신 참고용 DDL과 판단 규칙을 통합 계약에 둔다. 참고용 DDL은 빈 DB에 적용되는지 테스트로 확인한다(사람 확인: 2026-10-19). [동작](#동작)은 다른 웹이 만들 동작의 기준이고, [완료 기준](#완료-기준)은 이 저장소가 제공하는 것만 확인한다.

## 목표

- 참고용 DDL에 감시 Resource마다 Warning·Critical 임계값과 지속 시간을 저장할 곳이 있다. 지속 시간은 사용률이 임계값을 넘은 상태가 얼마나 이어져야 알림을 보낼지를 말한다.
- 참고용 DDL에 서버마다 리소스 알림의 재발송 주기를 저장할 곳이 있다(사람 확인: 2026-10-19).
- 참고용 DDL에 Resource의 단계(Warning, Critical)마다 판단 상태와 발생·복구 기록을 남길 곳이 있다. 판단 상태는 임계값을 넘기 시작한 시각, 발생 여부, 마지막으로 알림을 보낸 시각이다. 그래서 앱을 다시 띄워도 판단이 이어진다.
- 통합 계약에 앱이 임계값을 판단하는 규칙이 있다. 다른 웹의 개발자는 이 문서와 참고용 DDL만 보고 판단과 재발송을 만들 수 있다.
- 참고용 DDL은 MariaDB용과 PostgreSQL용이 있고 같은 논리 schema다. 둘 다 기준 migration(`V1__baseline.sql`)으로 만든 빈 DB에 적용된다.

## 하지 않는 것

- 코어(Prometheus, Alertmanager, Blackbox Exporter)의 설정과 규칙을 바꾸는 것. 리소스 임계값은 Prometheus Alert 규칙으로 판단하지 않는다(사람 확인: 2026-10-19).
- 참고용 DDL을 이 앱의 Manager Database migration에 넣는 것과 그 Entity를 만드는 것. 이 앱도 다른 웹도 새 테이블을 그대로 쓰지 않는다(사람 확인: 2026-10-19).
- 판단, 발송, 설정 API, 화면을 이 저장소에 만드는 것. 다른 웹이 만든다(사람 확인: 2026-10-19). 이 저장소 화면의 안내(임계값 기능이 아직 없다는 문구, 설정 화면의 기본 임계값 자리)도 그대로 둔다.
- 알림 방법과 받는 곳을 정하는 것. 문자, Telegram, webhook 가운데 무엇으로 보낼지는 다른 웹의 백엔드를 구현할 때 정한다(사람 확인: 2026-10-19, [#24](https://github.com/subinggrae/server-monitor/issues/24)). 그래서 리소스 알림을 누구에게 보낼지 정하는 테이블도 이번에 만들지 않는다.
- Resource 종류별 기본 임계값. 사용자가 임계값을 정한 Resource만 판단한다(요구사항 0004에서 사람 확인: 2026-10-15).
- 사용률이 아닌 값(남은 용량, Load average 등)에 임계값을 두는 것과 복구 기준을 임계값과 다르게 두는 것
- Check 알림의 지속 시간([#5](https://github.com/subinggrae/server-monitor/issues/5)), 재발송 주기, 알림 흐름을 바꾸는 것
- OS exporter 수집 실패 자체를 알리는 것. 서버가 살아 있는지는 Check가 판단한다([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계)).

## 사용자 경험

사용자는 두 부류다. 다른 웹의 개발자와 다른 웹 화면을 쓰는 사람이다.

1. 다른 웹의 개발자가 참고용 DDL을 보고 자기 DB에 맞는 테이블을 만든다.
2. 개발자가 통합 계약의 판단 규칙을 보고 판단과 재발송을 만든다.
3. 화면을 쓰는 사람이 감시 Resource마다 Warning·Critical 임계값과 지속 시간을, 서버마다 재발송 주기를 정한다.
4. 사용률이 임계값을 지속 시간 동안 넘으면 알림을 받는다. 그 상태가 이어지면 서버의 재발송 주기마다 다시 받고, 사용률이 내려가면 복구 알림을 받는다.

## 동작

판단은 감시 Resource의 단계마다 따로 한다. 사용률은 `manager:resource_usage_percent{server_id, resource_type, resource_key}`에서 읽는다.

### 정상 동작

- **S1. 임계값 정하기**
  - 상황: 서버에 감시 Resource가 있다.
  - 행동: 사용자가 Warning, Critical 임계값과 지속 시간을 정해 저장한다.
  - 결과: 값이 Manager Database에 남는다. 임계값은 1~100의 정수 %이고, Warning은 Critical보다 작다. 한 단계를 비우면 그 단계는 판단하지 않는다. 지속 시간은 1~60분의 정수이고 처음 값은 5분이다(사람 확인: 2026-10-19).
- **S2. 임계값이 없는 Resource**
  - 상황: 임계값을 정하지 않은 Resource가 있다.
  - 행동: 사용률이 얼마든 시간이 지난다.
  - 결과: 판단하지 않고 알림도 보내지 않는다.
- **S3. 임계값을 넘음**
  - 상황: Resource의 사용률이 한 단계의 임계값보다 크다.
  - 행동: 그 상태가 지속 시간 동안 이어진다. 앱은 서버의 수집 주기마다 판단한다. 수집 주기보다 자주 판단해도 새 값이 없기 때문이다(사람 확인: 2026-10-19).
  - 결과: 그 단계의 알림이 발생하고 알림을 보낸다. 발생과 보낸 시각이 기록에 남는다. Critical이 발생 중인 동안 같은 Resource의 Warning 알림은 보내지 않는다.
- **S4. 짧게 넘었다가 내려감**
  - 상황: 사용률이 임계값을 넘었다.
  - 행동: 지속 시간이 지나기 전에 임계값 이하로 내려간다.
  - 결과: 알림을 보내지 않고, 넘기 시작한 시각을 지운다.
- **S5. 복구**
  - 상황: 한 단계의 알림이 발생 중이다.
  - 행동: 사용률이 그 단계의 임계값 이하로 내려간다.
  - 결과: 그 단계가 복구되고 복구 알림을 보낸다. 복구 시각이 기록에 남는다.
- **S6. 이어지는 알림**
  - 상황: 한 단계의 알림이 발생 중인 채로 이어진다.
  - 행동: 시간이 지난다.
  - 결과: 마지막으로 알림을 보낸 뒤 서버의 재발송 주기가 지나면 다시 보낸다. 재발송 주기는 Check와 같은 5~1440분이고, 정하지 않은 서버는 60분이다(사람 확인: 2026-10-19).
- **S7. 운영 중에 값을 바꿈**
  - 상황: 한 단계의 알림이 발생 중이다.
  - 행동: 사용자가 그 단계의 임계값을 지금 사용률 이상으로 올린다.
  - 결과: 아무것도 다시 띄우지 않고 다음 판단에서 그 단계가 복구된다. S5처럼 복구 알림을 보낸다.
- **S8. 단계 끄기**
  - 상황: 한 단계의 알림이 발생 중이다.
  - 행동: 사용자가 그 단계의 임계값을 비운다.
  - 결과: 다음 판단을 기다리지 않고 저장할 때 그 단계가 복구로 끝나고 복구 알림을 보낸다. 대기 중이던 단계는 넘기 시작한 시각을 지운다. 이후에는 판단하지 않는다.
- **S9. 앱을 다시 띄움**
  - 상황: 넘기 시작한 단계나 발생 중인 단계가 있다.
  - 행동: 앱이 멈췄다가 다시 뜬다.
  - 결과: 앱은 Manager Database의 판단 상태에서 이어 간다. 넘기 시작한 시각은 처음부터 다시 재지 않는다. 발생 중이던 단계는 새로 알리지 않고, 마지막으로 보낸 시각부터 재발송 주기를 잰다.
- **S10. 기존 설치**
  - 상황: 이 저장소의 앱이 설치되어 있다.
  - 행동: 이 변경을 배포한다.
  - 결과: Manager Database의 schema와 데이터가 바뀌지 않는다. 다른 웹에서는 임계값 기능을 붙이기 전에 등록한 Resource가 모두 임계값이 없는 상태(S2)다.

### 예외 동작

- **S11. 허용하지 않는 값**
  - 상황: 임계값에 1보다 작거나 100보다 큰 값이나 정수가 아닌 값을 넣는다. 또는 Warning을 Critical 이상으로 넣거나, 범위 밖의 지속 시간이나 재발송 주기를 넣는다.
  - 행동: 저장을 요청한다.
  - 결과: 저장을 거부하고 이유와 허용 범위를 알린다. 기존 값은 바뀌지 않는다.
- **S12. 사용률을 읽지 못함**
  - 상황: 수집이나 Prometheus 조회가 실패했거나 값이 숫자가 아니어서(`NaN` 등) Resource의 사용률이 없다.
  - 행동: 판단할 때가 된다.
  - 결과: 그 Resource는 판단하지 않는다. 발생 중이던 단계는 복구로 보지 않고 유지한다. 값이 없어 판단할 수 없는데 복구 알림을 보내면 사람이 잘못 안심하기 때문이다(요구사항 0004에서 사람 확인: 2026-10-15). 넘기 시작했던 단계는 넘기 시작한 시각을 지우고, 다음에 값을 읽으면 처음부터 다시 잰다. Prometheus Alert 규칙의 `for`와 같은 동작이라 운영자가 예측하기 쉽다(사람 확인: 2026-10-19).
- **S13. Resource나 서버를 지움**
  - 상황: 임계값이나 판단 상태가 있는 Resource나 서버가 있다.
  - 행동: 사용자가 그 Resource나 서버를 지운다.
  - 결과: 임계값, 판단 상태, 서버의 재발송 주기가 함께 지워진다. 발생 중이던 단계는 복구 알림으로 끝낸다. 발생·복구 기록은 남는다. 장애를 조사할 때 지운 대상의 기록도 봐야 하기 때문이다.

### 보안

- 접근 권한: 다른 웹이 정한다. 이 저장소의 화면용 API와 두 webhook은 바뀌지 않는다.
- 외부 입력: 다른 웹으로 들어오는 임계값, 지속 시간, 재발송 주기. 앱이 받는 Prometheus 조회 응답
- 민감한 정보: 없음. 알림에 서버 이름과 Resource 이름(디스크 경로 등)이 들어가는데, 지금 Check 알림에 Check 이름과 대상 주소가 들어가는 것과 같은 수준이다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 코어의 설정과 규칙, HTTP SD 두 곳과 Alertmanager webhook의 계약, Prometheus series의 이름과 label
- 이 앱의 Manager Database schema, migration, Entity
- 이 저장소의 백엔드와 화면이 하는 일, Check 알림과 그 재발송
- MariaDB와 PostgreSQL 모두 지원

## 완료 기준

- [ ] C1. 기준 migration을 적용한 빈 MariaDB와 PostgreSQL에 참고용 DDL을 적용하면 S1, S6, S9의 값과 상태를 담는 테이블이 생기고, 두 DB의 논리 schema가 같다. (S1, S6, S9) — 확인: 두 DB에 참고용 DDL을 적용하는 통합 테스트
- [ ] C2. 참고용 DDL로 만든 DB에서 Resource나 서버를 지우면 임계값, 판단 상태, 재발송 주기가 함께 지워지고 발생·복구 기록은 남는다. (S13) — 확인: 같은 통합 테스트
- [ ] C3. 이 앱의 migration과 Entity가 바뀌지 않는다. (S10) — 확인: `git diff main -- backend/src/main/`
- [ ] C4. 통합 계약이 판단 규칙(S2~S9, S12, S13), 읽을 series, 참고용 DDL의 위치를 설명하고, 이 변경에 `infrastructure/`의 diff가 없다. 문서 검사가 통과한다. — 확인: `node scripts/check-docs.mjs`, `git diff main -- infrastructure/`, 문서 리뷰
- [ ] C5. 기존 백엔드와 화면의 테스트가 통과한다. (바뀌지 않는 것) — 확인: 전체 검증
