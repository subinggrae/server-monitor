# 0016. 운영자가 읽는 글의 문체와 문장 통일

- 상태: 승인
- 작성일: 2026-11-11
- 관련: [요구사항 0011](0011-core-ops-script.md), [요구사항 0013](0013-core-env-settings.md)

## 배경

설치 담당자와 운영자가 읽는 글의 문체가 파일마다 다르다. 예를 들어 `core-dev.bat build`를 한 번 실행하면 `core-dev.bat`의 `…받지 못했습니다`와 빌드 스크립트의 `커밋하지 않은 변경이 있다`가 섞여 나온다. [WRITING.md의 문서 밖의 글](../WRITING.md#문서-밖의-글)은 로그를 명사형으로 정했지만 실제로 그렇게 쓰는 곳이 없고, 명령 출력과 설정 파일 주석은 정한 문체가 없다.

문장도 읽기 어렵다. `처음 정하거나 줄이면 넘는 기록이 지워져 되돌릴 수 없으므로, 띄우기 전에 확인을 묻습니다.`처럼 다음 세 가지가 겹쳐 있다.

- 기준이 빠진 압축: 무엇을 처음 정하는지, 무엇을 넘는 기록인지 쓰지 않았다.
- 한 문장에 여러 단계: 이유, 결과, 조치를 한 문장에 이었다.
- 내부 동작 설명: 운영 명령이 무엇과 무엇을 비교하는지처럼 담당자에게 필요 없는 설명이 들어 있다.

사람이 2026-11-11에 이 문제를 지적하고, 담당자에게 직접 말하는 글만 합니다체로 쓰기로 정했다.

## 목표

- 읽는 사람과 글의 종류에 따라 문체 규칙 하나를 정해 WRITING.md에 적는다.
  - 담당자에게 직접 말하는 글은 합니다체로 쓴다. 명령 출력과 사용법, 설정 파일 주석이 여기에 든다. 요청은 `~해 주세요`로 쓴다.
  - 문서와 코드 주석은 평서형(`-다`)으로 쓴다.
- 운영자가 읽는 문장을 쓰는 법을 WRITING.md에 적는다. 상황, 결과, 할 일만 쓰고, 담당자가 몰라도 되는 내부 동작은 뺀다. 기준이나 대상을 생략하지 않는다. `확인을 묻다`처럼 추상 명사에 빈 동사를 붙이지 않는다. 문장을 늘리지 않고 바꾸며, 같은 내용이면 더 짧아야 한다.
- 다음 대상 파일의 운영자가 읽는 글을 이 규칙에 맞춘다.
  - 문서: `docs/OPERATIONS.md`, `docs/ADMIN-SERVER.md`
  - 설정 파일 주석: `infrastructure/.env.example`, `infrastructure/compose.yml`, `infrastructure/node-exporter/compose.yml`, 빌드 스크립트가 묶음용 compose 파일에 넣는 머리 주석
  - 명령 출력과 사용법: `core-dev.bat`, `infrastructure/core-server.sh`, `infrastructure/core-settings.sh`, `scripts/build-core-bundle.mjs`

## 하지 않는 것

- 개발자 문서(`docs/INTEGRATION.md`, `docs/ARCHITECTURE.md`, `docs/DEVELOPMENT.md` 등)와 코드 주석의 문장 다듬기. 이들은 이미 평서형이다.
- 앱(`backend/`, `frontend/`)의 화면 문구와 로그. 지울 예정이다.
- 장애 알림 문구(`infrastructure/prometheus/rules/`의 annotation). 이미 합니다체이고, 규칙 파일은 위험 영역이다.
- 검사 조건, 종료 코드, 계속할지 묻는 조건 같은 명령의 동작 변경

## 사용자 경험

1. 설치 담당자가 빌드 PC에서 `core-dev.bat build`를 실행하면, 출력이 처음부터 끝까지 합니다체다.
2. 코어 서버에서 `.env`를 열면 값마다 무엇인지, 바꾸면 무엇이 달라지는지, 조심할 것이 짧은 합니다체 문장으로 있다.
3. `start`가 실패하면 무엇이 문제인지와 무엇을 하면 되는지가 보인다. 운영 명령 내부에서 무엇을 비교했는지는 보이지 않는다.
4. 운영 가이드의 문제 해결 표에 있는 문구가 실제 출력과 같다.

## 동작

### 정상 동작

- **S1. 설정 파일 읽기**
  - 상황: 담당자가 묶음 폴더의 `.env`를 연다.
  - 행동: 기록 보관 기간 설명을 읽는다.
  - 결과: 예를 들어 `줄이면 오래된 기록이 지워지고, 되살릴 수 없습니다.`처럼 결과와 위험이 한 번에 읽힌다.
- **S2. 명령 실행**
  - 상황: 담당자가 `core-dev.bat build`, `core-dev.bat check`, `sh core-server.sh install`, `render`, `start`, `status`를 실행한다.
  - 행동: 출력을 읽는다.
  - 결과: 안내, 경고, 실패 문구가 모두 합니다체다. 실패는 `실패:`, 경고는 `경고:`로 시작한다.

### 예외 동작

- **S3. 틀린 설정 값**
  - 상황: `.env`에 허용 범위 밖의 값이 있다.
  - 행동: 담당자가 `start`를 실행한다.
  - 결과: 지금처럼 코어를 바꾸지 않고 멈춘다. 문구는 무엇이 틀렸는지와 고칠 방법을 쓴다.

### 보안

- 접근 권한: 없음(바뀌지 않음)
- 외부 입력: 없음(문구만 바뀜)
- 민감한 정보: token 값을 출력하지 않는 지금 동작을 유지한다.
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 운영 명령과 빌드 스크립트의 검사, 종료 코드, 계속할지 묻는 조건, 출력하는 정보의 종류
- `install`이 `.env.example`을 복사하고 `MONITORING_APP_ADDRESS=` 줄만 바꾸는 동작
- 설정 값의 이름, 기본값, 허용 범위
