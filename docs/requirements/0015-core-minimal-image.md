# 0015. 셸 없는 최소 코어 이미지

- 상태: 승인
- 작성일: 2026-11-09
- 관련: [0010](0010-core-image-bundle.md), [0011](0011-core-ops-script.md), [0013](0013-core-env-settings.md)(이 요구사항은 0013을 구현한 [PR #42](https://github.com/subinggrae/server-monitor/pull/42) 위에서 시작함), [ADR 0007](../decisions/0007-core-app-contract.md), [ADR 0009](../decisions/0009-core-config-in-image.md), [ADR 0011](../decisions/0011-core-address-format-check.md), [#44](https://github.com/subinggrae/server-monitor/issues/44)

## 배경

코어 묶음은 회사 밖(다른 회사의 프로젝트)에도 준다([LICENSES.md의 고지](../LICENSES.md#고지)). 그런데 코어 이미지는 공식 이미지(`quay.io/prometheus/*`) 위에 만들어서, 세 프로그램(Prometheus, Alertmanager, Blackbox Exporter) 밖의 파일이 함께 들어간다. 2026-11-09에 이 PC에 있는 공식 이미지를 읽기만 해서 확인한 내용은 다음과 같다.

| 공식 이미지 | 바탕의 BusyBox | 프로그램 밖에 든 것 | 실행 사용자 |
|---|---|---|---|
| Prometheus v3.14.0 | 1.38.0 | `promtool`(117MB), BusyBox, CA 묶음, 시간대 자료 443개 파일 | `nobody`(UID 65534) |
| Alertmanager v0.34.1 | 1.38.0 | `amtool`(30MB), BusyBox, CA 묶음, 시간대 자료 443개 파일 | `nobody`(UID 65534) |
| Blackbox Exporter v0.28.0 | 1.37.0 | BusyBox, CA 묶음, 시간대 자료 900개 파일 | `root`(UID 0) |
| node_exporter v1.12.1 | 1.38.0 | BusyBox, CA 묶음, 시간대 자료 443개 파일 | `nobody`(UID 65534) |

표에 다 적지 못한 내용은 다음과 같다.

- CA 묶음은 `/etc/ssl/certs/ca-certificates.crt`(약 220KB), 시간대 자료는 `/usr/share/zoneinfo`(Prometheus 이미지에서 약 1.9MB)다. 네 이미지 모두 `/bin/getconf`, `/etc`의 사용자 파일(`passwd`, `group`, `shadow`), 이름 풀이 파일(`nsswitch.conf`의 `hosts: files dns`), `services`, UTC로 된 `/etc/localtime`도 바탕에서 받는다.
- 세 프로그램의 실행 파일은 정적 링크다. 실행 파일의 ELF 헤더에 동적 링커(`PT_INTERP`)와 동적 구간(`PT_DYNAMIC`)이 없어서, 셸과 공유 라이브러리가 없는 이미지에서도 실행할 수 있다. 헤더만 읽어 확인했고, 최소 이미지를 만들어 실행해 보지는 않았다.
- Prometheus 이미지 372MB 가운데 `prometheus`가 142MB, `promtool`이 117MB다. 지금 묶음의 `core-images.tar`는 약 167MB다.

지금은 BusyBox(GPL-2.0)의 같은 버전 소스를 묶음의 `sources/`에 싣는다. BusyBox가 없는 이미지로 바꾸는 것보다 작업이 작아서 2026-10-22에 고른 방법이다([LICENSES.md의 고지](../LICENSES.md#고지)). CA 묶음과 시간대 자료의 출처와 라이선스는 아직 확인하지 않았다([#44](https://github.com/subinggrae/server-monitor/issues/44)).

이 방법을 바꾸기로 했다(사람 확인: 2026-11-09). 코어 묶음은 세 프로그램만 내부망에서 인터넷 없이 실행할 수 있게 건네고, 세 프로그램(Apache-2.0) 밖의 라이선스를 더하지 않는다. 그래서 코어 이미지를 셸 없는 최소 이미지로 바꾸고, 이미지에는 세 프로그램의 실행 파일과 이 프로젝트의 설정·규칙만 둔다.

셸과 BusyBox 명령이 없어지면 지금 그것에 기대는 다음 세 곳이 동작하지 않는다. 2026-11-09에 저장소 코드로 확인했다.

- **시작 스크립트**: 컨테이너가 시작할 때 셸 스크립트가 설정 값과 관리자 서버 주소를 검사해 설정 템플릿에 펼치고([0013](0013-core-env-settings.md)의 S6·S11·S16, [ADR 0011](../decisions/0011-core-address-format-check.md)), Alertmanager의 token 파일이 있고 읽을 수 있는지 확인한다([0010](0010-core-image-bundle.md)의 S7). 세 프로그램은 설정 파일 안에서 환경 변수를 펼치지 못하므로, 셸이 없는 이미지 안에서는 펼칠 곳이 없다.
- **컨테이너 정상 확인**: 세 컨테이너의 healthcheck가 BusyBox `wget`으로 준비 확인 주소(`/-/ready`, `/-/healthy`)를 부른다. 운영 명령의 띄우기, token 바꾸기, 상태가 이 결과를 읽는다([0011](0011-core-ops-script.md)의 S2·S7·S11).
- **빌드 PC의 검사**: 빌드한 이미지 안의 `promtool`, `amtool`, BusyBox `sh`로 설정 검사, 규칙 테스트, 시작 스크립트의 거부 확인, 운영 명령 시험을 한다.

CA 묶음과 시간대 자료는 다음처럼 쓰인다.

- **CA 묶음**: Blackbox Exporter의 HTTPS 확인만 쓴다. Prometheus와 Alertmanager는 `monitoring` 네트워크 안에서 `http`로만 부른다([INTEGRATION.md의 경로와 주소 바꾸기](../INTEGRATION.md#경로와-주소-바꾸기)). Go는 Linux에서 `/etc/ssl/certs/ca-certificates.crt`(Debian·Ubuntu), `/etc/pki/tls/certs/ca-bundle.crt`(Fedora·RHEL), `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem`(CentOS·RHEL 7) 등을 차례로 찾는다([Go `crypto/x509`의 `root_linux.go`](https://github.com/golang/go/blob/master/src/crypto/x509/root_linux.go), 확인일 2026-11-09).
- **시간대 자료**: 지금 설정은 쓰지 않는다. `infrastructure/`의 Prometheus·Alertmanager·Blackbox 설정과 규칙에 시간대 항목(`location`, `time_zone` 등)이 없고, `compose.yml`은 `TZ`를 넘기지 않는다(2026-11-09 확인). 지금 이미지의 `/etc/localtime`이 UTC이고, Go 프로그램은 `TZ`가 없고 `/etc/localtime`을 읽지 못하면 UTC를 쓴다([Go `time`의 `zoneinfo_unix.go`](https://github.com/golang/go/blob/master/src/time/zoneinfo_unix.go), 확인일 2026-11-09). 그래서 빼도 로그와 계산의 시각이 지금처럼 UTC다. 이 동작은 코드를 읽어 확인했고 실행해 보지는 않았다.

이 변경은 다음 결정과 부딪친다. 그래서 계획 단계에서 ADR 0012를 써서 아래 부분만 대신한다. 설정 템플릿을 펼치는 곳을 컨테이너 안에서 밖으로 옮기는 것은 compose 파일, 운영 명령, 빌드 스크립트, 문서에 걸치고 되돌리기 어렵기 때문이다.

- [ADR 0009](../decisions/0009-core-config-in-image.md): 공개 이미지를 바탕으로 하고 `render-config.sh`를 이미지에 넣는다는 결정과, `compose.yml`이 설정 파일을 volume으로 붙이지 않는지 보는 확인 방법, 빌드한 이미지로 설정을 검사하는 확인 방법. 설정과 규칙의 출처가 이미지 버전이라는 결정과 서버마다 다른 값을 실행할 때 받는 결정은 유지한다.
- [ADR 0011](../decisions/0011-core-address-format-check.md): 시작 스크립트도 관리자 서버 주소를 검사한다는 결정. 공용 검사 함수 하나로 검사한다는 결정은 유지한다.
- [ADR 0007](../decisions/0007-core-app-contract.md): Prometheus와 Alertmanager가 시작할 때 `render-config.sh`가 펼친다는 문장. 앱 주소를 `MONITORING_APP_ADDRESS` 하나로 받는 결정은 유지한다.
- [0013](0013-core-env-settings.md)의 S6·S11·S16과 C5·C10, [0010](0010-core-image-bundle.md)의 S7, [0011](0011-core-ops-script.md)의 바뀌지 않는 것(Compose를 직접 실행하는 절차도 동작한다). 운영 명령 없이 Compose로 띄우려면 먼저 운영 명령으로 설정을 검사해 펼쳐야 한다(S8, 사람 확인: 2026-11-09).
- [0011](0011-core-ops-script.md)의 S2·S7·S11이 말하는 정상 상태. 컨테이너 healthcheck 대신 운영 명령이 코어 서버에서 준비 확인 주소를 부른 결과로 판단한다(S15, 사람 확인: 2026-11-09).
- [LICENSES.md의 고지](../LICENSES.md#고지)의 2026-10-22 결정(BusyBox를 두고 소스를 싣는다)

## 목표

- 코어 이미지 세 개에는 세 프로그램의 실행 파일과 이 프로젝트의 설정·규칙만 있다. 셸, BusyBox, `promtool`, `amtool`, CA 묶음, 시간대 자료가 없다(사람 확인: 2026-11-09).
- 코어 묶음에 세 프로그램(Apache-2.0) 밖의 라이선스가 없고, BusyBox 소스를 싣지 않는다(사람 확인: 2026-11-09).
- node_exporter 묶음의 이미지도 이번에 함께 최소 이미지로 바꾼다. 이미지에는 node_exporter 실행 파일만 두고, node_exporter 묶음에도 node_exporter(Apache-2.0) 밖의 라이선스가 없다(사람 확인: 2026-11-09). 그래서 묶음 만들기에서 BusyBox 소스를 싣는 일이 모두 없어지고, [#44](https://github.com/subinggrae/server-monitor/issues/44)도 필요 없어진다.
- 코어 서버에서는 지금처럼 인터넷 없이 설치하고 띄운다. 운영 명령의 작업 이름과 순서, 설정 값의 검사와 안내는 바뀌지 않는다.
- 펼친 설정에는 지금처럼 검사를 통과한 값만 들어간다. 셸이 없는 이미지 안에서는 검사할 수 없으므로, 검사와 펼치기는 컨테이너 밖에서 한다.
- Blackbox Exporter의 HTTPS 확인은 코어 서버 OS의 CA 인증서 파일을 쓴다. Debian·Ubuntu 계열과 RHEL·Amazon Linux 계열에서 운영자가 경로를 적지 않아도 동작한다(사람 확인: 2026-11-09). 운영자가 설치할 때 운영 가이드대로 OS의 CA 인증서 파일을 설치 폴더의 `certs/ca-certificates.crt`에 복사하고, compose 파일이 그 파일을 HTTPS 확인을 하는 Blackbox Exporter 컨테이너에만 읽기 전용으로 붙인다. 운영 명령은 OS의 파일을 찾거나 복사하지 않고, 복사한 파일이 있고 컨테이너가 읽을 수 있는지만 확인한다(사람 확인: 2026-11-10). 시스템 파일을 다루는 일을 운영 명령에 두지 않기 위해서다. CA 인증서 파일은 코어 서버 OS의 파일이라 묶음에 들어가지 않으므로, 묶음의 라이선스가 늘지 않는다(사람 확인: 2026-11-09).
- 세 프로그램의 정상 상태는 컨테이너 healthcheck 대신 운영 명령이 코어 서버에서 `127.0.0.1`의 호스트 포트로 준비 확인 주소를 불러 판단한다(사람 확인: 2026-11-09).
- 설정 검사와 규칙 테스트는 빌드 PC에서 공식 이미지의 `promtool`, `amtool` 등으로 한다. 운영 이미지에 `promtool`을 넣지 않는 것은 이 변경의 결과로 따라온다(사람 확인: 2026-11-09).
- 시간대 자료는 넣지 않고, 코어는 지금처럼 UTC로 돈다(사람 확인: 2026-11-09).

## 하지 않는 것

- 세 프로그램의 버전을 올리거나, 소스에서 다시 빌드하거나, 실행 파일을 고치는 것. 공식 이미지의 실행 파일을 그대로 쓴다.
- 정상 확인이나 설정 펼치기를 하는 프로그램을 따로 만들어 이미지에 넣는 것. 세 프로그램 밖의 코드와 라이선스가 이미지에 들어간다.
- 코어 서버 OS에 CA 인증서를 설치하거나 갱신하는 것, 운영 명령이 OS의 CA 인증서 파일을 찾거나 복사하는 것(사람 확인: 2026-11-10). 운영 명령은 복사한 파일이 없을 때 복사하는 방법만 안내한다.
- 설치 폴더의 `certs/` 밖의 CA 인증서 파일을 쓰게 하는 것. 설정 파일(`.env`)에 CA 파일 경로를 적는 값을 두지 않는다(사람 확인: 2026-11-09). [0013](0013-core-env-settings.md)이 정한 서버 값 목록이 그대로이기 때문이다.
- Prometheus, Alertmanager, node_exporter 컨테이너에 CA 인증서 파일을 붙이는 것. 이 셋은 HTTPS로 부르는 곳이 없다(사람 확인: 2026-11-09).
- 시간대를 쓰는 설정(예: Alertmanager `time_intervals`의 `location`)을 더하는 것. 더하려면 시간대 자료를 다시 넣어야 하므로 별도 요구사항으로 다룬다.
- 서버에서 바꾸는 코어 값의 종류, 허용 범위, 검사 규칙을 바꾸는 것([0013](0013-core-env-settings.md))
- 관리자 서버(앱) 이미지, windows_exporter, ARM 서버용 묶음
- 묶음 크기를 줄이려고 실행 파일을 압축하는 것

## 사용자 경험

이 변경의 사용자는 코어 서버의 운영자와, 빌드 PC에서 코어를 빌드하는 개발자다.

운영자는 지금과 같은 순서로 설치하고 띄운다.

1. 운영자가 빌드 PC에서 만든 묶음 폴더를 코어 서버로 옮긴다. 묶음 폴더에는 BusyBox 소스 폴더(`sources/`)가 없다.
2. 운영자가 설치 준비 명령을 실행한다. 지금과 같다.
3. 운영자가 운영 가이드대로 코어 서버 OS의 CA 인증서 파일을 설치 폴더의 `certs/`에 한 번 복사한다(사람 확인: 2026-11-10).
4. 운영자가 띄우기 명령을 실행한다. 운영 명령이 설정 값과 CA 인증서 파일을 확인해 설정을 펼치고, 코어를 띄운 뒤 정상 상태가 될 때까지 기다린다.
5. 운영자가 상태 명령으로 버전, 컨테이너 상태와 정상 여부, 기본값과 다른 설정 값을 본다.

운영자에게 보이는 차이는 다음과 같다.

- 운영 명령이 펼친 설정은 코어 서버에 파일로 남는다. 띄울 때마다 다시 만들므로 운영자가 고치지 않는다.
- 컨테이너 안에 셸이 없어서 `docker exec`로 컨테이너 안의 명령을 실행할 수 없다. 운영자는 로그(`docker logs`)와 `127.0.0.1`의 HTTP API로 코어를 본다.
- 운영 명령 없이 Compose로 띄우려면 먼저 운영 명령의 설정 펼치기 작업을 실행한다(사람 확인: 2026-11-09).
- 컨테이너 healthcheck가 없어서 `docker compose ps`와 `docker ps`에 `healthy` 표시가 없다. 정상 여부는 운영 명령의 상태 명령으로 본다(사람 확인: 2026-11-09).
- 감시 대상 Linux 서버의 운영자는 node_exporter 묶음을 지금처럼 옮겨 이미지를 불러오고 띄운다. node_exporter 묶음 폴더에도 `sources/`가 없다(사람 확인: 2026-11-09).

개발자는 지금처럼 빌드 PC용 명령으로 묶음을 만들고, 설정을 검사하고, 개발용 코어를 띄운다. 설정 검사는 운영 이미지 대신 공식 이미지의 도구로 하고, 운영 이미지에 정해진 파일만 있는지도 함께 본다.

## 동작

### 정상 동작

- **S1. 처음 설치하고 띄우기**
  - 상황: 인터넷에 닿지 않는 x86-64 Linux 코어 서버에 Docker가 있고, 이 변경이 든 묶음 폴더를 옮겼다.
  - 행동: 운영자가 설치 준비와 띄우기 명령을 실행한다.
  - 결과: [0011](0011-core-ops-script.md)의 S1·S2와 같게 token과 설정 파일이 생기고, 세 프로그램이 정상 상태가 되며, 띄운 버전과 커밋이 보인다. 인터넷에서 아무것도 받지 않는다.
- **S2. 서버에서 바꾸는 값 반영**
  - 상황: 코어가 떠 있다.
  - 행동: 운영자가 설정 파일의 관리자 서버 주소나 코어 값을 바꾸고 띄우기 명령을 실행한다.
  - 결과: 운영 명령이 지금과 같은 규칙으로 검사한 뒤, 검사를 통과한 값으로 설정을 다시 펼쳐 코어를 띄운다. [0013](0013-core-env-settings.md)의 S2~S4·S14와 결과가 같고, 기록 보관 값을 줄이면 지금처럼 확인을 묻는다(0013의 S12).
- **S3. HTTPS 주소 확인**
  - 상황: Debian·Ubuntu 계열이나 RHEL·Amazon Linux 계열 코어 서버에, OS가 기본으로 둔 CA 인증서 파일이 있다.
  - 행동: 운영자가 운영 가이드대로 그 파일을 설치 폴더의 `certs/`에 복사하고, 경로를 적지 않고 띄우기 명령을 실행한다. 관리자 서버가 공인 인증서를 쓰는 HTTPS 주소를 감시 대상으로 내준다.
  - 결과: compose 파일이 복사한 파일을 Blackbox Exporter에 읽기 전용으로 붙이고(사람 확인: 2026-11-10), HTTPS 확인이 성공한다.
- **S4. OS의 CA 인증서가 바뀜**
  - 상황: 운영자가 코어 서버 OS의 CA 인증서를 갱신하거나 사내 인증 기관을 OS에 등록했다.
  - 행동: 운영자가 운영 가이드대로 OS의 CA 인증서 파일을 설치 폴더의 `certs/`에 다시 복사하고 띄우기 명령을 실행한다.
  - 결과: Blackbox Exporter가 OS의 새 CA 인증서로 확인한다. 사내 인증 기관을 등록했으면 그 기관이 서명한 HTTPS 주소도 성공한다. 이미지에 CA 묶음을 넣던 지금은 사내 인증 기관을 믿지 않았으므로 바뀌는 동작이다. 다시 복사하고 띄우기 전에는 바뀐 인증서를 쓰지 않는다(사람 확인: 2026-11-10).
- **S5. 이 변경 전 버전에서 갱신**
  - 상황: 이 변경 전 버전의 코어가 떠 있다.
  - 행동: 운영자가 새 묶음 폴더를 이전 폴더 옆에 두고, [0011](0011-core-ops-script.md)의 갱신 절차대로 설치 준비와 띄우기를 실행한다.
  - 결과: 새 버전이 이전 설정 파일의 값과 같은 token으로 뜨고, 같은 volume의 쌓아 온 기록과 Alert 상태가 이어진다.
- **S6. 이 변경 전 버전으로 되돌리기**
  - 상황: 이 변경의 버전이 떠 있고, 이전 버전 묶음 폴더가 남아 있다.
  - 행동: 운영자가 이전 폴더에서 띄우기 명령을 실행하고 확인에 `y`를 넣는다.
  - 결과: 이전 버전이 지금처럼 이미지 안에서 설정을 펼쳐 뜨고, 기록과 Alert 상태가 이어진다. 새 버전이 펼친 설정 파일은 쓰지 않는다.
- **S7. 상태 보기**
  - 상황: 코어가 떠 있거나 멈춰 있다.
  - 행동: 운영자가 상태 명령을 실행한다.
  - 결과: 떠 있는 버전, 커밋, 세 컨테이너의 상태와 정상 여부, 기본값과 다른 설정 값이 보인다. 정상 여부는 운영 명령이 코어 서버에서 `127.0.0.1`의 호스트 포트로 세 프로그램의 준비 확인 주소(Prometheus와 Alertmanager의 `/-/ready`, Blackbox Exporter의 `/-/healthy`)를 부른 결과다(사람 확인: 2026-11-09). 호스트 포트를 바꿨으면 바꾼 포트로 부른다.
- **S8. 운영 명령 없이 Compose로 띄우기**
  - 상황: 운영자가 [운영 가이드의 운영 명령 없이 실행](../OPERATIONS.md#운영-명령-없이-실행)대로 띄우려 한다.
  - 행동: 운영자가 운영 명령의 설정 펼치기 작업을 실행한 뒤 `docker compose up -d`를 실행한다.
  - 결과: 설정 펼치기 작업은 띄우기와 같은 규칙으로 설정 값과 관리자 서버 주소를 검사하고, token 파일과 CA 인증서 파일을 확인한 뒤 설정을 펼친다. 컨테이너는 만들거나 바꾸지 않는다. 이어서 Compose가 검사를 통과한 값으로 펼친 설정과 CA 인증서 파일로 코어를 띄운다(사람 확인: 2026-11-09). 펼친 뒤 설정 파일을 바꾸고 다시 펼치지 않으면 바꾼 값은 반영되지 않으므로, 운영 가이드에 이 점을 쓴다. 작업 이름은 계획에서 정한다.
- **S9. 빌드 PC의 설정 검사**
  - 상황: 개발자가 코어 설정이나 규칙을 바꿨다.
  - 행동: 개발자가 빌드 PC의 설정 검사를 실행한다.
  - 결과: 공식 이미지의 도구로 기본값과 허용 범위 양 끝 값으로 펼친 Prometheus·Alertmanager·Blackbox 설정을 검사하고, 운영 이미지에 든 것과 같은 규칙 파일로 규칙 테스트를 하며, 운영 명령 시험을 실행한다. 운영 이미지에 정해진 파일 밖의 것(셸, BusyBox, `promtool`, `amtool`, CA 묶음, 시간대 자료 등)이 있으면 실패한다.
- **S10. 빌드 PC에서 개발용으로 띄우기**
  - 상황: 저장소의 `infrastructure/`에 설정 파일과 token 파일이 있다.
  - 행동: 개발자가 빌드 PC용 명령의 띄우기 작업을 실행한다.
  - 결과: 명령 하나로 운영 명령과 같은 규칙의 검사와 펼치기를 거쳐, 바뀐 설정으로 다시 만든 운영 이미지와 같은 이미지가 뜬다([ADR 0009](../decisions/0009-core-config-in-image.md)).
- **S11. 묶음 만들기**
  - 상황: 빌드 PC에 저장소, Docker, Node가 있다.
  - 행동: 개발자가 묶음 만들기 작업을 실행한다.
  - 결과: 코어 묶음에 세 프로그램의 라이선스 전문과 고지만 있고, BusyBox 소스와 BusyBox 라이선스가 없다. 묶음 안내 파일은 세 프로그램만 적는다. node_exporter 묶음에는 node_exporter의 라이선스 전문과 고지만 있다(사람 확인: 2026-11-09). 묶음 만들기는 인터넷에서 BusyBox 소스를 받지 않는다.
- **S19. 감시 대상 서버에 node_exporter 설치**
  - 상황: 인터넷에 닿지 않는 Docker가 있는 Linux 감시 대상 서버에 이 변경이 든 node_exporter 묶음을 옮겼다.
  - 행동: 운영자가 [운영 가이드의 Docker가 있는 Linux 서버](../OPERATIONS.md#docker가-있는-linux-서버)대로 이미지를 불러와 띄운다.
  - 결과: 인터넷에서 아무것도 받지 않고 최소 이미지의 node_exporter가 뜨며, 코어가 지금과 같은 이름의 지표를 수집한다(사람 확인: 2026-11-09). Docker가 없는 서버용 실행 파일과 systemd unit은 바뀌지 않는다.

### 예외 동작

S12~S14에서 운영 명령(띄우기와 설정 펼치기)은 무엇이 잘못됐는지와 고치는 방법을 한국어로 보이고 실패로 끝난다. 이때 컨테이너를 만들거나 바꾸지 않으므로 떠 있던 코어는 그대로 돈다. S15는 띄운 뒤에 생기는 경우라 이미 띄운 컨테이너를 그대로 둔다.

- **S12. 틀린 설정 값이나 관리자 서버 주소**
  - 상황: 설정 파일이나 셸 환경 변수의 값이 [0013](0013-core-env-settings.md)의 S8~S10, S16에 해당한다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 지금과 같은 안내가 보이고 설정을 펼치지 않는다. 이전에 펼친 설정 파일도 바꾸지 않는다.
- **S13. CA 인증서 파일이 없음**
  - 상황: 설치 폴더의 `certs/ca-certificates.crt`가 없거나, 비어 있거나, 그 자리에 폴더가 있거나, 컨테이너 사용자가 읽을 수 없다.
  - 행동: 운영자가 띄우기 명령이나 설정 펼치기 작업을 실행한다.
  - 결과: 복사할 곳과 OS마다 복사할 파일, 운영 가이드를 안내하고 펼치거나 띄우지 않는다(사람 확인: 2026-11-09, 사람 확인: 2026-11-10). 띄우면 HTTPS 확인이 모두 실패해 장애 알림이 한꺼번에 갈 수 있기 때문이다.
- **S14. token이 없거나 쓸 수 없음**
  - 상황: token 파일이 없거나, 비어 있거나, 그 자리에 폴더가 있거나, 컨테이너 사용자가 읽을 수 없다.
  - 행동: 운영자가 띄우기 명령이나 설정 펼치기 작업을 실행한다.
  - 결과: [0011](0011-core-ops-script.md)의 S10과 같게 네 경우를 구분해 알리고, 설정을 펼치거나 띄우지 않는다(사람 확인: 2026-11-09). 그래서 운영 명령 없이 Compose로 띄우는 경로에서도 token 없이 Alertmanager가 떠 장애 알림이 조용히 끊기지 않는다.
- **S15. 정상 상태가 되지 않음**
  - 상황: 띄운 프로그램 가운데 하나의 준비 확인 주소가 3분 안에 준비됐다고 답하지 않는다.
  - 행동: 운영자가 띄우기 명령이나 token 바꾸기 명령을 실행했다.
  - 결과: [0011](0011-core-ops-script.md)의 S11과 같게, 정상이 아닌 컨테이너와 그 로그를 보는 명령이 보인다(사람 확인: 2026-11-09). 코어 서버에 준비 확인 주소를 부를 `curl`이나 `wget`이 없을 때의 동작은 이 요구사항에서 정하지 않고, 계획에서 지원하는 OS에 두 도구가 기본으로 있는지 확인한 뒤 정한다(사람 확인: 2026-11-09).
- **S16. 펼친 설정 없이 Compose로 띄움**
  - 상황: 운영 명령으로 설정을 펼친 적이 없거나 펼친 파일을 지웠다.
  - 행동: 운영자가 묶음 폴더에서 `docker compose up -d`를 실행한다.
  - 결과: 코어 컨테이너가 시작하지 않고, 운영 명령으로 설정을 펼치라는 안내를 볼 수 있다(사람 확인: 2026-11-09). Docker가 없는 파일 자리에 빈 폴더를 만들어 프로그램이 그 폴더를 설정으로 읽는 일이 생기지 않는다.
- **S17. 펼친 설정 파일을 서버에서 고침**
  - 상황: 운영자가 운영 명령이 펼친 설정 파일을 직접 고쳤다.
  - 행동: 운영자가 띄우기 명령을 실행한다.
  - 결과: 운영 명령이 띄우는 이미지와 같은 버전의 템플릿에서 설정을 다시 만들어, 고친 내용이 남지 않는다. 설정과 규칙의 출처는 이미지 버전 하나다([ADR 0009](../decisions/0009-core-config-in-image.md)).
- **S18. 컨테이너 안에서 셸을 열려 함**
  - 상황: 운영자가 문제를 살펴보려고 한다.
  - 행동: 운영자가 `docker exec -it prometheus sh`를 실행한다.
  - 결과: 컨테이너에 셸이 없다는 Docker 오류로 끝난다. 운영 가이드는 로그와 `127.0.0.1`의 HTTP API로 보는 방법만 안내한다.

### 보안

- 접근 권한: 설정 파일, 펼친 설정 파일, token 폴더는 묶음 폴더와 설치 폴더에 쓸 수 있는 코어 서버 운영자만 바꾼다. 코어 포트는 지금처럼 `127.0.0.1`에만 연다.
- 외부 입력: 설정 파일과 셸 환경 변수의 값. 지금처럼 [0013](0013-core-env-settings.md)의 S8·S16 형식만 받아 펼치므로, 줄바꿈이나 YAML 문법으로 다른 설정을 바꾸는 길이 없다. 운영자가 복사한 CA 인증서 파일은 OS와 운영자가 관리하는 파일로 보고 내용을 검사하지 않는다. 그래서 OS에 등록한 인증 기관을 Blackbox Exporter도 믿는다(S4). compose 파일은 이 파일을 Blackbox Exporter 컨테이너에만 읽기 전용으로 붙인다(사람 확인: 2026-11-09). 운영 명령은 OS의 파일을 읽거나 옮기지 않는다(사람 확인: 2026-11-10).
- 민감한 정보: webhook token. 지금처럼 Docker secret 파일로만 받고, 이미지, 묶음, 펼친 설정 파일, 출력에 넣지 않는다. 법이 암호화를 요구하는 항목은 아니다.
- 남길 보안 이벤트: 없음

이미지에 셸과 기본 명령이 없어서, 코어 컨테이너 안에서 실행할 수 있는 프로그램은 세 프로그램뿐이고 node_exporter 컨테이너 안에서는 node_exporter뿐이다.

### 바뀌지 않는 것

이 변경 뒤에도 다음은 그대로다.

- 세 프로그램의 버전(Prometheus v3.14.0, Alertmanager v0.34.1, Blackbox Exporter v0.28.0)과 공식 이미지의 실행 파일
- 실행 사용자: Prometheus와 Alertmanager는 `nobody`(UID 65534), Blackbox Exporter는 `root`(UID 0). Blackbox Exporter의 ping 확인이 지금처럼 동작한다.
- 쓰기 위치와 데이터: Prometheus의 `/prometheus`, Alertmanager의 `/alertmanager`에 붙는 volume `prometheus-data`, `alertmanager-data`와 그 안의 기록. 새 서버에서 처음 만든 volume에도 각 프로그램이 쓸 수 있다.
- 설정 파일 위치를 뺀 실행 인자(기록 위치, `--enable-feature=utf8-strict-mode` 등). 실행 인자로 설정 값을 넘기지 않는다([0013](0013-core-env-settings.md)).
- 컨테이너 이름, 컨테이너 안 포트(9090, 9093, 9115), 네트워크 이름 `monitoring`, `127.0.0.1` 바인딩, 재시작 정책 `unless-stopped`. 관리자 서버와의 약속이다([ADR 0007](../decisions/0007-core-app-contract.md), [INTEGRATION.md](../INTEGRATION.md)).
- 이미지 이름과 버전 태그, 버전·커밋·커밋 시각 label. 운영 명령이 이 label로 버전의 앞뒤를 판단한다.
- 설정 템플릿과 Alert 규칙의 내용, 통합 계약의 API·label·series. INTEGRATION.md에서는 설정을 펼치는 곳을 설명한 문장만 고친다.
- [0013](0013-core-env-settings.md)의 값, 기본값, 허용 범위, 검사 규칙, 안내 문구와, 관리자 서버 주소를 공용 검사 함수 하나로 검사하는 것([ADR 0011](../decisions/0011-core-address-format-check.md))
- [0011](0011-core-ops-script.md)의 운영 명령 작업(`install`, `start`, `rotate-token`, `status`)과 그 순서, 설치 폴더와 token 위치. 설정 펼치기 작업은 새로 더한다(S8).
- node_exporter의 버전(v1.12.1), 실행 사용자 `nobody`(UID 65534), 포트 9100, 서버의 네트워크·프로세스를 그대로 보고 루트 파일 시스템을 읽기 전용으로 붙이는 실행 방식, Docker가 없는 서버용 실행 파일과 systemd unit
- 컨테이너 이름과 감시 대상 주소의 이름 풀이. 공식 이미지는 `/etc/nsswitch.conf`로 `/etc/hosts`를 DNS보다 먼저 보므로 이 순서도 그대로여야 한다.
- 로그와 계산의 시각은 UTC다.
- 묶음은 x86-64 서버용이고, 코어 서버에는 인터넷, 저장소, Node가 필요 없다. 운영 명령은 POSIX sh와 코어 서버의 기본 도구, Docker만 쓴다. 준비 확인 주소를 부를 `curl`이나 `wget`이 기본 도구에 드는지는 계획에서 확인한다(S15).

## 완료 기준

- [ ] C1. 세 코어 이미지의 파일이 세 프로그램의 실행 파일, 이 프로젝트의 설정·규칙, 프로그램이 쓰는 빈 폴더뿐이고, node_exporter 이미지의 파일이 node_exporter 실행 파일뿐이다. 셸, BusyBox, `promtool`, `amtool`, `wget`, CA 묶음, 시간대 자료가 없다. (목표, S9) — 확인: 빌드 검사가 이미지마다 파일 목록을 허용 목록과 비교하고, 허용 목록 밖의 파일을 넣은 이미지에서 실패하는지 본다
- [ ] C2. 세 프로그램의 실행 사용자, 쓰기 위치, 실행 인자(설정 파일 위치 제외), 컨테이너 안 포트, 이미지 label이 이 변경 전 이미지와 같다. (바뀌지 않는 것) — 확인: 빌드 검사가 `docker image inspect` 값을 기대값과 비교, 두 버전 이미지를 비교하는 수동 확인
- [ ] C3. 인터넷이 없는 Linux 코어 서버에서 설치 준비와 띄우기만으로 세 프로그램이 정상 상태로 뜨고, 관리자 서버 주소와 코어 값이 펼친 설정에 들어간다. (S1, S2) — 확인: 인터넷을 끊은 Linux 컨테이너 안의 Docker에서 수동 확인, Prometheus flags·config API와 Blackbox `/config`로 값 확인
- [ ] C4. Debian·Ubuntu 계열과 RHEL·Amazon Linux 계열 코어 서버에서 운영 가이드대로 CA 인증서 파일을 복사하고 경로를 적지 않고 띄워 공인 인증서의 HTTPS 주소 확인이 성공한다. OS에 사내 인증 기관을 등록하고 다시 복사해 띄우면 그 기관이 서명한 주소도 성공한다. (S3, S4) — 확인: 두 계열의 Linux 환경에서 수동 확인
- [ ] C5. CA 인증서 파일은 Blackbox Exporter 컨테이너에만 붙는다. 설치 폴더의 CA 인증서 파일이 없거나 쓸 수 없으면 띄우기와 설정 펼치기가 복사하는 방법을 보이고, 설정을 펼치거나 컨테이너를 바꾸지 않고 실패한다. 운영 명령은 OS의 CA 인증서 파일을 읽거나 옮기지 않는다. (S3, S13) — 확인: 운영 명령 자동 시험, 띄운 세 컨테이너의 mount를 `docker inspect`로 보는 수동 확인
- [ ] C6. 이 변경 전 버전에서 갱신하면 기록(`minTime`)과 Alert 상태(silence)가 이어지고, 이 변경 전 버전으로 되돌릴 수 있다. (S5, S6) — 확인: 버전이 다른 묶음 두 개로 수동 확인
- [ ] C7. 틀린 설정 값과 관리자 서버 주소를 운영 명령이 지금처럼 거부하고, 이때 설정 파일을 펼치거나 바꾸지 않으며 컨테이너를 바꾸지 않는다. (S12) — 확인: 운영 명령 자동 시험. 검사를 지운 사본에서 시험이 실패하는지도 본다
- [ ] C8. 컨테이너 healthcheck가 없고, 운영 명령이 `127.0.0.1`의 호스트 포트(바꾼 포트 포함)로 준비 확인 주소를 불러 정상 여부를 판단한다. 준비되지 않은 프로그램을 띄우기와 token 바꾸기가 찾아 알리고, 상태 명령이 정상 여부를 보인다. (S7, S15) — 확인: 운영 명령 자동 시험, 한 프로그램을 일부러 준비되지 않게 만든 수동 확인
- [ ] C9. 설정 펼치기 작업 뒤 `docker compose up -d`로 코어가 뜨고, 펼친 설정이 없으면 코어 컨테이너가 시작하지 않으며, 설정 펼치기 작업은 틀린 값, token 문제, CA 파일 없음에서 설정을 펼치지 않는다. (S8, S12~S14, S16) — 확인: 운영 명령 자동 시험, 묶음 폴더에서 Compose로 직접 띄우는 수동 확인
- [ ] C10. 펼친 설정 파일을 고친 뒤 띄우면 고친 내용이 남지 않는다. (S17) — 확인: 운영 명령 자동 시험
- [ ] C11. 빌드 PC의 설정 검사가 공식 이미지의 도구로 기본값과 양 끝 값의 세 벌을 검사하고, 운영 이미지에 든 것과 같은 규칙 파일로 규칙 테스트를 하며, 운영 명령 시험을 BusyBox `sh`에서도 실행한다. [0013](0013-core-env-settings.md)의 C7처럼 범위 밖 값을 허용 범위에 넣으면 실패한다. (S9) — 확인: `node scripts/build-core-bundle.mjs --check`
- [ ] C12. 빌드 PC용 명령의 띄우기 작업 하나로 개발용 코어가 뜬다. (S10) — 확인: Windows 빌드 PC에서 수동 확인
- [ ] C13. 코어 묶음과 node_exporter 묶음에 `sources/`와 BusyBox 라이선스가 없고, 묶음 만들기가 BusyBox 소스를 받지 않는다. 묶음의 라이선스 파일과 안내 파일, [LICENSES.md](../LICENSES.md)의 고지와 들여온 것 표가 묶음의 실제 내용과 맞다. 묶음과 이미지, 펼친 설정에 비밀값이 없다. (S11, 보안) — 확인: 묶음 만들기 결과의 파일 목록, 묶음 만들기의 비밀값 검사, 문서 리뷰
- [ ] C16. 인터넷이 없는 Docker가 있는 Linux 서버에서 node_exporter 묶음으로 최소 이미지의 node_exporter가 `nobody`로 뜨고, `/metrics`가 이 변경 전 이미지와 같은 이름의 지표를 내며, 관리자 서버의 연결 시험이 통과한다. (S19) — 확인: 인터넷을 끊은 Linux 환경에서 수동 확인, 두 이미지의 `/metrics` 지표 이름 비교
- [ ] C14. 묶음 폴더, 불러온 이미지, 메모리를 다시 재서 운영 가이드의 코어 서버 사양 표에 적는다. 줄어드는 정도는 구현할 때 잰다. — 확인: 2026-11-09의 측정과 같은 방법으로 수동 측정
- [ ] C15. 운영 가이드(설치, 운영 명령 없이 실행, 설치 확인, 상태, 문제 해결, 라이선스), ARCHITECTURE.md, DEVELOPMENT.md의 검사 설명, INTEGRATION.md의 코어 설정, LICENSES.md가 바뀐 동작에 맞고, ADR 0012가 있으며, 문서 검사가 통과한다. [#44](https://github.com/subinggrae/server-monitor/issues/44)는 필요 없어진 이유를 적어 닫는다. — 확인: `node scripts/check-docs.mjs`, 문서 리뷰
