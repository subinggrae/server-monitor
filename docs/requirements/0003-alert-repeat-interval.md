# 0003. Check마다 다른 알림 재발송 주기

- 상태: 승인
- 작성일: 2026-10-14
- 관련: [0001](0001-per-target-scrape-interval.md)

## 배경

장애가 이어지는 동안 Telegram 알림을 다시 보내는 주기는 Alertmanager 설정(`infrastructure/alertmanager/alertmanager.yml`)의 `repeat_interval: 1h` 하나뿐이다. 모든 Check가 1시간마다 다시 알림을 받는다. 중요한 Check는 더 자주, 덜 중요한 Check는 더 드물게 받고 싶어도 Check마다 다르게 정할 수 없다.

이 값을 바꾸려면 설정 파일을 고치고 Alertmanager를 다시 띄우거나 설정을 다시 읽혀야 한다. 사용자가 화면에서 바꾼 설정 때문에 `infrastructure/`의 파일을 고치지 않는다는 경계([ARCHITECTURE.md의 지켜야 할 경계](../ARCHITECTURE.md#지켜야-할-경계))도 어긴다. Manager API에는 Alertmanager의 즉시 재시도만 막는 2분 중복 방지(`dedupe-window`)가 있을 뿐, 재발송 주기를 판단하는 곳은 없다.

## 목표

- 사용자가 화면에서 Check마다 재발송 주기를 정한다. 그 Check에 연결한 모든 Telegram 그룹이 같은 주기를 쓴다.
- 정한 주기는 Manager Database에 저장되고, Manager API와 Alertmanager를 다시 띄우지 않아도 다음 webhook부터 반영된다.
- 장애가 이어지는 동안 Manager API가 Alertmanager의 webhook을 받을 때마다, 마지막으로 보낸 뒤 정한 주기가 지났는지 보고 다시 보낼지 정한다.
- 주기를 정하지 않은 Check는 지금과 같은 1시간마다 다시 알림을 받는다.

## 하지 않는 것

- 사용자 설정 때문에 `alertmanager.yml`과 Alert 규칙을 고치거나 만드는 것
- Alertmanager가 보내지 않은 Alert를 Manager API가 스스로 다시 보내는 것. 장애가 이어지는지는 Alertmanager의 webhook으로만 안다.
- 첫 알림까지 기다리는 시간(`group_wait`)과 Alert 규칙의 판단 시간(`for: 1m`)을 바꾸는 것
- 복구 알림을 반복해서 보내는 것. 복구 알림은 지금처럼 한 번 보낸다.
- 재발송 알림의 메시지 형식을 바꾸는 것
- Telegram 그룹마다 다른 재발송 주기를 두는 것
- 재발송을 끄는 선택. 가장 긴 주기는 24시간이다.

## 사용자 경험

1. 사용자가 Check 상세 화면의 알림 절에서 재발송 주기를 분 단위로 입력한다. 처음 값은 60분이고, 5분에서 1440분(24시간)까지 입력할 수 있다는 안내가 보인다. 하한 5분은 Alertmanager가 같은 묶음을 다시 보내는 간격(`group_interval: 5m`)이다.
2. 범위 밖 값을 입력하고 저장하면 입력 칸 아래에 허용 범위를 알려 주는 오류가 보인다.
3. 저장하면 화면에 저장한 주기가 보인다. 장애가 이어지는 Check는 다음 webhook부터 새 주기로 다시 알림을 받는다.
4. 실제로 다시 보내는 시각은 정한 주기보다 최대 5분 늦을 수 있다는 안내가 보인다. Alertmanager가 5분마다 webhook을 보내고, Manager API는 그때 판단하기 때문이다. webhook 도착 시각의 작은 차이로 한 번 건너뛰지 않도록 1분의 허용 오차를 두므로, 주기보다 최대 1분 일찍 보낼 수도 있다(사람 확인: 2026-10-14).

## 동작

### 정상 동작

- **S1. 재발송 주기 정하기**
  - 상황: 사용자가 Check의 알림 설정을 고친다.
  - 행동: 5분에서 1440분 사이의 정수 분으로 재발송 주기를 정하고 저장한다.
  - 결과: 저장한 주기가 Manager Database에 남고, 알림 설정 조회 API 응답과 화면에 그 주기가 보인다.
- **S2. 주기가 지나서 다시 알림**
  - 상황: Check의 Alert가 이어지고 있고, 그 Telegram 그룹에 마지막으로 보낸 지 재발송 주기에서 1분을 뺀 시간 이상 지났다.
  - 행동: Alertmanager가 같은 Alert를 webhook으로 다시 보낸다.
  - 결과: 그 그룹에 Telegram 알림을 다시 보내고 전송 기록에 남긴다.
- **S3. 주기가 지나지 않음**
  - 상황: Check의 Alert가 이어지고 있고, 그 그룹에 마지막으로 보낸 지 재발송 주기에서 1분을 뺀 시간이 지나지 않았다.
  - 행동: Alertmanager가 같은 Alert를 webhook으로 다시 보낸다.
  - 결과: Telegram으로 보내지 않는다. 받은 Alert는 지금처럼 기록한다. 주기 전이라 보내지 않은 것은 전송 기록에 남기지 않는다. 5분마다 쌓여 전송 기록을 읽기 어렵게 만들기 때문이다.
- **S4. 장애 중에 주기를 바꿈**
  - 상황: Check의 Alert가 이어지는 동안 사용자가 재발송 주기를 바꾼다.
  - 행동: Alertmanager가 다음 webhook을 보낸다.
  - 결과: 바뀐 주기로 S2, S3를 판단한다. Manager API와 Alertmanager를 다시 띄우지 않는다.
- **S5. 첫 알림과 복구 알림**
  - 상황: 새 Alert가 생기거나, 이어지던 Alert가 복구됐다.
  - 행동: Alertmanager가 webhook을 보낸다.
  - 결과: 재발송 주기와 관계없이 지금처럼 바로 보낸다.
- **S6. 기존 Check**
  - 상황: 이 기능 전에 등록한 Check가 있다.
  - 행동: 기능을 배포한다.
  - 결과: 기존 Check의 재발송 주기는 60분이고, 화면에도 60분으로 보인다.

### 예외 동작

- **S7. 허용하지 않는 주기**
  - 상황: 재발송 주기에 5분보다 짧거나 1440분보다 긴 값, 정수가 아닌 값을 넣는다.
  - 행동: 화면이나 API로 알림 설정 저장 요청을 보낸다.
  - 결과: 저장을 거부하고 재발송 주기 입력 칸 아래에 허용 범위를 알려 주는 오류를 보인다. 기존 설정은 바뀌지 않는다.
- **S8. 주기를 보내지 않은 요청**
  - 상황: 재발송 주기 값이 없는 알림 설정 저장 요청이 들어온다.
  - 행동: 알림 설정 저장 요청을 보낸다.
  - 결과: 기존 주기를 그대로 둔다. 새로 등록한 Check의 주기는 60분이다.
- **S9. 이전 전송이 실패함**
  - 상황: 그 그룹에 마지막으로 보내려던 알림이 실패했다.
  - 행동: Alertmanager가 같은 Alert를 webhook으로 다시 보낸다.
  - 결과: 실패한 전송은 보낸 것으로 세지 않으므로, 마지막으로 성공한 전송을 기준으로 S2, S3를 판단한다.

### 보안

- 접근 권한: 기존 Check 알림 설정 화면과 같다. 화면용 API에는 인증이 없고 포트를 `127.0.0.1`에만 묶는다. Alertmanager webhook은 지금처럼 Bearer token으로 호출하는 쪽을 확인한다.
- 외부 입력: 화면용 API로 들어오는 재발송 주기 값. 5분에서 1440분 사이의 정수만 받는다.
- 민감한 정보: 없음
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- Alertmanager webhook의 요청 형식, Bearer token 확인, 응답(Telegram 전송이 실패해도 200)
- 받은 Alert를 `alert_events`에 기록하는 방식
- 복구 알림에서 Alertmanager의 즉시 재시도를 막는 2분 중복 방지. 이어지는 Alert의 즉시 재시도는 재발송 판단(하한 5분에서 허용 오차 1분을 뺀 4분)이 막는다.
- Check와 그룹 연결마다 정하는 Warning, Critical, 복구 알림 설정
- Alert 규칙, Alert label, HTTP SD 응답의 label
- 알림을 받을 Telegram 그룹을 Manager Database가 정하는 것

- [ ] C1. 알림 설정을 저장하면 정한 재발송 주기가 저장되고, 알림 설정 조회 API 응답에 그 주기가 들어 있다. (S1) — 확인: 알림 설정 API 단위 테스트
- [ ] C2. 마지막 성공 전송 뒤 주기에서 1분을 뺀 시간 이상 지났으면 다시 보내고, 지나지 않았으면 보내지 않으며 전송 기록도 남기지 않는다. 경계값(주기에서 1분을 뺀 시간과 정확히 같음)에서는 보낸다. (S2, S3) — 확인: 알림 전송 단위 테스트(현재 시각 주입)
- [ ] C3. 주기를 바꾼 뒤 들어온 webhook은 바뀐 주기로 판단한다. (S4) — 확인: 알림 전송 단위 테스트
- [ ] C4. 새 Alert와 복구 알림은 주기와 관계없이 보낸다. (S5) — 확인: 알림 전송 단위 테스트
- [ ] C5. 실패한 전송은 주기 계산에서 빠진다. (S9) — 확인: 알림 전송 단위 테스트
- [ ] C6. 기존 Check의 재발송 주기는 migration 뒤 60분이다. MariaDB와 PostgreSQL에서 같다. (S6) — 확인: 두 DB에 migration을 적용하고 수동 조회
- [ ] C7. 허용하지 않는 주기를 보내면 400과 재발송 주기 필드 오류를 돌려주고 저장된 값이 바뀌지 않는다. 주기가 없는 요청은 기존 값을 유지한다. (S7, S8) — 확인: 요청 검증 단위 테스트
- [ ] C8. 화면에서 재발송 주기를 입력하고 저장할 수 있고, 범위 밖 값이면 입력 칸 아래에 오류가 보이고, 저장한 주기와 최대 5분 지연 안내가 보인다. (S1, S7) — 확인: 컴포넌트 테스트
- [ ] C9. `docker compose`로 띄운 환경에서 Check를 장애 상태로 두고 재발송 주기를 바꾸면, 다시 띄우지 않고 바뀐 주기로 Telegram 알림이 다시 온다. (S2, S4) — 확인: 수동 확인
