# 0019. 모니터링 시스템이 운영자가 미리 만든 monitoring 네트워크를 쓰게 함

- 상태: 구현됨
- 작성일: 2026-11-16
- 관련: [PR #62](https://github.com/subinggrae/server-monitor/pull/62)(구현 계획과 확인 기록 포함), [0011](0011-core-ops-script.md), [0018](0018-core-only-repository.md), [ADR 0007](../decisions/0007-core-app-contract.md), [ADR 0014](../decisions/0014-operator-creates-monitoring-network.md)(0007의 네트워크를 만든다는 결정을 대신함), [INTEGRATION.md](../INTEGRATION.md), [운영 가이드](../OPERATIONS.md)

## 배경

모니터링 시스템과 관리자 서버는 같은 서버의 Docker 네트워크 `monitoring`으로 통신한다. 지금은 모니터링 시스템의 compose 파일(`infrastructure/compose.yml`)이 이 네트워크를 만들고, 관리자 서버는 `external: true`로 이미 있는 네트워크에 붙는다. 그래서 다음 문제가 있다.

- 관리자 서버는 모니터링 시스템이 떠 있어야만 띄울 수 있다. 모니터링 시스템을 먼저 띄우지 않으면 관리자 서버가 `network monitoring not found`로 뜨지 않는다(운영 가이드의 문제 해결).
- 모니터링 시스템을 `docker compose down`으로 내리면 Compose가 네트워크를 지우려 한다. 관리자 서버가 붙어 있으면 지우지 못해 경고가 나고, 붙어 있지 않으면 네트워크가 사라져 관리자 서버를 다시 띄울 때 실패한다.
- 네트워크를 모니터링 시스템 프로젝트가 가지므로, 모니터링 시스템을 갱신하거나 다시 설치할 때 관리자 서버 쪽 연결이 모니터링 시스템의 Compose 동작에 묶인다.

네트워크를 운영자가 한 번 만들고, 모니터링 시스템도 관리자 서버처럼 `external: true`로 붙게 한다(사람 확인: 2026-11-16).

## 목표

- 모니터링 시스템은 `monitoring` 네트워크를 만들지 않고, 이미 있는 네트워크에 붙는다. 관리자 서버와 모니터링 시스템 어느 쪽을 먼저 띄워도 된다.
- 운영자는 모니터링 서버를 처음 준비할 때 네트워크를 한 번 만든다. 그 방법이 운영 가이드에 있다.
- 네트워크가 없을 때 운영 명령이 모니터링 시스템을 띄우기 전에 멈추고, 만드는 명령을 알려 준다.
- 빌드 PC의 개발용 모니터링 시스템 실행(`monitoring-dev.bat start`)은 네트워크가 없으면 만든다.

## 하지 않는 것

- 네트워크 이름을 바꾸거나 설정 값으로 받는 것. 이름은 `monitoring` 그대로다(사람 확인: 2026-11-16).
- 운영 명령(`monitoring-server.sh`)이 네트워크를 만드는 것. 서버를 바꾸는 일은 운영 가이드로 안내하고 운영 명령은 최소 기능으로 둔다(사람 확인: 2026-11-16).
- 네트워크의 드라이버, 서브넷 같은 옵션을 정하는 것. Docker 기본값(bridge)을 쓴다.
- 모니터링 시스템과 관리자 서버를 다른 서버에 나눠 두는 것([#15](https://github.com/subinggrae/server-monitor/issues/15))

## 사용자 경험

1. 운영자가 모니터링 서버를 처음 준비할 때 운영 가이드대로 `docker network create monitoring`을 한 번 실행한다.
2. 모니터링 시스템과 관리자 서버를 각자 띄운다. 어느 쪽을 먼저 띄워도 된다.
3. 네트워크를 만들지 않고 `monitoring-server.sh start`를 실행하면, 운영 명령이 모니터링 시스템을 띄우지 않고 만드는 명령을 알려 준다.

## 동작

### 정상 동작

- **S1. 네트워크가 있을 때 모니터링 시스템 띄우기**
  - 상황: `monitoring` 네트워크가 있다.
  - 행동: 운영자가 `monitoring-server.sh start`를 실행한다.
  - 결과: 지금처럼 모니터링 시스템이 뜨고, 세 컨테이너가 그 네트워크에 붙는다.
- **S2. 관리자 서버를 먼저 띄움**
  - 상황: `monitoring` 네트워크가 있고 모니터링 시스템은 떠 있지 않다.
  - 행동: 관리자 서버를 먼저 띄운 뒤 모니터링 시스템을 띄운다.
  - 결과: 둘 다 뜬다. 모니터링 시스템이 뜨면 관리자 서버의 목록 API를 부르고, 관리자 서버는 `http://prometheus:9090`에 닿는다.
- **S3. 모니터링 시스템을 내림**
  - 상황: 모니터링 시스템과 관리자 서버가 떠 있다.
  - 행동: 운영자가 모니터링 시스템을 내린다(`docker compose down`).
  - 결과: 모니터링 시스템 컨테이너만 내려가고 `monitoring` 네트워크와 관리자 서버는 그대로다.
- **S4. 이미 모니터링 시스템을 설치한 서버를 갱신**
  - 상황: 이 변경 전의 모니터링 시스템이 만든 `monitoring` 네트워크가 있다.
  - 행동: 이 변경의 묶음으로 갱신한다.
  - 결과: 있던 네트워크를 그대로 쓰고, 운영자가 따로 할 일이 없다.
- **S5. 빌드 PC에서 개발용 모니터링 시스템 띄우기**
  - 상황: 빌드 PC에 `monitoring` 네트워크가 없다.
  - 행동: 개발자가 `monitoring-dev.bat start`를 실행한다.
  - 결과: 네트워크를 만들고 모니터링 시스템을 띄운다. 네트워크가 있으면 그대로 쓴다.

### 예외 동작

- **S6. 네트워크 없이 모니터링 시스템 띄우기**
  - 상황: `monitoring` 네트워크가 없다.
  - 행동: 운영자가 `monitoring-server.sh start`를 실행한다.
  - 결과: 컨테이너를 만들거나 바꾸기 전에 멈추고, 네트워크가 없다는 것과 `docker network create monitoring`으로 만든 뒤 다시 실행하라는 안내를 보인다. 떠 있던 모니터링 시스템은 그대로 둔다.
- **S7. 운영 명령 없이 Compose로 띄우기**
  - 상황: `monitoring` 네트워크가 없다.
  - 행동: 운영자가 운영 명령 없이 `docker compose up`을 실행한다.
  - 결과: Compose가 네트워크가 없다는 오류로 멈춘다. 운영 가이드의 문제 해결에 이 오류와 할 일이 있다.

### 보안

- 접근 권한: 바뀌지 않는다. 네트워크에 붙을 수 있는 것은 그 서버의 Docker를 쓸 수 있는 사람뿐이고, 지금과 같다.
- 외부 입력: 없음. 운영 명령은 고정된 이름 `monitoring`만 확인한다.
- 민감한 정보: 없음
- 남길 보안 이벤트: 없음

### 바뀌지 않는 것

- 네트워크 이름 `monitoring`, 모니터링 시스템 컨테이너 이름과 컨테이너 안 포트, 호스트 포트를 `127.0.0.1`에만 여는 것
- 모니터링 시스템과 관리자 서버 사이의 API와 webhook 계약
- 운영 명령의 다른 검사와 동작
