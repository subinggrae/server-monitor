# 디자인 점검

화면을 만들기 전과 만든 뒤에 하는 점검이다. 화면을 만드는 쪽과 판정하는 리뷰어가 함께 읽는다. 규칙은 [RULES.md](RULES.md), 이 제품의 결정은 [DESIGN.md](DESIGN.md)에 있다. 이 프로젝트가 이 파일과 다르게 정한 것은 [DESIGN.md의 고정 규칙과 다르게 정한 것](DESIGN.md#고정-규칙과-다르게-정한-것)에 있고, 그 절이 이 파일보다 앞선다.

## 점검 순서

화면 하나는 다음 순서로 만들고 고친다. 통과나 실패가 나오는 점검을 먼저 하고, 사람의 눈이 필요한 판정을 나중에 한다.

1. [만들기 전 점검](#만들기-전-점검)을 글로 정리한다.
2. 화면을 만든다.
3. [코드 점검](#코드-점검)으로 찾은 문제를 고친다.
4. [화면 점검](#화면-점검)대로 스크린샷을 찍고, 참고 화면과의 차이를 적고 고친다.
5. 화면을 만들지 않은 리뷰어가 [판정](#판정)한다.
6. 실패한 항목만 고치고 3부터 다시 한다.

## 만들기 전 점검

막연한 요청으로 만든 화면은 짜깁기한 배치, 정보에 비해 큰 컨테이너, 흔한 기본값으로 채워진다. 화면 코드를 쓰기 전에 다음을 글로 정리해 대화에 쓴다. 정리할 수 없는 항목은 만들기 전에 사람에게 묻는다.

- **목표**: [PRODUCT.md](../PRODUCT.md)의 대상과 가장 자주 하는 일 가운데 이 화면이 맡는 것
- **시각 용어**: [DESIGN.md](DESIGN.md)의 스타일과 이 화면에서 드러낼 색, 글자, 움직임, 배경. "깔끔하게" 같은 형용사 대신 스타일 이름과 토큰 이름으로 쓴다.
- **참고 이미지**: DESIGN.md 개요의 참고 화면이나 사람이 준 스크린샷. 참고 이미지에서 가져올 속성을 글로 풀어 쓴다.
- **예시 데이터**: 화면에 넣을 실제 같은 데이터. 짧은 값, 보통 값, 아주 긴 값, 빈 값을 넣는다.
- **쓸 코드**: 이 화면에 쓸 기존 컴포넌트와 토큰 파일의 위치
- **피할 기본값**: [흔한 기본값](#흔한-기본값) 가운데 이 화면에 나오기 쉬운 것과 대신 쓸 것. DESIGN.md의 해야 할 것과 하지 말 것을 함께 본다.

## 흔한 기본값

AI는 학습 데이터에서 가장 흔한 선택으로 모인다. 지시가 없으면 같은 글꼴, 같은 색, 같은 배치가 나온다. 화면에 다음이 있으면 이 제품에 필요한 이유를 설명할 수 있어야 하고, 설명하지 못하면 DESIGN.md의 값으로 바꾼다.

- **글꼴**: 이유 없이 고른 Inter, Roboto, Arial, 시스템 글꼴, Space Grotesk. 기울인 세리프 제목, 아주 좁힌 자간, 지나치게 큰 첫 제목, 단계 사이 차이가 작아(1.25배 미만) 위계가 흐린 글자 크기
- **색**: 흰 바탕의 보라 그라디언트, 크림·베이지 팔레트, 색을 고르게 나눈 소심한 팔레트, 색 바탕 위의 회색 글자
- **배치**: 예상 가능한 배치와 컴포넌트를 늘어놓은 구성, 짜깁기한 배치, 정보에 비해 큰 컨테이너, 카드 안의 카드, 아이콘 타일을 쌓은 구성, 모든 섹션 위에 되풀이한 작은 라벨, 첫 제목 위의 알약 모양 라벨
- **장식**: 한쪽 가장자리만 굵은 색 테두리, 어두운 배경의 발광과 원형 조명, 꾸미기용 점·격자 무늬, 기본 도형을 모아 만든 첫 화면 그림, 흐르는 글자 띠, 깜박이는 터미널 커서
- **움직임**: 튀어 오르는 곡선, 이미지에 가리키면 커지는 효과
- **마감**: 좁은 안쪽 여백, 화면 끝에 붙은 본문, 넘치거나 잘린 글

목록 확인일: 2026-10-07. 근거는 [Anthropic 프론트엔드 프롬프트](https://platform.claude.com/cookbook/coding-prompting-for-frontend-aesthetics), [Impeccable 검사 규칙](https://impeccable.style/detector), [NN/g 프롬프트로 만든 화면](https://www.nngroup.com/articles/vague-prototyping/)이다. 흔한 기본값은 모델과 시기에 따라 바뀐다. 금지만 하면 다른 기본값으로 옮겨 가므로 DESIGN.md에 대신 쓸 값을 정한다.

## 코드 점검

스크린샷을 찍기 전에 화면 코드에서 찾을 수 있는 문제를 먼저 찾는다. 코드에서 찾으면 매번 같은 결과가 나온다. [DESIGN.md](DESIGN.md) 개요의 화면 검사 도구와 프로젝트의 린터를 소스 파일에 실행하고, 도구가 잡지 못하는 아래 항목만 코드 검색으로 찾는다. [Impeccable](https://github.com/pbakaus/impeccable)의 `npx impeccable detect`는 코드, HTML 파일, 주소에서 흔한 기본값과 품질 문제를 찾는다.

- 토큰 파일에 없는 색, 크기, 간격, 모서리, 그림자 값
- 확대를 막는 viewport 설정(`user-scalable=no`, `maximum-scale=1`)
- 붙여넣기를 막는 처리(`onPaste`에서 `preventDefault`)
- `transition: all`
- 대신할 포커스 표시 없이 쓴 `outline: none`
- `a` 없이 클릭으로 하는 페이지 이동, 클릭 처리를 붙인 `div`와 `span`
- 크기가 없는 이미지, 라벨이 없는 입력 요소, `aria-label`이 없는 아이콘 버튼
- 가상 스크롤 없이 그리는 큰 목록
- 직접 쓴 날짜와 숫자 형식
- 이유 없는 자동 포커스, 압축한 동영상으로 바꿀 수 있는 움직이는 GIF
- 누르기와 키보드 대안이 없는 몸짓 동작
- 튀어 오르는 곡선. 이름에 `bounce`, `elastic`이 들어가거나 `cubic-bezier()`의 두 번째나 네 번째 값이 0~1 밖이다.
- 주요 브라우저가 모두 지원한 지 30개월이 지나지 않은 CSS 기능을 `@supports` 없이 쓴 곳. [web.dev의 브라우저 지원 기준](https://web.dev/baseline)으로 확인한다. ESLint가 있으면 `@eslint/css`의 `use-baseline` 규칙으로 찾는다.

같은 문제가 여러 작업에서 되풀이되면 린터 규칙이나 커밋 전 검사로 옮기자고 보고에 제안한다.

## 화면 점검

- 기준 폭마다 화면을 찍는다. 빈 상태, 오류, 아주 긴 데이터를 넣은 화면도 찍는다.
- 참고 화면이나 받은 디자인이 있으면 스크린샷과 나란히 놓고 차이를 목록으로 쓴 뒤 고친다.
- 넘침, 대비처럼 잴 수 있는 것은 눈으로 보지 않고 브라우저의 계산된 스타일과 코드로 잰다.
- DESIGN.md 개요의 화면 검사 도구를 기준 폭마다 화면 주소로 실행한다. 글자 위계, 넘침, 좁은 여백, 대비는 그려 봐야 잡힌다. 소스 파일 검사만으로 대신하지 않는다.
- 화면 검사 도구를 아직 정하지 않았으면 화면 점검을 마친 것으로 보지 않는다. [DIRECTION.md의 시각 체계 정하기](DIRECTION.md#시각-체계-정하기)대로 도구를 정해 사람에게 확인받는다.
- 같은 문제를 두 번 고쳐도 틀리면 고치기를 멈추고, 알게 된 것을 정리해 새 세션에서 다시 시작한다.

## 판정

새 화면과 구조를 크게 바꾼 화면은 만들지 않은 새 세션이나 하위 에이전트가 판정한다. 리뷰어에게는 스크린샷, 참고 화면, 잰 값, DESIGN.md, RULES.md, 이 파일만 준다. 화면을 만든 쪽의 설명은 주지 않는다.

- **위계**: 가장 중요한 정보와 동작이 먼저 보인다.
- **명확성**: 무엇을 하는 화면이고 다음에 무엇을 하면 되는지 바로 알 수 있다.
- **인상**: DESIGN.md 개요의 원하는 인상이 전해진다.
- **흔한 기본값**: [흔한 기본값](#흔한-기본값)이 이유 없이 들어가 있지 않다.
- **규칙**: [RULES.md](RULES.md)를 어긴 곳이 없다.
- **참고 화면과의 차이**: 참고 화면이나 받은 디자인과 다른 곳이 의도한 차이다.

항목마다 통과나 실패와 근거가 된 스크린샷 영역을 쓴다. 실패한 항목에는 고칠 방향을 DESIGN.md의 값이나 토큰 이름으로 쓴다. 문제를 찾으라고 요청받은 리뷰어는 문제가 없어도 무언가를 지적하기 쉽다. 위 항목과 이어지지 않는 지적은 고치지 않고 보고에 참고로 쓴다.
