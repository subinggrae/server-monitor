# 0009. 코어 설정은 코어 이미지에 넣고, 개발과 배포가 같은 이미지를 쓴다

- 상태: 승인
- 날짜: 2026-10-22
- 관련: [요구사항 0010](../requirements/0010-core-image-bundle.md), [ADR 0007](0007-core-app-contract.md)

## 배경과 문제

코어(Prometheus, Alertmanager, Blackbox Exporter)는 공개 이미지를 그대로 쓰고, 설정 파일과 Alert 규칙을 저장소의 `infrastructure/`에서 volume으로 붙여 넣는다. 그래서 코어를 띄우는 서버에는 저장소의 설정 파일과 인터넷이 있어야 한다. 코어를 인터넷에 닿지 않는 내부망 서버에도 설치해야 하고, 그 서버에 저장소를 두기는 어렵다(요구사항 0010).

## 검토한 선택지

- **공개 이미지와 설정 폴더를 함께 옮김**: 빌드가 없고, 서버에서 설정을 바로 고칠 수 있다 / 서버마다 설정 파일이 따로 남아 어느 설정으로 도는지 알기 어렵고, 저장소와 서버의 설정이 어긋나도 알아채지 못한다.
- **설정을 넣은 코어 이미지를 빌드해 파일로 옮김**: 옮길 것이 이미지 묶음과 compose 파일뿐이고, 이미지 태그로 어느 커밋의 설정인지 안다 / 규칙을 바꾸면 다시 빌드해 옮겨야 한다.
- **사내 이미지 저장소(registry)에 올림**: 서버가 이미지를 당겨 받아 편하다 / 내부망에 registry가 있어야 하고, 이번에는 그런 전제가 없다.

## 결정

두 번째 선택지를 고른다(사람 확인: 2026-10-22). 코어 구성 요소마다 공개 이미지를 바탕으로 설정 템플릿, Alert 규칙, `render-config.sh`를 넣은 이미지를 빌드한다. 앱 주소(`MONITORING_APP_ADDRESS`)와 webhook token처럼 서버마다 다르거나 비밀인 값은 이미지에 넣지 않고 실행할 때 받는다.

저장소에서 개발할 때도 같은 빌드 정의로 이미지를 만들어 띄운다(사람 확인: 2026-10-22). 설정 출처가 하나여야 개발에서 확인한 코어와 내부망에 옮긴 코어가 같다.

## 결과

- 좋아지는 점: 내부망 서버에는 저장소와 인터넷이 필요 없다. 띄운 코어의 이미지 태그로 설정의 출처(커밋)를 안다. 개발과 배포의 설정이 어긋나지 않는다.
- 감수할 점:
  - Alert 규칙과 Blackbox 설정을 바꾸면 이미지를 다시 빌드해 옮겨야 한다. 서버에서 바로 고칠 수 없다.
  - 개발 중에도 설정을 바꾸면 `--build`로 다시 띄워야 한다.
  - 이미지 묶음이 수백 MB라 옮기는 시간이 든다.
- 다시 볼 신호: 내부망에 registry가 생길 때, 서버마다 다른 Alert 규칙이 필요해질 때, ARM 서버를 써야 할 때

## 확인 방법

- 리뷰에서 확인: `infrastructure/compose.yml`이 코어 설정 파일을 volume으로 붙이지 않고, 이미지에 비밀값이 들어가지 않는지 본다.
- 빌드 스크립트가 빌드한 이미지로 Prometheus 설정 검사, 규칙 테스트, Alertmanager 설정 검사를 실행한다.
