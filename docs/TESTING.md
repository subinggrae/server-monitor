# 테스트

이 프로젝트에서 무엇을 어떤 테스트와 보안 검사로 검증하는지 정한다. 테스트를 쓰거나 고치기 전, 위험 영역을 건드리는 변경을 리뷰하기 전에 읽는다.

## 원칙

테스트를 쓰고 고칠 때는 다음 원칙을 따른다.

- 테스트의 가치는 개수가 아니라 "실패했을 때 알고 싶은 회귀를 알려주는가"로 판단한다. 그래서 커버리지는 참고 지표일 뿐 목표가 아니다.
- 사용자가 쓰는 방식에 가까운 테스트를 우선한다. 내부 상태, private 함수, 호출 횟수처럼 구현 세부를 검사하는 테스트는 리팩터링만 해도 깨지기 때문이다. 화면 요소는 역할과 화면에 보이는 텍스트로 찾는다.
- 협력 대상은 실제 구현, fake, mock 순으로 고르고, 함수가 호출됐는지보다 결과 상태를 검사한다. mock 위주의 테스트는 유지 비용이 크고 버그를 거의 찾지 못하기 때문이다.
- 기대값은 요구사항과 명세에서 가져온다. 구현을 실행해 나온 값을 기대값으로 옮기지 않는다. 그렇게 만든 테스트는 지금 코드의 버그를 정답으로 굳힌다.
- 보통·큰 변경은 요구사항 완료 기준의 테스트를 구현보다 먼저 쓰고, 실패하는 것을 확인한 뒤 구현한다. 다만 화면 모양처럼 구현하기 전에 정할 수 없는 것은 구현한 뒤에 쓴다.
- 새 테스트는 검사하는 결함이 생기면 실패해야 한다. 그래서 구현 뒤에 쓴 테스트는 검사하는 코드를 잠시 되돌리거나 망가뜨려 실패하는지 보고 원래대로 돌린다.
- 하나의 동작은 그 동작을 확인할 수 있는 가장 낮은 수준에서 한 번만 검사한다.
- 상위 수준 테스트가 잡은 버그를 하위 수준 테스트가 놓쳤다면 하위 수준 테스트를 추가한다.
- 테스트를 지우거나, 건너뛰게 하거나, 기대값을 느슨하게 바꿔서 통과시키지 않는다. 테스트가 틀렸다고 판단하면 그 이유를 보고한다.

## 결정적 실행

같은 커밋이면 누가 언제 어디서 실행해도 결과가 같아야 한다. 가끔 실패하는 테스트는 실패를 알려주지 못하고, 사람과 AI가 진짜 실패도 무시하게 만든다. 결과를 같게 하려면 다음을 지킨다.

- 테스트 명령은 한 번 실행하고 끝나며, 종료 코드가 결과다. watch 모드는 따로 둔다.
- 설치는 lockfile을 그대로 따른다. Frontend는 `npm ci`를 쓴다.
- 단위 테스트와 컴포넌트 테스트는 외부 네트워크에 접근하지 않는다. 대신 외부 서비스를 테스트 대역으로 바꾼다.
- 현재 시각은 고정하거나 주입한다. 시간대와 로케일은 명령 앞의 환경 변수가 아니라 테스트 설정 파일에서 정한다. 개발 PC와 CI의 시간대가 다르고, 운영체제마다 환경 변수를 넣는 방법이 다르기 때문이다. 값은 서비스 사용자의 시간대와 로케일(`Asia/Seoul`, `ko-KR`)로 하고, 시간대에 따라 결과가 달라지는 코드는 다른 시간대에서도 따로 테스트한다.
- 테스트는 실행 순서와 관계없이 통과해야 한다. 순서를 섞어 실행했다면 다시 재현할 수 있게 seed를 남긴다.
- 새로 쓴 테스트는 여러 번 반복 실행해 매번 같은 결과가 나오는지 확인한다.
- 재시도하거나, 고정된 시간만큼 기다리거나, 타임아웃을 늘려서 실패를 숨기지 않는다. 다만 재시도는 CI에서만 켜고, 재시도로 통과한 테스트는 불안정한 테스트로 보고한다. 불안정한 테스트는 이슈를 만들고 빨리 고친다.
- CI는 일부만 실행하게 표시한 테스트(`.only` 등)를 거부하고, 스냅샷을 새로 저장하지 않는다.
- CI는 로컬과 같은 명령을 실행한다. 다만 코드 스캐너처럼 CI에서만 돌 수 있는 단계는 자동 검사 표에 CI 전용이라고 적는다.

이 프로젝트의 설정은 다음과 같다.

- 시간대와 로케일: 아직 정하지 않았다. `frontend/vitest.config.ts`와 `backend/build.gradle`의 test 작업에 시간대 설정이 없다. 테스트 설정 파일에 `Asia/Seoul`을 정한다.
- CI의 재시도와 `.only` 거부: CI 없음. CI를 붙일 때 정한다. E2E는 `frontend/playwright.config.ts`에서 `retries: 0`, `forbidOnly: true`로 로컬에서도 재시도하지 않고 `.only`를 거부한다.

## 테스트 범위

테스트 종류마다 검사하는 계층이 다르다. 범위가 넓을수록 느리므로 적게 쓴다. 화면에만 있는 규칙은 컴포넌트 테스트가, 화면과 API의 계약은 E2E 테스트가 맡는다. 어느 테스트도 Prometheus, exporter, Telegram 같은 외부 시스템에는 연결하지 않는다. 도구를 고른 이유는 [ADR 0014](decisions/0014-frontend-test-tools.md)에 있다.

## 종류별 기준

테스트 종류마다 맡는 책임과 쓰는 경우는 다음과 같다.

| 종류 | 책임 | 쓰는 경우 | 쓰지 않는 경우 | 명령 |
|---|---|---|---|---|
| 정적 검사 | 타입 오류, 문법 오류, 금지 패턴 | 항상, 별도 테스트 없이 | 해당 없음 | `cd frontend && npm run lint`, `cd frontend && npm run build`(타입 검사) |
| 단위 | 분기가 있는 순수 로직: 계산, 변환, 검증 규칙, 외부 HTTP 호출 처리 | 조건이 둘 이상이거나 경계값이 있는 로직(예: 암호화, 설정 바인딩, 메시지 형식, Telegram·Prometheus client) | 단순 전달, getter, 프레임워크 설정, mock만 검사하게 되는 코드 | `scripts/verify fast` |
| 통합 | 실제 Manager Database와 함께 동작하는 API: 저장·조회, migration, SD 응답, webhook | API 엔드포인트, schema, 도메인 경계, 인증 정보 비노출 | 단위 테스트로 충분한 순수 로직 | `scripts/verify all` 또는 `cd backend && ./gradlew test` |
| 컴포넌트 | 화면에만 있는 규칙과 API 호출 처리(API 응답은 테스트가 만듦) | 입력에 따라 칸이나 보내는 값이 바뀌는 화면, Backend 오류를 보여 주는 방식, `lib/api.ts`의 요청·오류 처리 | 분기 없이 값을 그대로 보여 주는 화면, 스타일과 배치 | `cd frontend && npm test` |
| E2E | 화면과 API의 계약(실제 Backend와 빈 Manager Database에 브라우저로 연결) | 운영자가 매일 쓰는 핵심 흐름(지금은 Check 관리, Server SNMP 설정, Telegram 그룹과 알림 연결) | 컴포넌트·통합 테스트로 확인할 수 있는 분기와 예외, 수집 상태(OK·CRITICAL)와 알림 전송 | `cd frontend && npm run test:e2e` |

스냅샷 테스트는 오류 메시지나 직렬화 결과처럼 짧고 리뷰할 수 있는 출력에만 쓴다.

직렬화 후 복원, 정렬, 금액 계산처럼 모든 입력에 성립해야 하는 규칙은 속성 기반 테스트(예: fast-check)를 고려한다. 예시 몇 개로는 쓴 사람이 떠올리지 못한 입력을 검사하지 못하기 때문이다. 다만 라이브러리를 들이는 것은 의존성 변경이다.

### 두 DB 제품에서 같은 검증

통합 테스트는 Testcontainers로 MariaDB와 PostgreSQL container를 각각 띄워 같은 검증을 실행한다. 한쪽에서만 동작하는 SQL을 쓰거나 migration을 한쪽에만 추가하면 다른 쪽 테스트가 실패한다. 그래서 Docker가 필요하다.

- 검증 내용은 `AbstractManagerDatabaseTest` → `AbstractMonitoringApiTest` → `AbstractNotificationApiTest` → `AbstractSnmpApiTest`로 이어지는 abstract class에 쓴다.
- `MariaDbManagerDatabaseTest`와 `PostgresManagerDatabaseTest`가 이 class를 상속하고 DB container만 바꾼다.
- 새 통합 테스트는 해당 영역의 abstract class에 추가한다. 두 제품에서 자동으로 함께 돈다.

### 컴포넌트 테스트

Vitest와 jsdom에서 Testing Library로 화면을 그리고, API 응답은 MSW로 만든다. Docker와 Backend가 필요 없다.

- 테스트가 처리하지 않은 요청을 보내면 그 테스트는 실패한다. 화면이 부르는 API는 모두 테스트에서 응답을 정한다.
- 요소는 사용자가 보는 이름(label, role, 문구)으로 찾는다. CSS class나 component 내부 상태로 찾지 않는다.
- 공통 준비 코드는 `frontend/src/test/`에 있다. 화면은 `renderWithProviders`로 그린다.
- jsdom은 실제 브라우저가 아니다. layout, focus 이동처럼 브라우저에 기대는 동작은 E2E에서 확인한다.

### E2E 테스트

Playwright가 `frontend/e2e/compose.yml`로 E2E 전용 MariaDB, Backend, Frontend container를 띄우고 Chromium으로 흐름을 실행한다. 끝나면 결과와 관계없이 container를 내린다.

- 실행마다 빈 Database로 시작한다. 흐름은 이름에 고유 값을 붙여 실행 순서와 관계없이 통과하게 쓴다.
- 운영용 `compose.yml`과 secret 파일을 쓰지 않는다. Telegram, Prometheus, exporter에는 연결하지 않는다. 그래서 E2E에서 Bot Token이 없다는 안내와 수집 상태 UNKNOWN이 보이는 것은 정상이다.
- 개발용 구성과 Compose project 이름, image tag, port가 겹치지 않는다. port를 바꾸는 방법은 [DEVELOPMENT.md의 명령](DEVELOPMENT.md#명령)에 있다.
- 고정 시간 대기와 재시도를 쓰지 않는다. 저장이 끝나기를 기다려야 하면 화면 문구나 API 응답을 기다린다.
- 실패하면 스크린샷과 trace가 `frontend/test-results/`에 남는다. `npx playwright show-trace <trace.zip>`으로 연다.
- 실행이 중간에 끊겨 container가 남았다면 다음 실행이 먼저 지운다. 직접 지울 때는 `docker compose -p monitoring-manager-e2e down -v`를 쓴다.

### 검증 profile

`scripts/verify`가 검증 진입점이다.

| profile | 실행하는 것 | Docker |
|---|---|---|
| `fast` | Frontend 린트, 컴포넌트 테스트, 빌드, root package를 뺀 Backend 하위 package 테스트 전체 | 필요 없다 |
| `all` | Frontend 린트, 컴포넌트 테스트, 빌드, `./gradlew build`(통합 테스트 포함), E2E 테스트 | 필요하다(E2E용 Chromium도 필요) |

root package(`kr.co.unidocs.monitoring`)의 테스트만 Testcontainers로 Docker를 쓴다. 하위 package의 테스트는 Docker 없이 돈다. `fast`는 이 차이로 테스트를 고른다.

## 보안

기능 테스트가 모두 통과해도 권한 우회, 입력 주입, 비밀값 노출, 취약한 의존성은 남는다. 그래서 도구로 찾을 수 있는 문제는 자동 검사로 찾고, 나머지는 리뷰에서 점검 항목으로 확인한다.

### 보안 기준

이 프로젝트의 보안 기준은 다음과 같다.

- 목표 수준: 아직 정하지 않았다. 정할 때까지 OWASP ASVS 5.0 Level 2로 점검한다.
- 따르는 법과 지침: 아직 정하지 않았다. 공공기관 사업인지 확인한다. 공공기관 사업이면 행정안전부 「소프트웨어 개발보안 가이드」를 따른다. 지금 코드에는 사용자 계정이 없고 개인정보를 저장하는 모델이 없다. 개인정보를 처리하는 기능이 생기면 「개인정보의 안전성 확보조치 기준」을 더한다.

### 자동 검사

어떤 도구를 어디서 실행할지는 프로젝트가 정하고, 정한 도구는 다음 표에 적는다.

| 검사 | 찾는 것 | 언제 | 명령 |
|---|---|---|---|
| 비밀값 | 커밋에 들어간 API 키, 비밀번호, 토큰 | 커밋 전 | 아직 정하지 않음: 도구를 정한다 |
| 의존성(Frontend) | 알려진 취약점이 있는 의존성 | 의존성을 바꿨을 때, 정기 실행 | `cd frontend && npm audit --audit-level=high`(2026-10-08 실행 결과 실패한다: source-map-js의 high 취약점 1건) |
| 의존성(Backend) | 알려진 취약점이 있는 의존성 | 의존성을 바꿨을 때, 정기 실행 | 아직 정하지 않음: 도구를 정한다 |

자동 검사를 운영할 때는 다음을 지킨다.

- AI가 쓴 코드도 사람이 쓴 코드와 같은 검사를 거친다. 검사에서 나온 문제를 고친 뒤에는 다시 실행해 통과하는지 확인한다.
- 자동 검사는 바뀐 코드만이 아니라 저장소 전체를 본다. 그래서 처음 도입하면 기존 문제가 한꺼번에 나온다. 이 기존 문제는 목록으로 만들어 사람이 우선순위를 정하고, 검사 도구의 기준선 기능으로 등록해 CI가 새로 생긴 문제에서만 실패하게 한다.
- 거짓 양성이 많은 규칙으로 막으면 경고를 무시하게 된다. 그래서 막는 규칙은 틀리게 막은 적이 거의 없는 것만 둔다.
- 검사 결과를 예외로 등록할 때는 예외 설정에 이유를 적는다. 이유 없이 실패 기준을 낮추지 않는다.
- 새 취약점은 코드가 바뀌지 않아도 공개된다. 그래서 의존성 검사는 정기 실행에도 넣는다.
- 비밀값이 커밋에 들어갔으면 파일에서 지우는 것으로 끝내지 않는다. 값이 VCS 이력에 남으므로 그 값을 폐기하고 새로 발급한다. CI 로그나 AI와의 대화에 들어간 비밀값도 같다.

### 보안 테스트

보안이 걸린 로직을 테스트하고 고칠 때는 다음을 따른다.

- 인가, 입력 검증, 인증처럼 보안이 걸린 로직은 허용하는 경우와 함께 거부해야 하는 경우를 테스트한다. 예: `토큰이 틀린 Alertmanager webhook 요청은 401을 돌려준다`
- 거부 테스트는 그 로직을 확인할 수 있는 가장 낮은 수준(단위나 통합)에 둔다.
- 보안 약점을 고친 뒤에는 코드에서 같은 종류의 약점을 찾는다.

### 점검 항목

다음은 웹에서 흔한 취약점 목록으로, OWASP Top 10과 CWE Top 25에서 웹에 공통인 것을 골랐다. 요구사항, 계획, 구현, 자체 리뷰, 리뷰의 각 단계에서 이 목록을 다시 본다. 특히 위험 영역을 건드리거나 외부 입력을 다루는 변경은 리뷰 전에 바뀐 코드와 그 코드가 지나는 경로를 영역마다 확인한다.

- **인가**(CWE-862, CWE-863, CWE-639): 서버가 요청마다 사용자의 권한과 대상 데이터의 소유자를 확인한다. 화면에서 버튼을 숨기는 것으로 막지 않는다. 요청의 ID만 바꿔서는 다른 사용자의 데이터에 닿을 수 없다.
- **입력 검증**(CWE-20, CWE-434): 요청 본문, 쿼리, 헤더, 업로드 파일, 외부 API 응답을 서버에서 형식, 길이, 범위로 검증한다.
- **주입**(CWE-89, CWE-78, CWE-22, CWE-918): DB 쿼리는 파라미터 바인딩을 쓴다. 셸 명령, 파일 경로, 요청할 URL에 입력을 그대로 이어 붙이지 않는다.
- **출력**(CWE-79): HTML에 넣는 값은 프레임워크의 기본 escape를 거친다. `innerHTML`, `dangerouslySetInnerHTML`, `v-html`은 이유를 주석으로 남길 때만 쓴다.
- **인증과 세션**(CWE-287, CWE-352): 비밀번호는 복원할 수 없는 해시로 저장한다. 세션 쿠키에 `HttpOnly`, `Secure`, `SameSite`를 설정한다. 상태를 바꾸는 요청은 CSRF를 막는다.
- **비밀값**(CWE-798): 코드, 설정 파일, 로그, 오류 응답에 비밀값이 없다. 비밀값은 환경 변수나 비밀값 저장소에서 읽는다.
- **개인정보**(CWE-359, CWE-311): 로그와 오류 메시지에 개인정보를 남기지 않는다. 「개인정보의 안전성 확보조치 기준」이 정한 항목(주민등록번호, 여권번호, 운전면허번호, 외국인등록번호, 신용카드번호, 계좌번호, 생체인식정보)은 암호화해 저장하고, 개인정보와 인증정보는 암호화해 전송한다.
- **오류 처리**(CWE-209): 오류 응답에 stack trace, 쿼리, 내부 경로를 노출하지 않는다. 처리 중 예외가 나면 허용이 아니라 거부로 끝난다.
- **로그**(CWE-778, CWE-532): 로그인 성공과 실패, 권한 거부, 개인정보 조회와 내려받기 같은 보안 이벤트를 기록한다. 비밀값과 개인정보 값은 남기지 않는다.
- **설정**(CWE-942): 운영 설정에 디버그 모드, 기본 계정, 모든 출처를 허용하는 CORS(`*`)가 없다. 응답에 HSTS와 `X-Content-Type-Options: nosniff`를 보내고, Level 2 이상이면 CSP도 둔다.
- **의존성**(CWE-1395): 새 의존성은 레지스트리에 실제로 있고 관리되는 패키지다. AI는 없는 패키지 이름을 지어내므로 이름을 레지스트리에서 확인한다. 설치 스크립트(`postinstall` 등)와 알려진 취약점을 확인했다. 라이선스는 [LICENSES.md의 분류](LICENSES.md#분류)를 따른다. lockfile을 함께 커밋한다.
- **CI**: 작업 토큰은 읽기 권한을 기본으로 한다. PR 제목이나 브랜치 이름 같은 외부 입력을 스크립트에 그대로 넣지 않는다. 외부 action은 커밋 SHA로, 이미지는 digest로 고정한다. 외부 PR에 비밀값을 넘기는 트리거(`pull_request_target` 등)를 쓰지 않는다. 배포 자격 증명은 OIDC처럼 짧게 쓰는 것을 쓴다. 내려받아 실행하는 스크립트는 체크섬을 확인한다.
- **에이전트 설정**: 에이전트 권한 설정, 지침 파일, MCP와 hook 설정은 사람이 요청했을 때만 바뀌었다. 밖에서 들여온 지침과 규칙 파일에 보이지 않는 문자가 없다.
- **인증 정보 비노출**: DB 비밀번호, SNMP community, Telegram Bot Token, `APP_SECRET_KEY`가 API 응답, 로그, SD 응답, Prometheus label에 없다. 마스킹한 값도 넣지 않는다. 기준은 [ARCHITECTURE.md의 인증 정보](ARCHITECTURE.md#인증-정보)에 있다.
- **webhook 검증**: Alertmanager webhook은 Bearer token을, Telegram webhook은 webhook secret header를 확인하고, 맞지 않으면 거부한다.

### 전체 점검

변경 단위 점검은 바뀐 코드만 보므로, 기존 코드 전체는 따로 점검한다.

전체 점검은 다음과 같이 한다.

- 주기: 아직 정하지 않았다. 주기를 정한다.
- 방법: 자동 검사를 모두 실행하고, 인증·권한과 외부 입력을 처리하는 코드를 점검 항목으로 읽는다.
- 발견한 문제는 하나씩 별도 변경으로 고친다. 약점 내용과 재현 방법은 공개된 이슈, PR 설명, 커밋 메시지에 쓰지 않고 담당자에게 먼저 알린다. 기록은 접근이 제한된 곳(비공개 보안 신고, 내부 트래커)에 남긴다.

## 버그 수정과 회귀 테스트

버그를 고칠 때마다 테스트를 추가하지는 않는다. 추가할지는 다음 질문으로 판단한다.

> 같은 문제가 다시 생겼을 때 자동으로 발견할 가치가 있는가?

- **추가한다**: 로직 오류, 경계값 오류, 데이터 처리 오류처럼 코드가 바뀌면 다시 생길 수 있는 문제다. 이때는 버그를 재현하는 테스트를 먼저 쓰고, 고치기 전에 실패하는지 확인한 뒤 고친다.
- **추가하지 않는다**: 오타, 문구 변경, 일회성 설정 실수, 외부 서비스 장애처럼 코드로 재발을 막을 수 없거나 막을 가치가 없는 문제다.
- 추가하지 않았다면 이유를 결과 보고에 한 줄로 적는다.

## 위치와 이름

- Backend 테스트는 `backend/src/test/java/` 아래, 대상 class와 같은 package에 `*Test.java`로 둔다. Docker가 필요한 통합 테스트는 root package에 둔다.
- Frontend 컴포넌트 테스트는 대상 파일 옆에 `*.test.ts`나 `*.test.tsx`로 둔다. `describe`에는 대상 이름을 쓴다.
- E2E 테스트는 `frontend/e2e/`에 흐름별 `*.spec.ts`로 둔다.

실패 보고에는 테스트 이름이 가장 먼저 보인다. 그래서 이름만 읽고도 무엇이 깨졌는지 알 수 있게 다음과 같이 쓴다.

- 테스트 이름은 조건과 기대 결과를 평서형 한 문장으로 쓴다. 예: `오류 메시지에 Bot Token을 남기지 않는다`
- 이름에 "그리고"가 필요하면 동작이 둘이므로 테스트를 나눈다.
- 묶음(`describe`)에는 대상이나 조건을 쓰고, 테스트(`it`, `test`)에는 결과까지 담은 문장을 쓴다.
- JUnit은 method 이름에 문장을 쓸 수 없으므로 `@DisplayName`에 문장을 쓴다.
- 새 테스트부터 이 규칙을 따른다. 기존 테스트의 영어 camelCase 이름(예: `neverLeaksBotTokenInErrorMessage`)은 바꾸지 않는다.
