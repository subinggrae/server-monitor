# 문서 작성 가이드

이 저장소의 문서를 어디에, 누구를 위해, 어떤 형식과 문장으로 쓰는지 정한다. 한국어 문장, 문장 부호, 용어, 표기 규칙은 커밋 메시지, 주석, 로그 같은 문서 밖의 글에도 같다. 문서를 만들거나 고치기 전에 읽는다. 그림은 [DIAGRAMS.md](DIAGRAMS.md)를 따른다.

## 문서 체계

`README.md`와 `AGENTS.md`가 진입점이다. 기준 문서(ARCHITECTURE, DEVELOPMENT, TESTING, WRITING, TERMS, LICENSES, DIAGRAMS, PRODUCT, DESIGN과 그 규칙 문서)는 지금의 상태를 설명하고 코드와 함께 고친다. 변경 기록(요구사항, 계획, ADR)은 `docs/templates/`의 형식으로 작업마다 더한다.

문서마다 답하는 질문과 고치는 때는 다음과 같다.

| 문서 | 답하는 질문 | 고치는 때 |
|---|---|---|
| `README.md` | 무엇인가, 어떻게 시작하는가, 어떤 문서가 있는가 | 목적, 시작 방법, 문서 구성이 바뀔 때 |
| `AGENTS.md` | AI는 어떻게 일하는가 | 작업 절차나 AI가 반복하는 실수가 생길 때 |
| `docs/ARCHITECTURE.md` | 시스템은 어떻게 나뉘고 어디를 고쳐야 하는가 | 실행 단위, 디렉터리 책임, 경계가 바뀔 때 |
| `docs/DEVELOPMENT.md` | 코드를 어떻게 쓰고, 실행하고 검증하고 리뷰하고 반영하는가 | 도구, 명령, 코드 작성 기준, 브랜치·커밋·리뷰 규칙이 바뀔 때 |
| `docs/TESTING.md` | 무엇을 어떤 테스트와 보안 검사로 검증하는가 | 테스트 종류, 명령, 기준, 보안 기준이 바뀔 때 |
| `docs/PRODUCT.md` | 누가, 어떤 환경과 제약에서 쓰고, 사용자에게 보이는 글은 어떤 말투로 쓰는가 | 대상, 사용 환경, 제약, 말투가 바뀔 때 |
| `docs/design/DESIGN.md` | AI가 만드는 범위는 어디까지고, 이 제품의 시각 체계는 무엇인가 | 받은 디자인, 시각 체계, 토큰 파일 위치, 트렌드 기록이 바뀔 때 |
| `docs/design/RULES.md` | 모든 화면에 어떤 규칙을 적용하는가 | 고치지 않음(다르게 정한 것은 DESIGN.md에 쓴다) |
| `docs/design/REVIEW.md` | 화면을 만들기 전과 만든 뒤에 무엇을 점검하는가 | 고치지 않음(다르게 정한 것은 DESIGN.md에 쓴다) |
| `docs/design/DIRECTION.md` | 시각 체계, 참고 화면, 트렌드는 어떻게 정하는가 | 고치지 않음(다르게 정한 것은 DESIGN.md에 쓴다) |
| `docs/WRITING.md` | 문서는 어떻게 쓰고, 한국어는 어떻게 쓰는가 | 문서 규칙이나 표기가 바뀔 때 |
| `docs/TERMS.md` | 출처끼리 갈리는 말은 어떻게 쓰기로 했는가 | 출처가 갈리는 말을 새로 정하거나 출처가 바뀔 때 |
| `docs/LICENSES.md` | 바깥 것을 들여도 되는가, 무엇을 들였는가 | 바깥 것을 들이거나 분류 기준이 바뀔 때 |
| `docs/DIAGRAMS.md` | 그림은 언제, 어떻게 그리는가 | 그림 규칙이 바뀔 때 |
| `docs/requirements/NNNN-이름.md` | 이 기능은 무엇을 만족해야 하는가 | 기능을 추가하거나 동작을 바꿀 때 |
| `docs/requirements/NNNN-이름.plan.md` | 이 기능을 어떻게 바꿀 것인가 | 큰 변경을 하는 동안 |
| `docs/decisions/NNNN-이름.md` | 왜 이렇게 결정했는가 | 되돌리기 어려운 결정을 할 때 |
| `docs/templates/` | 요구사항, 계획, ADR은 어떤 형식인가 | 형식을 바꾸기로 합의했을 때 |
| `docs/assets/` | 문서에 들어가는 그림 | 그림을 쓰는 문서를 고칠 때 |

변경 기록 가운데 계획과 ADR은 다음처럼 다룬다.

- **계획**: 큰 변경을 하는 동안만 두고 리뷰가 끝나면 지운다. 시점은 [계획 템플릿](templates/plan.md)의 상태 값 설명을 따른다.
- **ADR**: 승인 후에는 고치지 않고 새 ADR로 대체한다.

### 출처는 한 곳

두 곳에 쓴 내용은 언젠가 서로 어긋난다. 그래서 지식 하나는 한 문서에만 쓰고, 다른 문서에서는 다시 쓰지 않고 그 문서를 링크한다. 이 원칙은 다음처럼 지킨다.

- 같은 내용은 따라 할 짧은 명령처럼 독자가 문서를 오가지 않아야 하는 내용일 때만 다시 쓰고, 이때도 기준 문서를 함께 링크한다. 예: AGENTS.md의 자주 쓰는 명령
- 명령은 `DEVELOPMENT.md`, 테스트 기준은 `TESTING.md`, 구조는 `ARCHITECTURE.md`가 기준이다. README와 AGENTS.md는 이들을 링크한다.
- AGENTS.md에는 README와 docs에 있는 개요나 설명을 옮겨 쓰지 않는다. 기존 문서와 겹치는 지침은 비용만 늘릴 뿐 작업 결과를 낫게 하지 않는다.
- 코드를 바꾸면 같은 변경에서 관련 문서도 고친다.

### 문서를 고칠 때

틀린 문서는 없는 문서보다 해롭다. 그래서 문서는 쌓아 가지 않고 지금 상태에 맞게 고친다. 고칠 때는 다음을 지킨다.

- 새 내용을 쓰기 전에 같은 주제를 다룬 문장을 찾는다. 있으면 그 자리에서 고쳐 쓰고, 문서 끝이나 새 절에 덧붙이지 않는다.
- 새 내용과 맞지 않게 된 문장은 같은 변경에서 지운다. 지난 내용은 VCS 이력에 있으므로, 기준 문서에 "예전 방식", "기존 내용" 같은 절을 남기지 않는다.
- 통째로 다시 쓰면 세부가 사라지므로, 문서 전체를 다시 요약해 쓰지 않고 바꿀 문장만 고친다.
- 요구사항과 ADR은 지우지 않는다. 다른 결정이 대신하면 상태를 대체됨으로 바꾸고 대체한 문서를 링크한다.
- 틀린 절을 이번 변경에서 고칠 수 없으면 그 절을 지우거나 틀렸다고 표시하고, 보고에 쓴다.

### 새 문서를 만드는 기준

위 표에 있는 문서로 먼저 해결한다. 새 문서는 다음 가운데 하나 이상이 성립하고 기존 문서에 넣으면 목적이 흐려질 때만 만든다.

- 독자가 다르다.
- 읽는 시점이 다르다. 예: 그림을 그릴 때만 읽는 규칙
- 따로 링크할 가치가 있다.

길다는 이유만으로 나누지 않는다. 다만 AI가 작업할 때마다 읽는 `AGENTS.md`는 길수록 AI가 지시를 덜 지키므로 200줄을 넘으면 나눈다. 반대로 한두 문장짜리 문서나 같은 질문에 답하는 짧은 문서가 여럿이면 합친다. 다른 문서에 이미 있는 내용은 새로 쓰지 않고 링크한다.

`ARCHITECTURE.md`는 하위 시스템이 따로 배포되거나 기술 스택이 다르고, 코드 지도가 한 화면을 넘을 때 `docs/architecture/하위-시스템.md`로 나눈다. 이때도 전체 구조, 실행 단위, 공통 경계는 `ARCHITECTURE.md`에 남긴다.

### 문서가 커졌을 때

문서를 고치다가 다음이 보이면 나눌지 검토한다.

- 한 문서가 둘 이상의 질문에 답한다.
- 일부 절만 다른 때 읽히거나 다른 사람이 읽는다.
- AI가 작업할 때마다 읽는 `AGENTS.md`가 200줄을 넘는다.

나누기로 하면 다음 순서로 고친다.

1. [새 문서를 만드는 기준](#새-문서를-만드는-기준)으로 나눌 이유를 확인한다.
2. 옮긴 절이 있던 자리에는 한두 줄 안내와 새 문서 링크만 남긴다. 옮긴 내용을 요약해 다시 쓰지 않는다.
3. README와 AGENTS.md의 문서 표, 이 문서의 문서 체계 표에 새 문서를 더한다.
4. 옮긴 제목을 가리키던 링크를 새 위치로 고친다.
5. `node scripts/check-docs.mjs`로 깨진 링크가 없는지 확인한다.

AI는 맡은 작업의 범위 밖에서 나눌 필요를 발견하면 나누지 않고, 나눌지 [AGENTS.md의 사람에게 묻기](../AGENTS.md#사람에게-묻기)대로 묻는다.

### 만들지 않는 문서

다음 문서는 저장소에 남기지 않는다.

- 작업이 끝난 뒤의 보고서와 요약. 보고는 대화와 PR 설명에 쓰고, 남길 결정은 ADR로 옮긴다. 진행 중인 작업의 상태와 다음 세션에 넘길 내용은 계획 문서에 두고, 계획은 작업이 끝나면 지운다.
- 탐색용 진입점(README)이 아니면서 링크만 모은 문서
- 빈 자리표시자 문서, 쓰지 않는 템플릿 사본
- 작업 중에 만든 임시 파일

## 독자

문서마다 주로 읽는 독자가 다르므로, 쓰는 방식을 독자에 맞춰 정한다.

- **AI**: `AGENTS.md`, 하위 `AGENTS.md`를 주로 읽는다.
  - 코드, README, 기준 문서로 알 수 없는 것만 쓴다. 저장소 개요와 모델이 이미 아는 일반 지식은 쓰지 않는다.
  - 한 줄에 지시 하나를, 지켰는지 확인할 수 있게 구체적으로 쓴다. 예: "코드를 깔끔하게" 대신 "들여쓰기는 공백 두 칸". 명령은 실제로 실행해 본 것만 쓴다.
  - 하지 말 것보다 할 것을 쓰고, 판단이 필요한 지시에는 이유를 한 구절 붙인다. 이유가 있으면 AI가 비슷한 다른 상황에도 맞게 판단한다.
  - 선택지를 늘어놓지 않고 기본값 하나와 예외를 쓴다. 서로 부딪치는 지시를 두지 않는다. 부딪치면 AI가 아무것이나 고른다.
  - 같은 대상은 같은 용어로 부른다. 날짜가 지나면 틀리는 정보를 쓰지 않는다.
  - 말투, 응답 분량, 외부 자료를 참고하라는 지시는 잘 지켜지지 않으므로, 넣기 전에 꼭 필요한지 본다.
  - 설명은 기준 문서로 링크한다.
- **AI와 사람**: `docs/`의 기준 문서, 요구사항, 계획, ADR을 주로 읽는다. 제목과 문단의 첫 문장만 이어 읽어도 내용을 짐작할 수 있게 쓰고, 나란한 항목은 표와 목록으로 보여 준다. 그렇다고 설명을 제목과 기호에 맡기지는 않는다. 제목을 지워도 본문이 이어 읽혀야 한다. 결정에는 이유를 함께 쓴다. 이유는 사람에게 맥락이 되고 AI에게 판단 근거가 된다.
- **사람**: `README.md`, PR 설명, 결과 보고를 주로 읽는다. 결론과 다음에 할 일을 먼저 쓰고, 판단에 필요한 만큼만 쓴다.

독자와 관계없이, 사람은 화면의 글을 훑어 읽는다는 점을 기억한다. 그래서 제목, 목록 항목, 표 칸의 첫 단어에 핵심어를 두고, 문단은 [문단](#문단)대로 첫 문장에 핵심을 쓴다.

## 문서 유형

한 절에는 한 유형만 담는다. 유형이 섞이면 절을 나누고 링크한다. 유형마다 답하는 질문과 쓰는 방식은 다음과 같다.

| 유형 | 답하는 질문 | 쓰는 방식 | 예 |
|---|---|---|---|
| 설명 | 왜 이렇게 됐고 어떻게 동작하는가 | 맥락, 이유, 버린 대안 | ARCHITECTURE.md, ADR |
| 절차 | 어떻게 하는가 | 전제, 번호 단계, 결과 확인 | DEVELOPMENT.md의 준비 |
| 참조 | 무엇이 있는가 | 같은 형식을 반복하는 표와 목록 | DEVELOPMENT.md의 명령 표 |
| 문제 해결 | 이 증상은 어떻게 고치는가 | 증상, 원인, 해결 | 설치 실패 |

유형별로 다음을 지킨다.

- **설명**: 절차를 넣지 않는다.
- **참조**: 설명을 섞지 않는다.
- **문제 해결**: 관련 절차 바로 뒤에 둔다.

### 절차

절차는 다음처럼 쓴다.

- 절차 앞에 전제 조건을 쓴다. 전제 조건은 필요한 도구, 권한, 먼저 해야 할 일이다.
- 단계는 번호 목록으로 쓰고 한 단계에 한 동작만 담는다. 단계 안에서는 위치를 먼저 쓰고 동작을 다음에 쓴다. 예: "`backend/`에서 `npm test`를 실행한다."
- 단계가 하나뿐이면 번호 없이 한 문장으로 쓴다.
- 절차 끝에는 결과를 확인하는 방법으로 예상 출력이나 확인 명령을 쓴다.
- 명령과 출력은 다른 코드 블록에 둔다. 복사해서 실행할 블록에는 `$` 같은 프롬프트나 생략 기호를 넣지 않는다.
- 단계가 일곱 개를 넘으면 나누거나 줄일 방법부터 찾는다.

### 절차를 줄이는 제안

문서로 설명하기 어려운 절차는 따라 하기도 어렵다. 절차를 쓰다가 다음이 보이면 문서를 늘리기 전에 더 간단한 방법을 제안한다.

| 보이는 것 | 제안 |
|---|---|
| 여러 명령을 차례로 실행해야 한다 | 스크립트 하나로 묶는다(예: `package.json`의 `setup` 스크립트) |
| 매번 같은 값을 입력하거나 고른다 | 기본값이나 예시 설정 파일을 둔다 |
| 사람이 결과를 눈으로 확인해야 한다 | 확인 명령이나 테스트로 바꾼다 |
| 환경마다 단계가 다르다 | 차이를 스크립트 안에서 처리한다 |

AI는 문서 작업 중에 스크립트나 설정을 직접 바꾸지 않는다. 대신 바꿀지 [AGENTS.md의 사람에게 묻기](../AGENTS.md#사람에게-묻기)대로 묻고, 사람이 바꾸기로 하면 별도 변경으로 바꾼 뒤 문서를 새 방법으로 고친다.

## 한국어

문서는 평서형(`-다`)으로 쓰고, 한 문서에서 `-습니다`와 `-다`를 섞지 않는다. 표 칸, 제목, `상태: 초안`처럼 이름표 뒤에 오는 짧은 값은 명사형으로 끝내도 된다. 자리가 좁고 값 하나만 담는 곳이기 때문이다. 반면 설명이 들어가는 목록 항목은 주어와 조사를 갖춘 문장으로 쓴다. 명사형으로 줄이면 조사와 어미가 함께 빠지고, 그것들이 나르던 원인, 조건, 목적도 사라진다.

### 문장

한 문장에는 한 가지 내용만 담는다. 다만 긴 문장을 나누면 앞뒤 문장의 관계도 함께 끊긴다. 그래서 나눈 문장은 `그래서`, `하지만`, `예를 들어`, `이 값은` 같은 접속어나 지시어로 시작해 관계를 다시 드러낸다.

- **이렇게 쓰지 않는다**: 토큰을 확인하고 만료됐으면 갱신하며 실패하면 로그인 화면으로 보내야 한다.
- **이렇게 쓴다**: 토큰이 만료됐으면 갱신한다. 갱신에 실패하면 로그인 화면으로 보낸다.

짧은 문장을 관계없이 늘어놓은 글도 읽기 어렵다. 독자가 문장 사이의 관계를 스스로 짐작해야 하기 때문이다.

- **이렇게 쓰지 않는다**: 캐시를 쓰지 않는다. 주문 상태가 자주 바뀐다. 요청마다 조회한다.
- **이렇게 쓴다**: 주문 상태가 자주 바뀌어서 캐시를 쓰지 않는다. 대신 요청마다 서버에서 새로 조회한다.

문장을 쓸 때는 다음도 지킨다.

- **조사와 어미**: 조사와 어미가 원인, 조건, 목적을 나르므로 줄이지 않는다. 예: "계획 수립, 시행" 대신 "계획을 세워 시행한다"
- **명사 나열**: 명사를 쉼표나 `및`으로 길게 잇지 않는다. 나란한 항목이면 목록으로 쓰고, 서로 관계가 있으면 동사로 푼다. 예: "연결 정보 설정 및 초기화가 필요하다" 대신 "연결 정보를 설정한 뒤 초기화한다"
- **주어**: 독자가 따라 하는 절차에서는 주어를 생략한다. 시스템, 팀, 결정을 설명하는 문장에는 누가 하는지를 쓴다. 예: "요청을 거부한다" 대신 "API 서버가 요청을 거부한다"

자주 틀리는 표현은 다음 표대로 고친다.

| 규칙 | 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|---|
| 주어와 동작을 분명하게 | 설정이 완료되어야 실행이 가능하다 | 설정을 마친 뒤 실행한다 |
| 이중 피동 금지 | 값이 저장되어진다, 보여진다 | 값을 저장한다, 보인다 |
| 빈 동사 대신 실제 동작 | 배포를 진행한다, 검증을 수행한다 | 배포한다, 검증한다 |
| 번역투 줄이기 | API를 통해 조회한다 | API로 조회한다 |
| 번역투 줄이기 | 배포 절차에 대해 설명한다 | 배포 절차를 설명한다 |
| 번역투 줄이기 | 테스트에 있어서 중요한 점 | 테스트에서 중요한 점 |
| 번역투 줄이기 | 세 개의 모듈을 가지고 있다 | 모듈이 세 개 있다 |
| 직접 서술 | 이 값은 캐시 키로 사용되는 것이다 | 이 값은 캐시 키로 쓴다 |
| 모호한 표현 금지 | 적절한 크기로 나눈다, 일부 브라우저에서 문제가 있을 수 있다 | 300줄 안팎으로 나눈다, Safari 16에서 날짜 입력이 비어 보인다 |
| 군더더기 금지 | 앞서 설명했듯이, 참고로 말하자면 | 바로 본론을 쓴다 |

군더더기로 지우는 것은 "앞서 설명했듯이", "이제 알아보겠다"처럼 글의 흐름을 설명하는 말이다. 문장 사이의 관계를 알리는 접속어는 군더더기가 아니므로 남긴다.

### 문단

문단은 주제 하나를 다루는 논리 단위다. 첫 문장에 그 문단의 핵심을 쓰고, 이어지는 문장으로 이유, 예, 조건을 붙여 뒷받침한다. 주제와 관계없는 문장은 다른 문단으로 옮기거나 지운다.

절과 문서도 같은 방식으로 시작한다. 규칙이나 세부 설정을 먼저 늘어놓지 않는다. 무엇을 위한 내용이고 읽으면 무엇을 할 수 있는지를 먼저 쓴다.

문단의 길이와 쓰임은 다음을 따른다.

- 문단은 3~5문장 안팎으로 쓴다. 한 문장짜리 문단이 이어지면 합칠 수 있는지 본다. 짧은 문단만 이어지면 글이 끊겨 읽힌다.
- 원인과 결과, 주장과 이유, 대조는 목록으로 쪼개지 않고 문단으로 쓴다. 글머리표는 항목 사이의 관계를 보여 주지 못한다.

### 문장 부호

국립국어원 「한글 맞춤법」의 문장 부호 규정을 따른다. 자주 쓰는 부호는 다음 표대로 쓴다.

| 부호 | 쓰는 때 | 띄어쓰기 | 예 |
|---|---|---|---|
| 가운뎃점 `·` | 여러 말을 하나의 단위로 묶을 때 | 앞뒤에 붙인다 | 인증·권한 |
| 쉼표 `,` | 낱낱이 나열할 때 | 뒤만 띄운다 | 테스트, 린트, 빌드 |
| 쌍점 `:` | 이름 뒤에 설명을 붙일 때 | 앞은 붙이고 뒤는 띄운다 | 상태: 초안 |
| 물결표 `~` | 범위 | 앞뒤에 붙인다 | 3~5문장 |
| 빗금 `/` | 대비되는 말 | 앞뒤에 붙인다 | 성공/실패 |
| 소괄호 | 원어, 보충 설명 | 여는 괄호를 앞말에 붙인다 | ADR(Architecture Decision Record) |

그 밖에 다음을 지킨다.

- 시각과 비율의 쌍점은 앞뒤를 붙인다. 예: `10:20`
- 제목, 표 칸, 명사형으로 끝나는 목록 항목, 그림 이름표에는 마침표를 찍지 않는다. 문장으로 끝나는 항목은 찍는다.
- 숫자와 단위는 붙여 쓴다. 예: `24px`, `3초`, `20%`
- 영어 낱말 뒤의 조사는 영어 발음에 맞춘다. 예: API를, PR이, CI가

### 용어

용어는 다음 기준으로 쓴다.

- 코드, 명령, 파일 이름, 설정 키, 제품 이름은 원문 그대로 쓰고 코드 서식으로 표시한다. 예: `git commit`, `main`, `.env`
- 기술 용어는 한국 개발자와 디자이너가 실제로 쓰는 말로 쓴다. 영어 용어를 우리말로 새로 옮기지 않는다. 옮긴 말은 읽는 사람이 원래 용어를 떠올려야 해서 읽기가 더 느리고, 다른 뜻으로 읽히기도 쉽다. 예: header를 "머리", elevation을 "높이", placeholder를 "자리표시"로 옮기면 각각 신체, CSS `height`, 다른 기능으로 읽힌다.
- 용어는 쓸 때마다 출처를 찾아 정한다. 이미 문서에 쓰인 말이라고 해서 근거가 되지는 않는다. 먼저 [TERMS.md](TERMS.md)에서 찾고, 없으면 다음 순서로 실제 쓰임을 확인한다.
  1. 이 프로젝트의 코드, 설정, 쓰는 도구의 화면에 나오는 이름을 본다. 예: `test:watch`가 있으면 watch 모드
  2. 쓰는 디자인 시스템과 프레임워크의 한국어 문서를 본다. 화면 구성 요소는 KRDS 등 디자인 시스템의 이름을 쓴다. 예: 헤더, 모달, 토스트, 페이지네이션
  3. 쓰는 도구의 공식 한국어 번역과 용어집을 본다. 예: Git·SVN 메시지 번역, GitLab 화면, Kubernetes와 MDN의 한국어 용어집. 기계 번역한 문서는 근거로 쓰지 않는다.
  4. 출처끼리 다르면 개발 문서와 업계에서 더 널리 쓰는 쪽을 고른다.
  5. 개발 문서에 쓰임이 없는 일반 낱말은 표준국어대사전에서 찾는다.
- 출처끼리 갈리거나 출처에 답이 없는 말을 하나로 정했으면, 또는 자연스러워 보이지만 쓰지 않기로 한 말이 있으면 TERMS.md에 근거와 확인일을 붙여 행을 더한다. 출처 하나가 분명히 답하는 말은 더하지 않는다.
- 개발 현장에서 굳어진 외래어는 한글로 쓴다. 외래어 표기법도 굳어진 외래어는 관용을 존중한다. Git의 동작은 음차하고 `하다`를 붙여 쓴다. 예: 커밋한다, 푸시한다, 리베이스한다, 브랜치, 빌드, 로케일
- 한글로 옮기면 뜻이 흐려지거나 실제로 쓰는 한국어를 확인하지 못한 용어는 영어로 쓴다. 예: diff, PR, CI, API, E2E, worktree, front matter
- 우리말로 쓰는 것은 개발자가 그 우리말을 이미 쓰는 경우뿐이다. 예: 저장소, 배포, 병합, 요구사항, 작업 사본
- 처음 나오는 약어는 풀어 쓴다. 예: ADR(Architecture Decision Record)
- 이 문서의 독자가 모를 수 있는 용어는 처음 쓸 때 한 문장으로 설명한다. 이런 용어는 쓰는 사람에게 익숙한 말이라 설명이 필요하다는 것을 알아차리기 어렵다. 설명하지 않은 용어는 제목에 쓰지 않는다.
- 한 개념에는 한 용어만 쓰고, 한 용어를 두 개념에 쓰지 않는다. 예: "리뷰 요청"은 리뷰어에게 리뷰를 부탁하는 일이므로 PR을 가리키는 말로 쓰지 않는다.

### 제목

제목은 다음처럼 쓴다.

- 명사형으로 쓰고 30자를 넘기지 않는다. 같은 수준의 제목은 같은 형태로 맞춘다. 예: `변경 반영 단계`, `버그 수정과 회귀 테스트`
- 물음표와 느낌표를 쓰지 않는다.
- 제목만 읽어도 내용을 짐작할 수 있게 핵심어를 앞에 둔다.
- 제목 수준을 건너뛰지 않는다. 하위 제목은 하위 주제가 둘 이상일 때만 둔다. 제목 바로 아래에 다른 제목을 두지 않는다.
- 제목에 링크를 넣지 않는다.

## 형식

문서의 형식은 다음을 따른다.

- 다른 문서나 절을 가리킬 때는 문서 이름과 제목으로 링크한다. 예: `[DEVELOPMENT.md의 커밋](DEVELOPMENT.md#커밋)`
- `3장`, `다음 절`, `위에서 설명한`처럼 위치나 번호에 기대는 표현을 쓰지 않는다. 이런 표현은 문서가 바뀌면 의미를 잃는다.
- 링크 문구는 대상을 설명한다. "여기", "이 문서"를 링크 문구로 쓰지 않는다.
- 목록은 나란한 항목, 조건, 예외, 순서에 쓰고, 설명은 [문단](#문단)으로 쓴다. 목록과 표 앞에는 무엇을 모은 것인지 알려 주는 문장을 둔다.
- 순서가 있는 절차는 번호 목록, 순서가 없는 항목은 글머리표 목록으로 쓴다. 항목이 하나뿐이면 목록으로 만들지 않는다. 다만 `- 문체:`처럼 이름표가 붙은 줄과, 규칙을 하나씩 더해 가는 절(지켜야 할 경계, 프로젝트 고유 규칙 등)은 항목이 하나여도 목록으로 둔다.
- 항목마다 비교할 속성이 세 가지 이상이면 표로 쓴다. 열이 하나뿐인 표는 목록으로 바꾼다.
- 표의 칸은 짧은 구나 한 문장으로 쓴다. 저장소 화면의 본문 폭이 좁아서 긴 칸은 여러 줄로 감기거나 가로로 밀리기 때문이다. 칸에 문장이 여럿 필요하면 표 대신 이름표를 붙인 목록으로 쓴다. 같은 열의 칸은 같은 형태로 맞추고, 빈 칸 대신 `없음`을 쓴다.
- 굵은 글씨는 목록 항목 앞의 짧은 이름표에만 쓴다. 강조는 낱말 선택으로 한다.
- 알림 블록(`> [!NOTE]` 등)은 한 문서에 한두 개까지 쓰고 연달아 두지 않는다. 내용이 두 문장을 넘으면 절로 쓴다.
- 접기(`<details>`)에는 대부분의 독자가 읽어야 할 내용을 넣지 않는다.
- 코드 블록 앞에는 무엇을 하는 블록인지 한 문장을 둔다.
- 화면 문구나 오류 메시지를 문서에 옮길 때는 코드 서식으로 감싼다. 그러면 문서와 문체가 달라도 옮긴 글임을 알 수 있다. 예: 빈 제목이면 `제목이 비어 있습니다. 제목을 입력하세요.`를 보여준다.
- 날짜는 `2026-01-31` 형식으로 쓴다. "최근", "현재", "곧"처럼 시간이 지나면 틀리는 말을 쓰지 않는다.
- 아직 정하지 않은 내용은 `아직 정하지 않았다.`라고 쓰고 무엇을 정해야 하는지 덧붙인다. 표 칸에서는 한 문장으로 `아직 정하지 않음: 도구를 정한다`처럼 쓴다. 빈 절, `TBD`, 추측한 값을 남기지 않는다.
- 비밀값, 개인정보, 개인 PC 경로를 쓰지 않는다.

## 문서 밖의 글

커밋 메시지, PR 설명, 리뷰 코멘트, 코드 주석, 문서 주석, 테스트 이름, 로그·오류 메시지도 저장소에 남아 다른 사람이 읽는다. AI의 대화 보고와 AI가 하위 에이전트와 주고받는 글은 저장소에 남지 않지만 작업하는 동안 사람이 화면에서 읽는다. 이 글들도 [한국어](#한국어)의 문장, 문장 부호, 용어, 표기 규칙을 따른다. 글마다 독자와 문체가 다르고, 규칙은 그 글을 쓸 때 읽는 문서에 있다.

| 글 | 독자 | 문체 | 규칙 |
|---|---|---|---|
| 커밋 메시지 | 이력을 읽는 개발자 | 요약은 명사형, 본문은 평서형 | [DEVELOPMENT.md의 커밋](DEVELOPMENT.md#커밋) |
| PR 설명 | 리뷰어 | 합니다체 | [DEVELOPMENT.md의 PR 설명](DEVELOPMENT.md#pr-설명) |
| 리뷰 코멘트 | 변경을 만든 사람 | 해요체 | [DEVELOPMENT.md의 리뷰 코멘트](DEVELOPMENT.md#리뷰-코멘트) |
| 코드 주석 | 코드를 고칠 개발자 | 평서형 | [DEVELOPMENT.md의 코드 주석](DEVELOPMENT.md#코드-주석) |

## AI 지침

`AGENTS.md`와 하위 `AGENTS.md`는 AI가 작업할 때마다, `docs/design/DESIGN.md`는 화면 작업 때마다 읽는다. 이런 문서는 짧을수록 잘 지켜진다. 지시가 늘면 지시를 빠뜨리는 일이 늘고, 필요 없는 지시는 작업을 어렵게 만든다.

### 넣는 것과 넣지 않는 것

지침의 내용은 다음 기준으로 정한다.

- 넣는다: 코드만 읽어서는 알 수 없는 명령, 도구 기본값과 다른 규칙, AI가 반복한 실수와 그 이유. 쓰는 방식은 [독자](#독자)의 AI 항목을 따른다.
- 넣지 않는다
  - 코드에서 알 수 있는 내용. 예: 디렉터리 목록, 의존성 목록
  - README와 기준 문서에 있는 저장소 개요와 설명
  - 린터, 포매터, 타입 검사가 이미 강제하는 규칙
  - "깨끗한 코드를 쓴다"처럼 누구나 아는 관례
  - 가끔 하는 작업의 긴 절차. 기준 문서에 쓰고 언제 읽을지와 함께 링크한다.
- 규칙은 AI가 같은 실수를 반복할 때 한 줄씩 더한다. 더한 뒤에는 AI의 행동이 실제로 바뀌는지 본다.
- 반드시 지켜야 하는 규칙은 지침이 아니라 hook, CI, 린트 설정으로 강제한다. 지침에는 강제력이 없기 때문이다.
- 강조 표현("반드시", "절대로", "IMPORTANT")은 지켜지지 않는 한두 줄에만 쓴다. 여러 줄을 강조하면 어느 것도 두드러지지 않는다.

### 점검

지침 문서를 점검할 때는 처음부터 읽고 줄마다 "이 줄을 지우면 AI가 실수하는가"를 묻는다. 답이 아니면 지운다. design/RULES.md, design/REVIEW.md, design/DIRECTION.md는 고치지 않는 고정 규칙이므로, 이 프로젝트에 맞지 않는 줄은 지우지 않고 DESIGN.md의 고정 규칙과 다르게 정한 것에 쓴다.

점검은 다음 때 한다.

- AI가 지침을 어기거나 같은 실수를 되풀이할 때
- 도구, 명령, 디렉터리 구조를 바꿨을 때
- 큰 변경을 마쳤을 때

줄마다 다음도 함께 확인한다.

| 확인 | 처리 |
|---|---|
| 가리키는 경로, 명령, 스크립트가 지금도 있는가 | 없으면 고치거나 지운다 |
| 도구가 이미 강제하는가 | 지운다 |
| 기준 문서와 같은 내용인가 | 지우고 기준 문서를 링크한다 |
| 다른 지시와 충돌하는가 | 하나로 정하고, 정할 수 없으면 사람에게 묻는다 |
| 한 번만 필요했던 작업 지시인가 | 지운다 |

`node scripts/check-docs.mjs`는 다음을 경고한다.

- 없는 경로와 스크립트
- 강조 남용
- 200줄이 넘는 AGENTS.md
- 여러 문서에 똑같이 들어간 문장
- DESIGN.md에 직접 쓴 색 값

나머지는 사람과 AI가 판단한다. 지침을 지우거나 바꿀 때는 이유를 커밋 본문에 쓴다.
