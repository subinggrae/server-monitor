# 한국어 기술 문서 작성 규칙

AI가 README, 설계 문서, ADR, 운영 문서 등 프로젝트의 영구 문서를 작성하거나 수정할 때 적용한다.

## 사실을 우선한다

현재 코드, 테스트, 설정, schema, CI 또는 기존 문서에서 확인한 내용만 사실로 작성한다.

근거가 없는 목적, 설계 의도, 장점 또는 미래 계획을 추측해 작성하지 않는다.

확인하지 못한 내용은 사실처럼 보완하지 않는다.

## 원본을 문서에 복제하지 않는다

코드나 설정에서 직접 확인할 수 있는 정보를 Markdown에 다시 나열하지 않는다.

예:

- 전체 API 목록
- 전체 DB schema
- 전체 클래스 또는 함수 목록
- 전체 dependency 목록
- 전체 환경변수 목록
- 코드에서 그대로 재구성할 수 있는 호출 관계

필요한 경우 내용을 복사하지 말고 실제 source of truth의 위치를 연결한다.

## 지속적으로 가치가 있는 내용만 남긴다

영구 문서에는 다음과 같은 정보를 우선한다.

- 프로젝트의 목적
- 코드만으로 알기 어려운 제약
- 중요한 결정과 그 이유
- 중요한 trade-off
- 운영자가 알아야 하지만 자동화되지 않은 절차

일회성 코드 분석이나 특정 기능의 현재 구현 설명을 자동으로 영구 문서화하지 않는다.

## 짧고 직접적으로 작성한다

- 한 문단에는 하나의 주제만 작성한다.
- 핵심 정보를 먼저 작성한다.
- 가능한 경우 능동형 문장을 사용한다.
- 불필요한 서론과 반복 결론을 작성하지 않는다.
- 같은 내용을 제목, 본문, 요약에서 반복하지 않는다.

다음과 같은 근거 없는 수식어를 피한다.

- 효율적인
- 강력한
- 유연한
- 확장 가능한
- 원활한
- 다양한
- 최적의

해당 표현이 필요한 경우 구체적인 근거를 함께 작성한다.

## 구조는 정보의 목적에 맞게 사용한다

- 절차와 순서 → 번호 목록
- 순서가 없는 항목 → bullet
- 비교해야 하는 속성이 여러 개 → 표
- 긴 내용을 탐색해야 함 → 설명적인 제목

단순한 문장을 억지로 여러 bullet이나 표로 변환하지 않는다.

## 설명적인 제목을 사용한다

제목만 읽어도 해당 절에서 무엇을 찾을 수 있는지 알 수 있게 작성한다.

나쁜 예:

- 기타
- 참고
- 상세
- 추가 내용

좋은 예:

- 로컬 개발환경 실행
- 인증 서비스 장애 시 복구
- 데이터베이스 변경 제약

## 새 문서보다 기존 문서를 우선한다

새 Markdown 파일을 만들기 전에 다음을 확인한다.

1. 기존 문서에 해당 내용을 추가할 수 있는가?
2. 코드나 설정이 이미 source of truth인가?
3. 이 내용이 영구적으로 유지될 필요가 있는가?
4. 특정 작업을 위해 한 번 생성되는 분석 결과에 불과하지 않은가?

새 문서가 필요하지 않다면 생성하지 않는다.

## ADR을 규칙집으로 사용하지 않는다

ADR에는 중요한 기술적 결정의 배경, 결정 내용, 주요 결과와 trade-off를 기록한다.

일반적인 코딩 규칙이나 반복 작업 절차를 ADR로 만들지 않는다.

## 변경할 때 검증한다

기존 문서를 수정할 때는 실제 코드와 설정이 여전히 문서 내용과 일치하는지 확인한다.

일치 여부를 확인하지 못했다면 임의로 최신 상태라고 표현하지 않는다.
